# status-runner

Read only; changes nothing, except `runner outbox drop` below. Read commands take `--json`.

- `localrunner status`: queue and running jobs with steps and the wait reason. Filters: `--project`, `--source session|github`, `--as <label>`, `--broker <name>`. After the queue it lists the runners that are `stale` or `offline` (name, last seen, silent for); `--json` has the same in a `runners` array per broker (a broker too old to know runners has no such key). A queue that does not move with no runner listed there is waiting for a reason in `explain`. `status --recent [N|DURATION]` adds the orders that left the queue (last N, 10 without a value, or those of a period such as `2h`): final state (`rejected` for a refusal), the reason and who ended it (`cancelled by upgrade: runner_stopped`, `cancelled by <label>: sender_gone` for an order withdrawn by its dead sender, `cancelled by <label>: cancelled_by_user`); `--json` has them in `recent` with `reason` and `cancelled_by`. Use it when an order disappeared from the queue.
- `localrunner status <job-id>`: one job (not with `--html`): the `explain` text and the record of `history show` (state, wait reason, steps). A job id not found on any reachable broker is an error with a non-zero exit; an id used by several clients is reported as the broker says it, and `--client <key>` (also on `explain`) picks the run.
- `status --html [path]`: one self-contained HTML file, default `temp/runner/queue.html`; add `--history` for the history table. `--with-logs` embeds job logs, which may hold secrets of profile commands: use it only when the user asks. Give the user the printed path.
- `localrunner explain <job-id>`: why a job waits, naming the policy rule. A wait reason `занято чужими процессами` means the runner machine has too little free memory or CPU because of foreign load (broker policy `[admission]`); the job starts by itself when the load drops. For a job granted to a runner that has not started it, the text says how long it waits and when the runner last answered (`выдан раннеру r1, ждёт старта уже 12 мин; раннер отвечал 12 мин назад (offline)`): that is a runner that does not take work, not a slow start. A wait `раннер занят заказом J (N мин)` names the job that holds the slot and for how long (a job of another client shows as `чужим заказом` when the visibility policy hides it). For a finished job it also gives the end reason and the peaks; for a cancelled or refused one (every recorded job id answers) the reason code in plain words, who ended it and the detail, for a refusal the unmet requirement (`r1: bash не найден`: the runner lacks the program).
- `localrunner runners [--broker B]`: state, kind (`local`: connected over the broker's local channel; `joined`: connected by key, takes only commit orders; empty from an older broker), platforms, programs, pool load, tags, services, and `enforcement` (`os`: limits of the OS; `watcher`: user-space sampling, approximate on macOS, and the `limit` enforcement mode acts as `warn` there). Runners are grouped by pool under one header (`pool default: memory 12/32 GB free, cpu 6/16 free, tags held: gradle`: the budget all runners of the pool share) and each shows `idle` or `busy` and `can start a job now: yes/no`: `idle` only means no job runs on that runner, `can start a job now: yes` only means that the runner is free, takes work and the pool has at least 1 CPU and 1 MB left; it does not take into account the size of a particular order, reserve and quota rules, foreign load (`[admission]`), orders already queued or backfill holding for the head order, so with `cpu 1/16 free` every idle runner says yes and a 4-CPU order still waits (read `explain`); `can start a job now: no` on an idle runner means the pool is full (memory, CPU), or the runner is stale, offline or draining; there is no dry-run query. Where the visibility policy hides the orders of others, held tags show without job ids, in the pool header and on every runner; `--json` has `pools` per broker (absent from an older broker, which prints the flat list). `localrunner brokers`: known brokers, availability, orders in the outbox.
- `localrunner history [--project --source --as --profile --result --since --limit --platform --runner --broker]`; `--all` shows every run the visibility policy allows; `history show <job-id>` is the full record. Every finished job has its peak memory and disk in MB (`PEAK_MEM_MB`, `PEAK_DISK_MB` of `history`, `peak_mem_mb` and `peak_disk_mb` in `--json` and in `status --json`, `peak mem` lines of `history show`); use them to judge whether the `mem_mb` and `disk_mb` of a profile are set right. A job killed for exceeding its declared `mem_mb` or `disk_mb` ends `failed` with the reason `resource_exceeded` and the text "declared X MB, peak Y MB" (only when the machine owner set `[resources] mode = "kill"` in the broker policy; without the table the default is `warn`: the log holds a warning, the CPU is capped and the process count is limited; with an explicit `off` nothing is limited and only the peaks are recorded). Fix such a job by raising the declared value in the profile, not by retrying. An order the broker refused at intake (more than the pool, a name no runner list has, a secret not allowed for the label) is recorded too: `history` shows it as `rejected` (`history --result rejected` lists them) and `history show` gives the reason; the last column `REASON` of `history` is `cancelled by <actor>: <code>` for a cancelled run (actors: the `--as` label of `cancel`, the sender label, `upgrade`, `down`, `broker`) or the reason code, `cancelled_by` in `--json`; fix the request, not the broker. `localrunner stats [--project --profile --client --since]` for pass rate, waiting time and saturation.
- `localrunner log <job-id> [--step NAME] [--tail N] [-f]`: read with `--tail` or a step, never whole.
- `localrunner dashboard`: live page on loopback only (127.0.0.1 and ::1). Start it as its own background task, give the user the URL from its output, stop it when the user is done. Never expose it beyond loopback.
- `localrunner runner outbox drop [--runner NAME] <job-id>`: when a runner keeps delivering entries of a job the broker already cancelled or lost, closes its pending outbox entries on the running runner and prints `closed N entries of <job-id>`. Refused while the runner still runs that job; never edit `runner.db` by hand.
- If nothing answers, run `localrunner doctor`.
