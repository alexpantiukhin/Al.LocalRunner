# status-runner

Read only; changes nothing, except `runner outbox drop` below. Read commands take `--json`.

- `localrunner status`: queue and running jobs with steps and the wait reason. A queued order that waits for capacity names the jobs that hold the runner (profile, label, running time of the timeout) and ends with `no later than N`, an upper bound (the remaining timeouts of the running jobs ahead plus the timeouts of the queued ones), not a forecast: with several runners the real wait is shorter, and jobs you may not see are summed and not named (`detail` in `--json`, with `requested`: memory, CPU, tags). A queued order shows `priority N`, the effective priority the policy gives it (`priority` in `--json`; absent for a job whose fields you may not see and from an older broker); `explain` names the rule and the attribute that set it, or says `no rule sets a priority: 0`. The `--as` label is the client label: `CLIENT_LABEL` in the columns of `history` and `explain` (the JSON key stays `label`), `Client label` on the dashboard, and the profile labels are `Labels`. Filters: `--project`, `--source session|github`, `--as <label>`, `--broker <name>`. After the queue it lists the runners that are `stale` or `offline` (name, last seen, silent for); `--json` has the same in a `runners` array per broker (a broker too old to know runners has no such key). A queue that does not move with no runner listed there is waiting for a reason in `explain`. `status --recent [N|DURATION]` adds the orders that left the queue (last N, 10 without a value, or those of a period such as `2h`): final state (`rejected` for a refusal), the reason and who ended it (`cancelled by upgrade: runner_stopped`, `cancelled by <label>: sender_gone` for an order withdrawn by its dead sender, `cancelled by <label>: cancelled_by_user`); `--json` has them in `recent` with `reason` and `cancelled_by`. Use it when an order disappeared from the queue. A running job shows `last output 7.0s ago`, how long ago its log last received output (`last_output_ago_ms` in `--json`; absent before the first output, for a job whose fields you may not see, and from an older broker): a large value on a job that normally prints often means the output stalled; read the end of its log with `log <job-id> --tail`, and do not cancel only because of it.
- `localrunner status <job-id>`: one job (not with `--html`): the `explain` text and the record of `history show` (state, wait reason, steps). A job id not found on any reachable broker is an error with a non-zero exit; an id used by several clients is reported as the broker says it, and `--client <key>` (also on `explain`) picks the run.
- `status --html [path]`: one self-contained HTML file, default `temp/runner/queue.html`; add `--history` for the history table. `--with-logs` embeds job logs, which may hold secrets of profile commands: use it only when the user asks. Give the user the printed path.
- `localrunner explain <job-id>`: why a job waits, naming the policy rule. A wait reason `занято чужими процессами` means the runner machine has too little free memory or CPU because of foreign load (broker policy `[admission]`); the job starts by itself when the load drops. For a job granted to a runner that has not started it, the text says how long it waits and when the runner last answered (`выдан раннеру r1, ждёт старта уже 12 мин; раннер отвечал 12 мин назад (offline)`): that is a runner that does not take work, not a slow start. A wait `раннер занят заказом J (N мин)` names the job that holds the slot and for how long (a job of another client shows as `чужим заказом` when the visibility policy hides it). For a finished job it also gives the end reason and the peaks; for a cancelled or refused one (every recorded job id answers) the reason code in plain words, who ended it and the detail, for a refusal the unmet requirement (`r1: bash не найден`: the runner lacks the program).
- `localrunner runners [--broker B]`: state, kind (`local`: connected over the broker's local channel; `joined`: connected by key, never in the zone `local`; empty from an older broker), platforms, programs, pool load, tags, services, and `enforcement` (`os`: limits of the OS; `watcher`: user-space sampling, approximate on macOS, and the `limit` enforcement mode acts as `warn` there). Runners are grouped by pool under one header (`pool default: memory 12/32 GB free, cpu 6/16 free, tags held: gradle`: the budget all runners of the pool share) with a table under it (NAME, STATE, KIND, VERSION, PLATFORM, MEMORY, CPU, DISK, TAGS, READY; `--wide` adds PROGRAMS, ENFORCEMENT, CACHE; `runners <name>` prints a card with everything about one runner: held tags, services, unmet requirements, cache) whose READY column says `yes`, `busy` or `no` (a runner whose declared `[programs]` were not found stays online: `programs not found: ...` is printed in its card and `status` lists it; tell the user which programs, a profile that needs one waits or is refused; a runner older than this binary has its VERSION highlighted and gets the note `<runner>: version X is behind Y: run localrunner upgrade on its machine` under the table: pass that on): `busy` means a job runs on that runner, `yes` only means that the runner is free, takes work and the pool has at least 1 CPU and 1 MB left; it does not take into account the size of a particular order, reserve and quota rules, foreign load (`[admission]`), orders already queued or backfill holding for the head order, so with `cpu 1/16 free` every idle runner says yes and a 4-CPU order still waits (read `explain`); `no` on an idle runner means the pool is full (memory, CPU), or the runner is stale, offline or draining; there is no dry-run query. Where the visibility policy hides the orders of others, held tags show without job ids, in the pool header and on every runner; `--json` has `pools` per broker (absent from an older broker, which prints the flat list). `localrunner brokers`: a table of the known brokers: zone, availability, version (highlighted when it differs from this binary), orders in the outbox. The output is colored and shortened to the window only in a terminal; piped or with `NO_COLOR` it is plain text (use `--json` to parse).
- `localrunner history [--project --source --as --profile --result --since --ran-since --ran-until --limit --platform --runner --broker]`; `--all` shows every run the visibility policy allows; `history show <job-id>` is the full record. `--since` keeps the runs queued since a time (the enqueue time), while `--ran-since` and `--ran-until` keep the runs that were running at some moment of a window (started at or before its end and not finished before its start; a run still going counts, an order that never started does not): use them to find what ran beside a job that timed out. `history` lists the most recently finished runs first (the `QUEUED`, `STARTED` and `FINISHED` columns, `-` for a time not reached, and `queued_at`, `started_at`, `finished_at` in `--json`; a run without a finish time comes last, and `--limit` keeps the most recently finished). Every finished job has its peak memory and disk in MB (`PEAK_MEM_MB`, `PEAK_DISK_MB` of `history`, `peak_mem_mb` and `peak_disk_mb` in `--json` and in `status --json`, `peak mem` lines of `history show`); use them to judge whether the `mem_mb` and `disk_mb` of a profile are set right. A job killed for exceeding its declared `mem_mb` or `disk_mb` ends `failed` with the reason `resource_exceeded` and the text "declared X MB, peak Y MB" (only in the `kill` mode, set by `[resources] mode` in the broker policy or by the runner owner's `[limits] enforce`, which wins; in the `limit` mode a job that fails after reaching the OS memory limit gets the same reason, keeps its exit code and was not killed; without the table the default is `warn`: the log holds a warning, the CPU is capped and the process count is limited; with an explicit `off` nothing is limited and only the peaks are recorded). Fix such a job by raising the declared value in the profile, not by retrying. An order the broker refused at intake (more than the pool, a name no runner list has, a secret not allowed for the label) is recorded too: `history` shows it as `rejected` (`history --result rejected` lists them) and `history show` gives the reason; the last column `REASON` of `history` is `cancelled by <actor>: <code>` for a cancelled run (actors: the `--as` label of `cancel`, the sender label, `upgrade`, `down`, `broker`) or the reason code, `cancelled_by` in `--json`; fix the request, not the broker. `localrunner stats [--project --profile --client --since]` for pass rate, waiting time and saturation.
- `localrunner log <job-id> [--step NAME] [--tail N] [-f]`: read with `--tail` or a step, never whole. A value hidden because of its name is shown as `***(name: command)`: the masker did it, the program did not print it; the stored log is intact.
- When `status`, `doctor`, `up` or `down` print `state directory: <path> (from LOCALRUNNER_STATE_DIR)` to stderr, the answer is about that directory, not the usual installation: unset the variable before judging whether the real hub runs.
- `localrunner dashboard`: live page on loopback only (127.0.0.1 and ::1). The command starts the dashboard in the background itself, prints the link on one line (it carries a one-time token) and exits, so it needs no background task of yours; closing the terminal does not stop the page. Give the user the link from the output and do not write it to logs or files. A repeated call finds the running dashboard of this user and prints a fresh link with a new token (a link already used no longer works). `--foreground` keeps the old behavior: it serves in the terminal until Ctrl+C (run it as a background task then). Stop the page with `localrunner down` (it also ends when the hub stops) when the user is done; there is no `dashboard` role in `autostart`. Never expose it beyond loopback. Its History tab is paged (previous, next, page size, the position and the total); the queue says `shown N of M queued orders` when a broker's list limit left orders out, so a short queue on the page is not always the whole queue.
- `localrunner runner outbox drop [--runner NAME] <job-id>`: when a runner keeps delivering entries of a job the broker already cancelled or lost, closes its pending outbox entries on the running runner and prints `closed N entries of <job-id>`. Refused while the runner still runs that job; never edit `runner.db` by hand.
- `localrunner doctor [--elevate]`: checks of this node as a report with `ok`, `warn` and `fail` markers and a count line. Without `--elevate` it does not read the `policy.toml` of a broker installed as an OS service (the file needs administrator rights) and says so in one line. `--elevate` asks the user for the rights in the user's terminal (UAC or `sudo`); an agent session has no terminal, so do not pass it on your own and tell the user to run it.
- `localrunner runner list` and `localrunner client list`: the runners and the clients known to the broker. When the OS refuses the admin channel of a broker installed as an OS service, the command asks the user for administrator rights in the user's terminal; without a terminal or with `--no-elevate` it prints the error and the way, give it to the user.
- If nothing answers, run `localrunner doctor`.
