description: >-
  Use whenever a heavy task (tests, builds, lint, deploy, migration) must run on a machine shared by
  parallel sessions: submit it to the queue instead of starting it directly. Triggers: "run tests via runner", "прогони через
  раннер", and any test-run step of a consumer project that declares profiles.

# run

Inputs: the sender label (`--as`), an optional note, the profile, an optional lower timeout.

1. Pick the profile from the consumer `.localrunner/profiles.toml`; with a single profile the name may be omitted. Never invent a profile; the fields of a profile are listed in README.md, section "Project profiles". Requirements (memory, CPU, programs, tags) come from the profile; `--mem <size>` (`6144`, `512m`, `6g`) and `--cpu <cores>` replace memory and CPU for this run only. When the profile declares arguments (`[profile.X.args.name]`), fill them with `--arg name=value` (repeat the flag for a `many` argument) instead of asking for one more profile per test target; the resources do not change with the arguments, so raise `--mem`/`--cpu` yourself for a heavier run.
2. Make sure the roles are up (`status-runner`); if not, `up-runner`. Before submitting several jobs, read the pool view (`localrunner runners`): runners of one pool share one memory, CPU and exclusive-tag budget, so an idle runner may be unable to start a job while the pool is full; prefer one submission (one profile with `steps`) when the pool budget is shared. Compare the `mem_mb` and `cpu` of your profile with the pool header: `can start a job now: yes` only says the runner is free and the pool has 1 CPU and 1 MB left, and reserve or quota rules, foreign load and orders already queued can still hold your order; after submitting, use `localrunner explain <job-id>`. If `up` reports that an upgrade runs, do not repeat it and do not start runners another way: wait, your order stays queued and runs after the upgrade.
3. Submit from the working directory to test (a worktree is fine): `localrunner submit [profile] --as <label> [--note ...] [--timeout s]`, or `localrunner run ...`, which is `submit --wait` and returns the job's exit code. `submit` detaches by default: the order outlives the sending process (a shell call of an agent session ends right after `submit` returns the job id), so no flag is needed; it prints only the job id to stdout and a hint block to stderr (`queued`, `follow`, `result`, `cancel` with ready-to-copy commands for this order; `--quiet` and `--json` suppress it). `--no-detach` restores the old behavior, where the order is cancelled when the sending process exits; `submit --wait` and `run` keep it, the order lives as long as the sender. `--as` is required: use `<agent>:<short session name>` (for example `claude:fix-609`) and keep it for the whole session; never submit under another session label. `--timeout` (seconds) only lowers the profile timeout. `--platform <name>` resolves the profile for one other platform. `--zones <list>` (or `--max-zone <zone>`) narrows the zones the order may run in; a code to fetch outside the machine is passed as an ordinary argument (`--arg branch=...`).
4. `submit` prints the job id, then wait as a background task with `localrunner wait <job-id>` or follow `localrunner log <job-id> -f`; write the output to `temp/runner/<job-id>.log`. Never read the whole log: bring into context the final state, the exit code and the failing lines (`log <job-id> --tail N`, `--step NAME`). Interrupting `wait` cancels nothing. Several jobs of one session: `localrunner wait <id1> <id2> ...` or `localrunner wait --as <label>` (the active jobs of the label, else its last job; also when the ids are lost) waits for all of them at once and prints one line per job (`<job-id> <profile> <state>`) with no log; the code is the first non-zero one. `wait` and `log` accept `--as <label>` like the other commands. Run a heavy task only through the queue (`submit`, then `wait`), never as a background command of your own: the runner does not see such a process, and when the system kills it for lack of memory there is no result and no message. Do not edit the sources while a job of the zone `local` runs: it works in your live directory.
5. A profile with `steps` is one job; the report lists each step. Job results: `passed`, `failed`, `timeout`, `cancelled`, `lost`. Name the first failed step; do not rerun the whole sequence to see a later one. A timeout or `lost` is a failure of the run, not of the tests: report it as such and do not retry in a loop. If a job waits, run `localrunner explain <job-id>`.
6. Know your own jobs: after a context loss list them with `localrunner jobs --mine --active --as <label>`. Never guess which job is yours from the profile name. Cancel early when the result no longer matters: `localrunner cancel <job-id> --as <label> --reason ...` or `cancel --mine --as <label> --yes` (`--mine` asks for confirmation, refused without a terminal: add `--yes` only when the user chose to cancel all).
7. Do not start the same command outside the queue while a job of your session is queued or running.
8. `cancel` without `--as` fails and names the label of the job when it is visible to you; use that label only if the job is yours. Do not cancel jobs of other labels, and never use `--force` unless the user asked for it.
