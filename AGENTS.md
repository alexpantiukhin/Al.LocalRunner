# Al.LocalRunner — a resource-aware job queue for a developer and AI agents

## Project overview
See `README.md` (English, the main one) and `README.ru.md` (Russian), and `docs/architecture.html` (Russian) with `docs/architecture.en.html` (English): the single design document in two languages (architecture, requirements, config formats, security) with a table of contents. Do not add design Markdown files; update the HTML instead. Keep each pair in sync: a change to one file of a pair is made in the other in the same commit. Each README starts with a language switch line.

## Rules
- Respond in Russian; write AGENTS.md and all AI instructions in English
- Everything on GitHub in this repository is in English: issues, pull requests (titles, descriptions, comments, reviews), commit messages, release notes, labels. Russian and other languages are allowed only in documentation (`README.<lang>.md`, `docs/`) and in instructions for people, and only as a translation in addition to the English original, never instead of it
- Do not add comments to code unless requested, except doc comments on public items
- Do not create files unless strictly necessary; read a file before modifying it
- No limit on file length; still decompose code by responsibility
- Save temporary files to `temp/` (gitignored)
- Run heavy tasks (build, `cargo test`, clippy, the full gate) through `localrunner` using the profiles in `.localrunner/profiles.toml` (`localrunner run rust-unit --as <label>`, `localrunner run rust-gate --as <label>`), not directly, so parallel sessions share the machine. Use the `localrunner:run` skill. There is no direct-run exception: even one test builds the crate and its dependencies on all cores, and a worktree has its own `target`. The first profile run in a new worktree builds every dependency from scratch and takes longer (more than five minutes for `skills-lint`); it is not a hang: submit it detached and wait. The rule covers every `cargo build`, `check`, `test`, `clippy` and `doc`, in the main checkout and in worktrees, and it binds subagents too: put it in their prompt, they do not read this file. For a narrower run (one crate, one test) add a profile or a profile argument to `.localrunner/profiles.toml` instead of calling `cargo` by hand. Seeing yourself type `cargo` for any of these is the signal to stop and use `localrunner run`.
- Never read, print or copy files under `secrets/`
- No agent attribution (`Co-Authored-By`, "Generated with") in commits and pull requests
- Plugins are installed at project scope only (`--scope project`)
- **Runner limits belong to the runner owner.** A refusal because an order does not fit any runner (`rejected_no_matching_runner`: timeout above the ceiling, memory, cores, tags) is the intended behavior, not a bug: the user of the runner fits into its limits (split the job, or ask the owner), and the runner or the profile is not changed to suit one machine. Do not file it as a defect
- **Generic core.** The daemon, queue and scheduler MUST NOT name or branch on a specific consumer, language, toolchain or test framework. All specificity comes from consumer-supplied profiles (`.localrunner/profiles.toml`)
- **Tests do not wait on real time.** Synchronize on an event the code produces (a reply, a queue or SSE event, a closed channel, a marker written after the action); check timers with a manual clock and `start_paused`; do not poll with `eventually` or `sleep` for a result. A timeout is only an upper bound against hangs. If the code has no such signal, add a test hook
- **A pull request is created only after the local twins of its CI jobs are green.** `.github/workflows/ci.yml` runs jobs by the changed paths, and each job has a profile in `.localrunner/profiles.toml` with the same command. On the final commit of the branch, run through `localrunner run <profile> --as <label>` every profile whose job the PR triggers, and create the pull request only when all of them passed: `rust-fmt`, `rust-clippy` and `rust-unit` for the job `rust` (`crates/`, `install/`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `deny.toml` or the workflow file changed; `rust-gate` is the same three steps in one job, for a runner whose limits allow it); `skills-lint` for the job `skills` (`plugin/` changed and the job `rust` does not run); `ci-docs` for the job `docs` (`README*.md`, `docs/`, `plugin/`, `AGENTS.md` or the workflow file changed); `ci-workflows` for the job `workflows` (`.github/workflows/` changed). If the runner's limits refuse or cancel `rust-unit`, run the same tests through `rust-test-all` (the whole workspace with `-j 2`, without the time budget, which CI still checks); if that is refused too, run them package by package through `rust-test` (every workspace member). Say which one you used in the PR description. A profile that was not run or was red blocks the pull request. When a CI job changes, change its profile in the same commit; the Python checks live in `.github/scripts/` and are called by both. The profiles run on the local OS only, so a red Linux or macOS job of an open PR is fixed on the PR
- **The plugin follows the behavior.** When a change alters what the user sees or does (a command, a flag, an output, a config key, a zone, a default, an error), bring `plugin/` (the skills and `plugin/shared/os/*.md`) in line with the new behavior in the same pull request, and check that every skill still matches the implementation before the pull request is created. A pull request that changes behavior and leaves a skill describing the old one is not ready
- When a path or a directory name used by `install.ps1` / `install.sh` changes, update `plugin/shared/os/*.md` and the `install-runner` skill in the same commit
- Diagrams in Markdown files use Mermaid
