Al.LocalRunner — архитектура и проектирование

Очередь тяжёлых задач с учётом ресурсов для разработчика и его AI-агентов, на одной машине или на нескольких. Это единственный документ проектирования: архитектура, требования, формат конфигурации и безопасность. Отдельных Markdown-описаний нет; план реализации — docs/superpowers/plans/2026-11-09-localrunner.md. Слева — содержание.

Глоссарий

Все термины определены здесь один раз. Подчёркнутое точками слово в тексте и на схемах показывает определение из этого раздела при наведении мыши или фокусе с клавиатуры; отдельной копии текста определений нет.

Узлы и роли

Компьютер
Физическая машина. На ней может стоять несколько установок: те, что работают одновременно (основная ОС, Docker, виртуалки), образуют один пул, а взаимоисключающие (двойная загрузка) — разные пулы.
Установка
Один экземпляр программы со своим каталогом состояния, MachineId и ключами: основная ОС, контейнер Docker или виртуалка. Один компьютер может нести несколько установок.
MachineId
Случайный идентификатор установки. Создаётся один раз при первой инициализации установки и хранится в файле machine-id. Служит для учёта и истории. Зону local определяет локальный IPC, а не равенство заявленных идентификаторов; брокер при вступлении по сети отклоняет MachineId, совпадающий с его собственным.
Hub (хаб)
Роль клиентской стороны: превращает профили проекта в заказы, отправляет их брокерам, ведёт outbox заказов, копию логов и дашборд и следит за процессом-отправителем. Джобы не исполняет и очереди ресурсов не держит. Стоит на машине пользователя; у каждой клиентской машины свой hub.
Брокер пула
Роль, один на пул: показывает, какие раннеры с какими характеристиками есть в пуле, принимает заказы, держит их очередь и раздаёт раннерам по политике. Отдаёт API: приём заказов и чтение состояния. Хранит историю запусков на своих раннерах и для каждого запуска записывает, с какого клиента он пришёл. В коде про hub ничего не знает: клиент для него — любое аутентифицированное соединение.
Заказ
Просьба выполнить джобу: требования к раннеру (платформа, ресурсы, программы, теги), коммит и команды, желаемый приоритет. Приоритет в заказе — только пожелание, порядок решает политика. Принадлежит ключу клиента, а не соединению: короткий обрыв связи (сон ноутбука, смена сети) его не отменяет. Ждущий заказ отменяется, только если hub не появлялся дольше срока политики (по умолчанию 6 часов).
Политика
Правила владельца в policy.toml на брокере: порядок выдачи, веса и квоты групп, резерв ресурсов, допуск клиентов, выбор раннера, окна ожидания, хранение. Код содержит только механизм и встроенные стратегии; неизвестное правило — отказ при загрузке, ошибка перезагрузки оставляет прежнюю политику.
Раннер
Роль и отдельный процесс: подключается к брокеру, исполняет выданные им джобы и возвращает результаты и логи. На одной установке может работать несколько раннеров, например light и heavy.
Клиент
Клиентская машина: на ней стоят только hub и сессии агентов, джобы она не исполняет. Для брокера её соединение — обычный клиент с ярлыком, который владелец задал при выдаче ключа.
Демон
Фоновый процесс localrunner, который держит одну роль: hub, брокер или раннер. Запускается командой up; брокер можно поставить службой ОС (раздел 3.12).
ci-раннер
Настоящий self-hosted раннер GitHub Actions с меткой al-ci. Сам ресурсов у брокера не берёт: джоба GitHub вызывает localrunner run через hub своей машины, и заказ идёт в общую очередь брокера как любой другой, под ярлыком ci. Не путать с нашим раннером.
Дашборд
Страница в браузере: очередь, история, живой лог, статистика, раннеры. Запускается по требованию и слушает только loopback (127.0.0.1 и ::1) своей машины. Раннеры, нагрузку и очередь берёт из API брокеров, историю запусков — тоже из API брокеров.

Очередь и ресурсы

Джоб
Один запуск профиля: очередь, шаги, результат. Имеет JobId. Джоба идёт на одну платформу; вторая платформа — вторая джоба.
Профиль
Описание запуска в .localrunner/profiles.toml проекта: команда или шаги, таймаут и требования к раннеру (память, CPU, диск, программы, платформы, теги). Это требования джобы, а не настройки машины.
Требования заказа
Что нужно джобе от раннера: платформа, память, CPU, диск, программы, теги, потолок таймаута, зона. Заказ перечисляет их сам; уровней-меток нет. Hub и брокер подбирают раннер, у которого есть всё требуемое, иначе возвращают ошибку с цифрами.
Ярлык клиента
Метка группы, которую владелец брокера задаёт ключу клиента при выдаче. Входит в запись ключа, поэтому клиент подделать её не может; по ярлыку политика считает права, квоты, веса и приоритет. Не путать с меткой --as, которую выставляет сам вызывающий.
ci
Ярлык клиента для джоб GitHub Actions: его владелец задаёт ключу hub на машине с GitHub-раннером. Политика по умолчанию даёт ему наивысший приоритет (100): такие заказы берутся первыми, но уже работающие джобы не вытесняются.
Приоритет
Порядок выдачи решает политика брокера по атрибутам: ярлык клиента из записи ключа и заявленные заказом (источник, теги, размер), а не код. Заявленные атрибуты сами приоритет не повышают. Политика по умолчанию: строгий приоритет (джобы GitHub Actions с ярлыком ci идут первыми), внутри приоритета порядок постановки, джоба старше 30 минут поднимается до высшего приоритета.
Пул
Набор установок, которые работают одновременно и делят общий бюджет: лимиты памяти и CPU и набор exclusive-тегов. Лимиты задаёт владелец в политике брокера, а не проект; брокер у пула один. На одном компьютере может быть несколько пулов, если они взаимоисключающие (двойная загрузка): у каждого лимиты всего компьютера.
Платформа
Непрозрачная метка владельца (macos, ios, android...). Ядро только сравнивает метки на равенство. Джоба идёт на одну платформу; вторая платформа — вторая джоба.
Тег
Ресурс, который джоба удерживает на время прогона (gradle, emulator). Теги раннера означают заявленные им возможности.
exclusive
Тег, который одновременно не может держать никто другой. Действует внутри пула.
Зона
Расстояние от отправителя до раннера: local, lan или remote. Среди подходящих раннеров по умолчанию предпочитается ближайший (это правило политики), но занятый ближайший не блокирует свободный дальний.
Отправитель
Процесс, вызвавший CLI (родитель localrunner), вместе с меткой --as и MachineId. По нему определяется право отмены и правило мёртвого отправителя.
Головной заказ
Заказ, который стоит первым в очереди по порядку политики. Если он не помещается в свободные ресурсы, следующие заказы могут обойти его, только если не задержат его старт (заполнение дыр с предсказанием, раздел 6).
Ручка
Файл temp/runner/<job-id>.json в каталоге отправителя: метка, идентификатор, профиль и время запуска. По ней агент после потери контекста находит свои джобы.
Reaper
Часть hub, которая следит за процессом-отправителем и при его гибели отменяет заказы у брокера.
Мёртвый отправитель
Когда процесс-отправитель завершился, его ожидающие джобы снимаются, а выполняющиеся убиваются. Флаг --detach отключает правило для заказа целиком: ждущий и выполняющийся заказ переживают отправителя.

Связь

Код подключения
Одноразовый код (по умолчанию живёт 1 час, срок задаёт политика), который выдаёт брокер, чтобы раннер или hub вступил. После вступления машина использует собственную пару ключей.
network
Имя сети из списка [networks] в конфигурации брокера, по нему считается зона lan. Брокер определяет его по адресу каждого подключения; адрес вне списка — зона remote. Клиент и раннер метку не хранят и не объявляют.
Heartbeat
Сигнал живости раннера каждые 15 секунд. После трёх пропусков раннер считается offline.
Outbox
Постоянная очередь исходящих сообщений на hub, брокере и раннере: заказы, отмены, вывод и результаты записываются на диск до подтверждения получателем и повторяются после обрыва; получатель отбрасывает дубликаты по идентификатору и номеру seq.
Получатель (sink)
Место, куда уходят события логирования и метрики: файл на диске (по умолчанию), консоль, журнал ОС или OTLP-приёмник вроде Grafana Alloy. Задаётся в logging.toml; сетевой получатель выключен, пока владелец его не включил.
Кэш раннера
Именованные каталоги, которые раннер хранит между запусками проекта и отдаёт джобе путём в переменной окружения. Размер и срок хранения задаёт владелец раннера в runner.toml; когда места не хватает, удаляются самые давно использованные. Ядро не знает, что в них лежит.
Сервис раннера
Программа, которую раннер по правилам владельца поднимает и гасит для джоб (демон сборки, эмулятор). Когда и для кого — решает политика, а гарантии (ограниченная жизнь, учёт ресурсов, полная уборка, проверка готовности, изоляция) зашиты в код. Ядро не знает, что внутри.
IPC
Локальный канал между CLI, hub, брокером и раннером на одной установке: именованный канал в Windows, Unix-сокет в других ОС. Доступ только у пользователя ОС.
TLS
Шифрованное соединение раннера или hub с брокером по сети. Сертификат брокера закреплён отпечатком, который входит в код подключения.

1. Цели и принципы

  • Цели. Параллельные сессии агентов ставят запуски в очередь, а не перегружают машину. У каждого запуска обязательный таймаут; по истечении или отмене убивается всё дерево процессов. Ядро универсальное, потребитель поставляет профили.
  • Универсальное ядро. Очередь, планировщик и роли не знают про язык, тестовый фреймворк и платформы. Названия платформ, метки и команды приходят от владельца машины и из профилей проекта.
  • Роли разделены. Hub — клиент: превращает профили в заказы, ведёт outbox заказов и дашборд, джобы не исполняет и очереди ресурсов не держит. Брокер пула знает свои раннеры, заказы и историю запусков на них; о hub он ничего не знает в коде (логика не различает потребителей), а в данных записывает, с какого клиента пришёл каждый запуск. Раннер исполняет и не решает, что запускать. Интерфейсов два: протокол раннера (раннер ↔ брокер) и API брокера (заказы и чтение; hub ↔ брокер).
  • Роли зависят от абстракций. Хранилище, сеть, процессы, время, секреты и получатели логов роли получают через трейты из lr-abstractions; реализации подключает только точка сборки lr-cli, поэтому логика проверяется на заглушках (раздел 13).
  • Решает политика. Порядок выдачи, квоты, допуск, выбор раннера, окна ожидания и хранение — правила владельца в policy.toml на брокере (и в hub-policy.toml у hub для выбора брокера). В коде только механизм и проверки безопасности (протокол, ключи, изоляция процессов).
  • Один бинарник, три роли. localrunner работает как hub (профили, outbox заказов, дашборд), брокер (раннеры, очередь заказов, история запусков, политика) и раннер (выполняет джобы). На одной машине up запускает все три отдельными процессами. Одна машина с этим набором — вариант по умолчанию, остальное включается по желанию.
  • Раннер сам подключается к брокеру, как у GitHub self-hosted: входящие порты на раннере не нужны.
  • Ресурсы считаются по пулу — набору установок, которые работают одновременно и делят бюджет, а не по раннеру. Docker и виртуалки остаются отдельными установками со своим ID, но входят в пул хоста; у пула один брокер. Взаимоисключающие установки (двойная загрузка) — разные пулы на одном компьютере.
  • Hub и брокеры — «многие ко многим». У каждого hub свой список брокеров, брокер не знает, сколько hub его используют.
  • Рабочее дерево — раннеру той же машины, коммит — удалённому.
  • Дашборд — дополнение, а не единственный способ. Всё, что видно на странице, можно получить командой CLI в тексте и в --json; действий, которых нет в CLI, на странице нет. Агенты и скрипты работают только через CLI.
  • Тесты не ждут реального времени. Тест синхронизируется по событию, которое производит сам код (ответ, событие очереди или SSE, закрытый канал, маркер, записанный после действия), проверяет таймеры ручными часами и start_paused и не опрашивает результат через eventually или sleep. Тайм-аут — только верхняя граница против зависания. Если у кода нет такого сигнала, добавляется точка наблюдения для теста, а не ожидание.
  • Ничего не уходит наружу. Дашборд слушает только loopback; телеметрии и загрузок нет. Единственное исключение — сетевой получатель логов и метрик (OTLP), который владелец включает сам и явно.

2. Архитектура: машины и связи

Раннеры могут стоять в этой же сети, в другой сети или на VPS: нужен только адрес брокера, который владелец вводит вручную. NAT-обхода и туннелей нет.

Синие линии — постоянные соединения с брокером: заказы идут вниз, состояние и результаты вверх (по IPC на своей машине, по сети через общую шину TLS). Серые — IPC и HTTP на loopback между сессиями, браузером и hub. Пунктирные рамки — компьютеры; рамка внутри — установка со своим ID. Точечные синие рамки — пулы: у каждого пула один брокер, установки внутри рамки делят ресурсы, два пула на одном компьютере взаимоисключающие. Зелёные — раннеры. Брокер не знает о hub в коде: для него hub — клиентское соединение, но в историю он записывает, с какого клиента пришёл запуск; у каждого hub свой список брокеров, который ему выдал владелец: разные hub могут знать разных брокеров или одних и тех же (на схеме у hub компьютера 1 нет mac-mini, у ноутбука есть все три). Какому из известных брокеров отправить заказ, hub решает по своей политике (платформа, доступность).

Что где работает

  • Запуск джобов с любого компьютера. У каждой клиентской машины свой hub. Сессии агентов говорят с ним по IPC, а он отправляет заказы нужным брокерам. Очередь заказов живёт на брокере пула, порядок выдачи решает его политика.
  • Дашборд с любого компьютера. Дашборд слушает loopback своего hub и собирает вид сам: раннеры, нагрузку, очередь и историю запусков — из API брокеров; заказы, которые брокер ещё не принял, hub держит в своём outbox. Если брокер недоступен, на дашборде видно, что его данные устарели.
  • Переключение между Windows и Mac. У каждой клиентской машины свой hub, а брокеры стоят на компьютерах пулов. Выключили ноутбук — пропали только его заказы; остальные клиенты и пул работают.
  • Несколько раннеров на одной ОС. На Windows и на Linux работают по два отдельных процесса, например раннеры с именами light и heavy (имена ничего не значат для ядра). У каждого своё имя, правила допуска и регистрация на брокере; раннер выполняет одну джобу за раз, параллельность дают несколько раннеров; пул общий, память и CPU считаются вместе.
  • Один компьютер — несколько установок. Windows, Docker и виртуалка на компьютере 1 — три установки с тремя ID, один пул и один брокер.
  • Разные ОС. Платформа раннера — метка владельца (windows, linux, macos, ios, android); ядро сравнивает метки на равенство.

Ключевые решения

  • Hub ставит пользователь на каждую клиентскую машину. Брокеры стоят на компьютерах пулов; hub видит брокеры, ключи к которым получил. На одной машине up запускает hub, брокер и раннер.
  • Hub и брокеры связаны «многие ко многим»: у каждого hub свой список брокеров (ключ и адрес на каждого), и брокер не знает, сколько hub его используют. Общий пул делят все hub, знающие его брокера; бюджет считает один брокер, поэтому раннер не перегружается, как бы много hub ни слали заказы.
  • Брокер выдаёт заказ подходящему раннеру: по платформе, программам, ресурсам, меткам и потолку таймаута; среди подходящих по умолчанию ближайшему по зоне (local, lan, remote). Всё это правила политики.
  • Приоритет решает политика. По умолчанию ci идёт первым без вытеснения запущенных, а заказ без ci, ждущий больше 30 минут, упорядочивается как ci.
  • Заказ принадлежит ключу hub, а не соединению: после обрыва он остаётся. Брокер отменяет ждущие заказы, только если hub не появлялся дольше absent_after_min (по умолчанию 6 часов, политика); уже запущенная джоба доживает, а результат ждёт возвращения hub.
  • Если брокер пропал на 3 минуты, раннер убивает свои запущенные джобы; результаты завершённых хранит и отдаёт позже. Срок и действие — политика.

3. Роли и взаимодействие

Три роли — hub, брокер пула, раннер — и два интерфейса между ними. Всё, что можно решить политикой, решается политикой.

3.1 Hub

  • Живёт на клиентской машине, по одному на пользователя ОС (у каждого пользователя свой каталог состояния). Принимает команды CLI по IPC, читает профиль, превращает его в заказ и отправляет брокеру. Хранит outbox: исходящие заказы и отмены записываются на диск до подтверждения брокером и повторяются после обрыва; пока запуск активен, помнит его процесс-отправитель. Ведёт копию логов в каталоге отправителя, дашборд, проверку отправителя и право отмены.
  • Не исполняет джобы, не держит очередь ресурсов, не хранит реестр раннеров и не выдаёт им заказы. Сводку раннеров, нагрузку, очередь и историю он читает из API брокеров.
  • Выбор брокера. Зону каждого брокера относительно себя hub узнаёт у самого брокера: в ответ на подключение брокер сообщает, какой сетью считает адрес hub (ноутбук переехал из дома в офис или в мобильную сеть — зона пересчитана при следующем подключении). Hub ничего не вводит и не хранит, кроме последней известной зоны. Зоны: local (брокер на той же машине: связь с ним идёт по локальному IPC, а не по сети), lan (адрес hub и адрес брокера входят в одну сеть из [networks]) или remote. Для каждого заказа hub действует так:
    1. Оставляет только брокеров, чья зона допустима заказу. Заказ с требованием «та же машина» (рабочее дерево) рассматривает только local и никогда не уходит в сеть: шаг 3 к нему не применяется, политикой это не отключается. Если локального брокера нет в списке hub или пользователя нет в [[local_user]], заказ отклоняется с причиной; если брокер временно недоступен, заказ ждёт в outbox, а не переезжает на другую машину и не подменяется коммитом; заказ с ограничением zone = "lan" — local и lan и никогда не уходит на remote. Граница заказа — жёсткий инвариант, а не предпочтение: переход к следующей зоне (шаг 3) разрешён только внутри допустимых зон, и политикой границу расширить нельзя. Брокеров недопустимых зон он не опрашивает вовсе.
    2. Опрашивает брокеров первой зоны по порядку (параллельно, с коротким таймаутом из hub-policy.toml): раннеры, платформы, программы, ресурсы, теги, потолки таймаута, online/offline. Данные не кэшируются, решение принимается по свежим сведениям. Локальный брокер (по IPC) входит в список hub автоматически под именем local, если он на этой машине настроен: роль broker записана init, есть его broker.db или установлена служба брокера. Hub, запущенный раньше первого старта брокера, увидит его после перезапуска (up, поднимая обе роли, запускает hub только после того, как брокер ответил; если брокер не ответил за срок запуска, up сообщает об этом, завершается с кодом 1 и hub не запускает); на машине без брокера local в списке нет. Если допустимых брокеров нет вовсе (зона заказа никого не допускает), заказ отклоняется с причиной, а не ждёт в outbox. Адрес брокера у hub один: из другой сети он должен быть достижим по тому же адресу (публичное имя, VPN).
    3. Если среди них есть подходящие (раннер на связи и удовлетворяет требованиям; занятость не исключает: заказ встанет в очередь брокера), выбирает по политике и дальше не ходит. Если нет, переходит к следующей допустимой зоне. Порядок зон задаёт hub-policy.toml (broker_zone_order): по умолчанию от ближней к дальней (["local", "lan", "remote"]), но можно и обратный (["remote", "lan", "local"], например чтобы разгрузить свою машину), или любой другой. Политика может также потребовать опрашивать все допустимые зоны сразу. Порядок меняет только очерёдность внутри допустимых зон; границу заказа он не расширяет.
    Брокер, не ответивший за таймаут, на этот выбор считается недоступным, но отказа он не даёт: если кто-то из допустимых брокеров недоступен, а остальные ответили «нет подходящего», hub повторяет опрос (общее число попыток query_attempts, включая первую, и пауза query_retry_s в hub-policy.toml), и заказ ждёт с причиной «брокер X недоступен». Недоступный брокер зоны на шаг перехода к следующей зоне считается «нет подходящего», а повтор опроса затрагивает весь выбор целиком. Если попытки исчерпаны, а недоступный брокер так и не ответил, заказ отклоняется с причиной, где недоступные брокеры названы поимённо; отказ с цифрами о несоответствии даётся только когда ответили все допустимые брокеры. Данные могут устареть между запросом и приёмом заказа, поэтому окончательно допустимость проверяет брокер, в том числе границу зоны (раннер за пределами допустимой зоны относительно клиента он заказу не выдаст): если он отклонил заказ, hub пробует следующего по политике. То же после приёма: если брокер возвращает ещё не стартовавший заказ с причиной (например, «раннер установки пропал», раннер удалён командой runner remove), hub снова проходит выбор брокера по шагам выше, исключая вернувший брокер, и сразу ставит заказ на замену, не дожидаясь пользователя; граница зоны при этом прежняя. Для заказа «та же машина» замены нет (он не уходит с машины), поэтому он завершается отказом с причиной. Если не ответил ни один допустимый брокер, заказ ждёт в outbox с причиной «брокеры недоступны», и выбор повторяется при появлении связи. (Решение пользователя.)
  • У hub свой список брокеров: адрес и ключ на каждого, выданные владельцем при вступлении. Разные hub могут знать разных брокеров или одних и тех же. Если подходят несколько брокеров, выбор делает политика hub: файл hub-policy.toml в каталоге состояния (список и порядок брокеров, стратегия выбора). По умолчанию «первый в списке, остальные запасные». (Решение пользователя.)
  • Outbox. Отмена заказа, который ещё лежит в outbox без Accepted, снимает запись локально и всё равно уходит брокеру отметкой «отменён»: если заказ успел дойти раньше, брокер отбросит его при приёме. Заказ и отмена сначала записываются в постоянную очередь hub и доставляются брокеру с повтором, пока не придёт подтверждение; брокер отбрасывает повтор той же пары «ключ клиента + JobId» (идентификатор присваивает hub) и отвечает Accepted только после фиксации заказа в broker.db; по Accepted hub удаляет запись из outbox. Результат и вывод идут отдельным потоком брокер → hub со своим подтверждением (seq). Так заказ переживает недоступность брокера и перезапуск hub и не выполняется дважды. Срок ожидания в outbox — оба условия сразу, срабатывает более раннее: заказ ждёт, пока жив процесс-отправитель (если не --detach), и не дольше [outbox] ttl_hours (по умолчанию 24); по истечении on_expire решает: fail — заказ отклоняется с причиной «брокер не появился за срок», keep — ждёт дальше. Смерть отправителя снимает и заказ без Accepted (reaper, 7.3).
  • Возвращение после обрыва. Заказ принадлежит ключу hub, а не TCP-соединению. После переподключения (сон, смена сети, перезапуск hub) hub сверяет свои активные заказы с брокером: что идёт, что завершилось, что отменено за время отсутствия. Если брокер отменил заказы по сроку отсутствия, hub показывает их как cancelled с причиной и сам не ставит их заново. При запуске hub проверяет и процессы-отправители: заказы мёртвых отправителей отменяются по правилу из раздела 7.
  • Ресурсы на один запуск. Флаги --mem и --cpu у submit и run (рядом с --timeout) заменяют память и CPU профиля для этого заказа, вверх или вниз: hub подставляет их в требования заказа вместо значений профиля (и вместо максимума по шагам) и помечает в заказе как переопределённые. Без флага действует значение профиля. Значения выбирает пользователь, подбора по истории запусков нет. Ноль — ошибка флага (error malformed). Потолок проверяет брокер при приёме: значение флага больше пула ([pool]) — отказ rejected_override_above_pool с цифрами («--mem 20000 МБ больше пула: максимум в пуле 16384 МБ»); если пул превышает значение самого профиля, остаётся rejected_pool_memory или rejected_pool_cpu. Раннер с меньшей памятью или CPU, чем задано флагом, заказу не подходит, как и при значениях профиля (rejected_no_matching_runner с цифрами). Если оба флага больше пула, отказ называет оба. Правила политики видят переопределённое значение: условие min_mem_mb, резервы и квоты сравниваются с ним, и их отказы идут своими кодами (rejected_reserved, rejected_quota). Шаги заказа (steps) хранят mem_mb и cpu из профиля как справочные: бюджет пула считается только по требованиям заказа. (Решение пользователя.)

3.2 Брокер пула

  • Один на пул. Знает только раннеры своего пула: имя, платформы, программы, теги, ресурсы, нагрузку, состояние. Принимает заказы, держит очередь заказов, выдаёт их раннерам по политике и следит за бюджетом пула. Хранит outbox для каждого клиента: чанки вывода, результаты, подтверждения отмен — до подтверждения получателем. Хранит историю запусков на своих раннерах: запись на джобу и шаг, полные логи, и для каждого запуска — клиент (ключ, MachineId, ярлык). (Решение пользователя.)
  • В коде про hub не знает: логика не различает потребителей, не ветвится по ним и не требует от клиента ничего, кроме ключа. В данных клиент записывается как поле. Клиент для него — аутентифицированное соединение с ключом и ярлыком, который владелец задал при выдаче ключа. Ярлык и MachineId брокер берёт из записи ключа, а не из заказа, поэтому подписаться чужой машиной или чужим ярлыком нельзя.
  • Отдаёт API двух видов: приём заказов (создать, отменить, получать вывод и результат) и чтение состояния и истории (раннеры с характеристиками, нагрузка пула, очередь, выполняющиеся заказы, история запусков, логи, статистика). Видимость чужих заказов задаёт политика ([visibility] others_orders): none — чужие заказы не видны, только занятость пула; summary (по умолчанию) — идентификатор, состояние, платформа, раннер, времена и ярлык клиента, а проект, ветка, каталог, команда, заметка, метка --as, пользователь ОС, хост и лог скрыты; full — все поля заказа, но не вывод джобы: полный лог отдаётся только клиенту-владельцу запуска при любом уровне. «Владелец брокера» — пользователь ОС с правами на каталог состояния брокера (администратор машины или владелец службы, 3.9); он видит всё, включая логи, и только он вправе отменять чужие заказы при [cancel] others = "owner". Остальные локальные пользователи из [[local_user]] видят и отменяют своё. (Решение пользователя.)
  • По умолчанию на одной машине up запускает hub, брокер и раннер отдельными процессами одного бинарника, связанными по локальному каналу.
  • Один брокер на пул; пул, обслуживаемый одним брокером, — единица бюджета. Брокер остановился — пул простаивает; заказы без Accepted ждут в outbox hub в состоянии «брокер недоступен», принятые хранятся на брокере и продолжаются после его возвращения; раннеры доживают текущие джобы и отдают результаты после переподключения.

3.3 Раннер

  • Отдельный процесс. Подключается к брокеру сам (входящих портов нет), регистрируется, исполняет выданные джобы, стримит вывод и возвращает результат. Что запускать, он не решает.
  • Настройки владельца раннера: потолок таймаута джобы, размер и хранение кэша и рабочих копий (раздел 3.10).
  • Возможности раннера: platforms (непрозрачные метки владельца), programs (какие программы найдены и проверены), свободный диск, tags, имя (уникально на брокере). Необязательное правило допуска [accept] резервирует раннер под нужные заказы (раздел 4).
  • На одной установке может работать несколько раннеров (например, light и heavy); у каждого своё имя, правила допуска, платформы и теги; каждый выполняет одну джобу за раз. Они делят пул установки.
  • Если брокер недоступен дольше льготного срока (по умолчанию 3 минуты, политика), раннер убивает свои запущенные джобы; результаты завершённых хранит и отдаёт после переподключения.
  • Раннер принимает джобы только от брокера, к которому вступил, и выполняет команды из выданного заказа.

3.4 Заказ

Заказ — данные, не код: идентификатор JobId от hub, описательные поля (проект, ветка, каталог, метка, заметка, источник), которые брокер записывает в историю запуска вместе с клиентом, требования к раннеру (платформа или «та же машина, что у клиента», программы, теги, память, CPU, диск, exclusive, самая дальняя зона), источник кода (рабочее дерево или коммит), команды и шаги с таймаутами, желаемый приоритет. Приоритет в заказе — только пожелание, порядок решает политика.

  • Рабочее дерево. Джоба, которой нужны локальные файлы, несёт требование «выполнить на той же машине». Брокер считает раннер «той же машиной», только если клиент и раннер подключены к нему по локальному IPC от одного и того же пользователя ОС (пользователя проверяет ядро ОС); заявленные при вступлении MachineId этого не заменяют. Поэтому рабочее дерево доступно только раннеру того же пользователя на машине, где стоит брокер. Ждать имеет смысл, только пока есть живой раннер установки: если подходящий раннер на связи, но занят, заказ ждёт, и причина это называет («раннер занят»). Если раннеров установки нет или все они offline (выключены), заказ сразу отклоняется при приёме; то же, если раннер пропал уже после Accepted, пока заказ не стартовал: брокер возвращает его с причиной, и hub завершает его отказом с подсказкой («нет раннера на вашей установке, запустите его: up»): ждать нечего, а агент не повиснет. Если раннеры на связи, но ни один не подходит по характеристикам, отказ идёт с цифрами. Подмены коммитом нет. (Решение пользователя.)
  • Коммит. Джоба на раннере другой установки проверяет запушенный коммит (подробнее в 3.7).
  • Кто выбирает источник кода. Источник — поле заказа, его до маршрутизации выбирает hub: заказ без платформы — рабочее дерево, заказ с платформой — запушенный коммит, даже если его исполнит раннер той же машины. Что коммит запушен, проверяет hub; CLI только собирает данные. У заказа на рабочее дерево нет снимка: джоба читает живой каталог клиента, поэтому правки во время прогона попадают в неё; от них изолирует только заказ на коммит.

3.5 Политики

Принцип: ядро содержит механизм, решение принимает политика, которую пишет владелец. Своего кода и скриптов политика не содержит: это декларативные правила и именованные встроенные стратегии.

Семантика ключей определена в подразделе «Семантика политики» ниже; перечень стратегий закрытый. Фиксированные правила остаются в коде.

  • Что остаётся в коде и политикой не задаётся: протокол и версии, аутентификация и проверка ключей, изоляция процессов и kill дерева, целостность хранилища. Политика выбирает, что разрешено, а не как работает проверка.
  • Правит политику только тот, кто сидит за машиной брокера. Файл правится локально, policy reload принимается только по локальному каналу; удалённо поменять нельзя, скомпрометированный hub ничего не изменит. Особый удалённый ключ владельца — возможное расширение. (Решение пользователя.)
  • Защита от самих политик. Каждое правило проверяется при загрузке; битый файл — отказ, прежняя политика остаётся. Неизвестное имя стратегии — отказ. Любая задержка или отказ называет сработавшее правило (например, «правило ci-reserve: 2 из 8 ядер зарезервированы»). Пустой файл не ломает систему: действуют значения по умолчанию.
  • Доверенные и заявленные атрибуты. Доверенные берутся из записи ключа (ключ, ярлык, MachineId); заявленные приходят в заказе (источник, проект, теги, размер, --as) и клиент может назвать их как угодно. Правила приоритета, резерва, квот и группировки по заявленным атрибутам допускаются только вместе с условием на доверенный ярлык; иначе файл отклоняется при загрузке. Время постановки заказа (от него считаются FIFO и старение) брокер назначает сам, по своим часам в момент приёма; время, присланное hub, не используется, поэтому клиент не может «состарить» заказ и обойти правила.
  • Перезагрузка без остановки: policy reload проверяет и применяет файл; предупреждения (например, перекрытое правило) выводятся, но не мешают применению, а изменения [listen] и [networks] применяются только при перезапуске службы, о чём команда сообщает. Новая политика действует для новых заказов и решений планировщика; уже принятые заказы не пересматриваются, выполняющиеся джобы не затрагиваются, а изменённый [grace] брокер рассылает подключённым раннерам. Вызов без прав на каталог состояния отклоняется.
  • Команды в заказе. По умолчанию клиенту с ключом доверяют (как self-hosted раннеру GitHub); для отдельных ключей политика может ограничить заказы названиями из списка раннера. (Решение пользователя.)

Семантика политики

  • Порядок правил. Правила [[rule]] проверяются сверху вниз. По каждому полю решения (priority, reserve, quota, weight) действует первое подошедшее правило, которое это поле задаёт; правила с разными полями дополняют друг друга. Поэтому ответ на вопрос «почему такой приоритет» одна строка: «правило номер N». При загрузке правило, которое никогда не сработает (его целиком перекрыло более раннее), выдаёт предупреждение.
  • priority — число, больше — раньше; без правила 0. reserve = { cpu, mem_mb } — доля ресурсов пула, которую получают только заказы, подошедшие под правило: остальные заказы её не занимают, даже когда она свободна. quota = { max_running, max_mem_mb } — потолок одновременно выполняющихся джоб и памяти для группы (по group_by). weight — вес группы для стратегии weighted.
  • Стратегии. priority-fifo: по убыванию приоритета, внутри приоритета по времени постановки. fair-share: внутри приоритета группы по очереди, первой идёт та, что дольше всех не получала ресурсы. weighted: как fair-share, но доля группы пропорциональна weight. Старение (age_after_min) действует поверх любой стратегии.
  • Условия when. Правило подходит, когда совпали все заданные поля; пустое или отсутствующее when подходит всем. Доверенные поля: client_key, client_label, machine_id (из записи ключа). Заявленные: source, project, submitter_label (метка --as), tag (заказ просит этот тег) и min_mem_mb (заказ просит не меньше стольких МБ). Правило с заявленным полем и любым из priority, reserve, quota, weight без client_label отклоняет файл. Имена правил уникальны; weight не меньше 1.
  • Значения по умолчанию. Без [[rule]] действует одно правило ci-first (client_label = "ci", priority = 100); rule = [] задаёт политику без правил. [queue]: priority-fifo, 30 минут; [clients] group_by = "label"; [join] code_ttl_min = 60; [orphans]: 360 минут, queued = "cancel", running = "finish"; [grace] lost_min = 3; [results] keep_hours = 72; [listen] и [networks] пусты (сеть не слушается, все адреса remote); [[local_user]] пишет установщик; [cancel] others = "owner"; [[secrets.allow]] пуст (секреты не разрешены никому); [pool]: без mem_mb и cpu — вся память и все ядра машины брокера, exclusive_tags пуст; [limits]: потолка таймаута нет, timeout_above_max = "reject", 256 МБ, 512 МБ, 100, 1200 запросов в минуту; [routing]: local, lan, remote; [history]: 30 дней и 2 ГБ логов, 365 дней строк; [saturation]: 15 минут, 90 %; [cache] share = "client"; [services] evict_idle = true, без [[services.allow]] сервисы может запрашивать любой ярлык, а со списком — только перечисленные (первое подошедшее); [visibility] others_orders = "summary"; [resources]: mode = "warn", mem_headroom и disk_headroom 1.25 (без таблицы раннер берёт те же значения: действуют warn, предел CPU и предел числа процессов; off нужно выбрать явно); [admission]: foreign_load = "off", mem_headroom_mb = 256 (3.14); [commands] default = "any". Неизвестная таблица или ключ — отказ с именем таблицы, ключа и номером строки.
  • policy check печатает предупреждения: правило, целиком перекрытое более ранними; правило без действий; условие min_mem_mb больше пула; резервы, занимающие весь пул; квота max_running = 0; слишком широкая сеть в [networks] (короче /16 для IPv4 и /48 для IPv6); разрешённые секреты ярлыку без [commands] mode = "named"; [cache] share = "project" и отдельно — вместе с клиентом [commands] mode = "named" (проект заявлен клиентом, и ограниченный клиент может подложить артефакт в общий кэш доверенных сборок); [visibility] others_orders = "full"; [limits] timeout_above_max = "trim" без max_job_timeout_s; [resources] mem_headroom или disk_headroom при mode = "off" (не действуют); [admission] mem_headroom_mb при foreign_load = "off", а также mem_headroom_mb не меньше памяти пула (при раннере, сообщающем нагрузку, ни один заказ не запустился бы).

3.6 Пулы и ресурсы

  • Пул — набор установок, которые работают одновременно и делят один бюджет: память, CPU и набор exclusive-тегов. Лимиты принадлежат владельцу машины и описаны в политике брокера, а не в проекте. Профили лишь говорят, что нужно джобе.
  • Раннеры одного пула делят лимиты и занятые теги. Windows-хост и раннер в Docker на нём — один пул, поэтому планировщик видит их нагрузку вместе. Совместное использование нельзя надёжно определить, его объявляет владелец.
  • Несколько пользователей на одном компьютере. Пул один, значит и брокер один. Он работает как служба ОС (3.12), поэтому не зависит от того, кто вошёл в систему: выход пользователя не останавливает пул. Hub и раннеры пользователей подключаются к службе по локальному IPC, список разрешённых пользователей и их ярлыки — [[local_user]] в policy.toml; подключаться по сети (127.0.0.1) можно как обычному клиенту. «Та же машина» требует, чтобы hub и раннер подключились по IPC от одного и того же пользователя ОС: у каждого пользователя рабочее дерево работает со своим раннером и недоступно чужому.
  • Раннер входит в пул того брокера, к которому вступил. Раннер, не делящий ресурсы ни с кем, — это пул из одного раннера со своим брокером.
  • Пул — это общий предел машины, пулы не вкладываются. Два пула на одном компьютере — два независимых бюджета: это правильно для взаимоисключающих установок (двойная загрузка), а для одновременно работающих владелец объявляет один пул.
  • Раннер выполняет одну джобу за раз; параллелизм — это число работающих раннеров, и он ограничен лимитами пула. Лимиты — статические числа от владельца; брокер ведёт учёт по заявленным числам. По умолчанию он не измеряет реальную нагрузку, поэтому посторонняя работа вне очереди не считается; владелец может включить допуск по реальной нагрузке машины раннера через [admission] foreign_load = "wait" (3.14).
  • ci-раннер — обычный клиент: его джобы ставят заказы через hub своей машины, и ресурсы пула считаются один раз, по заказу. Ярлык ci задаётся ключу hub этой машины, поэтому машину с GitHub-раннером владелец держит отдельно от сессий агентов, иначе их заказы получат тот же приоритет.

3.7 Маршрутизация и доставка кода

  • Заказ подходит раннеру, если совпали одна из запрошенных платформ, все теги, программы, диск, таймаут не больше потолка раннера и пул может выдать ресурсы. Без платформы заказ идёт раннеру той же установки, что и клиент: оба подключены к брокеру по локальному IPC от одного пользователя ОС (так «та же машина» определена везде).
  • Профиль может иметь несколько платформ и команду на каждую ([profile.X.platform.ios]). run --platform имя принимает ровно одну платформу и создаёт одну джобу; для второй платформы пользователь или агент запускает команду ещё раз (это вторая независимая джоба, группы запусков нет). Без --platform платформа берётся из профиля, а если и там их несколько, команда просит указать одну.
  • Выбор среди подходящих по умолчанию: раннер на машине клиента, затем в локальной сети, затем удалённые; среди равных по зоне — с наибольшей свободной ёмкостью. Это правило политики брокера (runner_zone_order), порядок можно обратить или задать любой; на границу заказа (3.1) он не влияет. Допустимость всегда первична: ближний неподходящий раннер не выбирается вместо дальнего подходящего. Предпочтение не резервирование: если ближний занят, а дальний свободен, заказ уходит на дальний сразу.
  • Зона — расстояние раннера от клиента: local (клиент и раннер подключены к брокеру по IPC от одного пользователя ОС; IPC другого пользователя той же машины считается адресом хоста брокера, то есть зоной той сети из [networks], где стоит хост, обычно lan), lan (адреса клиента и раннера входят в одну сеть из [networks]), remote (всё остальное, в том числе мобильная сеть и адрес вне списка). Адрес клиента — тот, с которого брокер видит подключение (адрес источника). Владелец один раз описывает сети в конфигурации брокера: [networks] home = ["192.168.1.0/24", "127.0.0.1/32", "172.17.0.0/16"]; хост брокера, его loopback и мост Docker относятся к той сети, в которой стоит хост. Брокер сообщает зону и hub, и раннерам относительно клиента, поэтому ограничение заказа проверяется по зоне раннера, а не только брокера. Проект может сузить зону полем zone. Приоритет заказов и предпочтение между раннерами независимы: первое упорядочивает очередь, второе выбирает раннер для головного заказа.
  • Заказ, которому по характеристикам не подходит ни один зарегистрированный раннер (для «той же машины» — ни один раннер этой установки), отклоняется при приёме с причиной; для «той же машины» то же происходит, если раннеров установки нет или все они offline; если все подходящие раннеры offline, заказ ждёт и показывает причину.
  • Доставка кода. Раннер другой установки проверяет запушенный коммит. Hub отказывает в удалённом заказе, если HEAD недоступен из удалённой ветки, и просит закоммитить и запушить (MR не нужен); незакоммиченные изменения (изменённые, добавленные в индекс и новые файлы, как их показывает git status) игнорируются с предупреждением, заказ они не блокируют: hub возвращает отправителю вместе с JobId (submit и run печатают его в stderr) и пишет в копию лога строку «warning: uncommitted changes are ignored: the runner checks out the pushed commit <коммит>». Раннер держит на каждый проект общее bare-зеркало, делает в нём git fetch и для каждой джобы создаёт отдельную рабочую копию (git worktree) с чистым отсоединённым checkout, поэтому джобы одного проекта не мешают друг другу; доступ к репозиторию — собственные учётные данные git на раннере, ядро их не хранит. Подготовка рабочей папки — не встроенная магия ядра, а обычная последовательность команд в заказе (шаг source, выполняется раньше шагов профиля). Для заказа «та же машина» это просто cd в рабочий каталог отправителя, ничего не клонируется. Для удалённого: cd в зеркало проекта на раннере (путь из [workspace]), git fetch и git worktree add на нужный коммит; если зеркала на раннере ещё нет, сначала mkdir и git clone --mirror <адрес>. Hub собирает эту последовательность по умолчанию для git; параметры — плейсхолдеры {repo_url} (из git remote get-url origin), {commit}, {branch} и {workspace}, последний подставляет сам раннер (зеркало лежит внутри его каталога состояния, поэтому раннеры не делят его и не гонятся за git fetch); рабочий каталог джобы выставляют сами шаги source, шаги профиля стартуют в нём; профиль вправе заменить её любыми своими командами (другое зеркало, sparse checkout, монорепозиторий). Учётные данные для этих команд остаются на раннере. Профиль для удалённого заказа читается из коммита (git show <commit>:...). Доставка через origin по умолчанию; упаковка коммита в файл через брокера — возможное расширение политикой. (Решение пользователя.)
  • Раннер принимает заказы любого проекта; ограничение — его собственные учётные данные git. Списка проектов нет.

3.8 Вступление в пул

Как у self-hosted раннеров GitHub: вступающий сам подключается к брокеру, входящий порт ему не нужен.

  • На брокере: localrunner broker add [--name имя-клиента] [--label ярлык] (имя клиента уникально на брокере, по нему работают client list и client remove; ярлык общий для группы клиентов) печатает адрес и одноразовый код (по умолчанию живёт 1 час, [join] code_ttl_min в политике) с отпечатком сертификата брокера: код — составной токен, отпечаток зашит в него, поэтому join принимает только адрес и код. Если у брокера несколько адресов в [listen], печатается первый, другой задаёт --address. Код не ключ: ключ создаётся при вступлении, срока не имеет и живёт до отзыва, поэтому раннер после вступления работает без дальнейших действий. Для нескольких раннеров broker add --runners N выдаёт код на N вступлений (каждое всё равно создаёт свой ключ). Команда работает через административный канал брокера: для брокера, установленного службой ОС, нужен администратор (Windows) или пользователь ОС брокера (Unix), а отказ в доступе сообщается вместе с этим действием. Поскольку join отказывается работать от администратора, код передаёт broker add --code-file файл: администратор записывает его в новый файл, обычный пользователь передаёт файл в join --code-file.
  • На новой машине: runner join <host:port> <код> [--name имя] [--count N] [--config файл] для раннеров (платформы, теги и программы берутся из runner.toml, флаги --platforms и --tags их переопределяют; имя раннера: --name побеждает name из runner.toml, без обоих берётся имя машины, а при --count N получаются имя-1 … имя-N) или hub join <host:port> <код> [--name имя-брокера] для hub (имя брокера в списке hub и в hub-policy.toml задаёт владелец hub; по умолчанию — адрес брокера). Вступающий (hub или каждый раннер отдельно, по своему коду) создаёт свою пару ключей, брокер хранит публичный ключ, код погашен. Счётчик кода (uses_left) уменьшается только после записи вступления в broker.db, поэтому оборванное вступление теряет лишь непогашенные части. Исчерпанные и просроченные коды удаляются при выдаче следующего кода. Дальше аутентификация по ключу; ключ раннера регистрирует только то имя, под которым вступил: hello с другим именем отклоняется (unauthorized), поэтому один ключ не множит себе раннеров и не забирает имя раннера в состоянии removed.
  • Адрес брокера владелец вводит вручную. Автообнаружения в сети (mDNS и подобного) нет: брокер ничего не объявляет и не слушает ради поиска, а подмену адреса исключают одноразовый код и отпечаток сертификата. (Решение пользователя.)
  • Канал — TLS с сертификатом брокера, закреплённым отпечатком из кода (самоподписанный, создаётся при первом запуске); посредник в сети не может ни вступить, ни подменить брокера.
  • runner list, client list, runner remove, client remove на брокере; удаление отзывает ключ сразу. Ключ принадлежит одному участнику, поэтому отзыв раннера не задевает hub и другие раннеры. При отзыве брокер разрывает соединения этого ключа, отменяет его ждущие заказы, действие над выполняющимися определяет политика ([orphans] running), а его outbox удаляет.
  • Локальный владелец. Подключение по локальному IPC ключа не требует: пользователя ОС брокеру сообщает ядро, а его запись берётся из списка [[local_user]] в policy.toml (по умолчанию в нём один пользователь — тот, кто поставил брокера; при установке через sudo или UAC берётся исходный пользователь, а не root или учётная запись администратора). У каждого пользователя из списка своя клиентская запись: ключ клиента — пара «локальный пользователь + пользователь ОС», ярлык берётся из списка. Поэтому ключ идемпотентности и право отмены у двух пользователей одной машины не пересекаются, а ярлык ci получает только тот, кому его назначил владелец. Пользователь вне списка отклоняется. Hub на машине брокера по коду вступать не нужно.
  • Брокер слушает сеть только на явных адресах из своей конфигурации (их может быть несколько, например LAN и мост Docker) и только пока выдан непогашенный код подключения или зарегистрирована хотя бы одна машина. Адресов по умолчанию нет, подстановочный адрес (0.0.0.0, ::) отвергается при старте; единственное исключение — address = "container" внутри контейнера (10.4). Дашборд всегда на loopback.
  • При вступлении по сети брокер отклоняет MachineId, совпадающий с MachineId самого брокера.
  • Раннер доверяет брокеру, к которому вступил; не направляйте раннер на брокер, который принимает заказы от тех, кому вы не доверяете.

3.9 Отказы и протокол

  • Протокол. Постоянное соединение с heartbeat каждые 15 секунд; раннер, пропустивший 3, считается offline. Сообщения: вступление (код, публичный ключ, возможности), опрос возможностей, заказ и ответ на него (Accepted или отказ), назначить, Started (раннер сообщает, что джоба стартовала; брокер ставит started_at по своим часам, поэтому расхождение часов не влияет на срок lost), отменить, чанк лога, результат шага и джобы, heartbeat, resume (после переподключения получатель сообщает последний принятый seq по каждому JobId, отправитель досылает остальное), drain и Bye (раннер или hub уходит штатно), запросы чтения для CLI и дашборда (состояние, история, explain, поток лога, подписка на события очереди и раннеров), отчёт раннера о состоянии сервисов (кто тёплый, сколько памяти) и команда брокера «остановить сервис» (вытеснение, 3.11). Административные команды (policy reload и подобные) в протоколе по сети не существуют: сетевое подключение получает отказ, а принимаются они только по локальному IPC от пользователя ОС, у которого есть права на каталог состояния брокера (администратор машины или владелец службы). Отдельной пометки «админ» в конфигурации нет: кто имеет доступ к машине брокера, тот им и управляет (правит policy.toml, вызывает policy reload, broker add, runner remove, client remove); пользователи из [[local_user]] без этих прав только ставят свои заказы и смотрят своё. Каждое сообщение о джобе идемпотентно по ключу клиента, JobId и номеру seq (счётчик отдельно по каждой паре «джоба, направление»), поэтому повтор после переподключения ничего не меняет. В рукопожатии версия протокола; брокер отказывает несовместимой мажорной версии и сообщает об этом, так что обновлять всё одновременно внутри мажорной версии не нужно.
  • Обновление программы. Владелец обновляет каждую машину сам; совместимость обеспечивает версия протокола (внутри мажорной версии роли разных версий работают вместе, при несовместимой версии брокер отказывает с понятным сообщением). Распространения бинарников и самообновления нет, поэтому нет и дополнительного исходящего соединения. (Решение пользователя; самообновление через брокера — возможное расширение.)
  • Живой лог. Раннер стримит чанки брокеру, брокер сохраняет лог и ретранслирует чанки hub; hub пишет temp/runner/<job-id>.log в каталоге отправителя, и агенты читают один файл. Раннер и брокер ведут каждый свой outbox (брокер хранит результаты для отсутствующего hub [results] keep_hours и потом удаляет, раннер хранит до доставки и отбрасывает при удалении раннера брокером): при разрыве раннер сбрасывает брокеру вывод и результаты по порядку без дублей, а брокер так же доставляет hub чанки, результаты и подтверждения отмен.
  • Hub пропал. Брокер держит заказы этого hub до absent_after_min (отсчёт от последнего heartbeat клиента, а после рестарта брокера от момента его старта; для локального клиента last_seen брокер ведёт по IPC-соединению), затем действует по политике; выполняющаяся джоба доживает, результат и вывод ждут в outbox брокера до возвращения hub (хранение и срок — политика).
  • Брокер пропал. Пул простаивает, заказы без Accepted остаются в outbox hub, принятые хранятся на брокере; раннер доживает джобы и по истечении срока убивает их.

  • Остановка раннера. Раннер сети не слушает, но у него есть локальный канал управления в каталоге состояния (IPC, доступ только пользователю ОС): через него down имя передаёт команду. С --drain раннер шлёт брокеру drain, брокер больше не выдаёт ему заказы, раннер доделывает текущую джобу, гасит сервисы и шлёт Bye; с --cancel он отменяет джобу с причиной runner_stopped, затем Bye. Без флагов down работает как --drain. Если брокер недоступен, раннер всё равно перестаёт брать заказы и доделывает джобу, а Bye уходит при появлении связи; после Bye брокер отмечает раннер offline.
  • Отзыв раннера. При runner remove выполнявшаяся на нём джоба сразу получает lost с причиной «раннер удалён», ресурсы возвращаются в пул; результат такой джобы, если раннер всё же пришлёт, не принимается. Отказ в авторизации раннер понимает как команду: он немедленно убивает дерево процессов джобы и не ждёт льготного срока.
  • Раннер пропал. Раннер без heartbeat получает состояние offline; то же правило (15 секунд, 3 пропуска) действует для клиента: по последнему heartbeat брокер пишет machine.last_seen и считает срок absent_after_min. Срок, переданный раннеру брокером, раннер может в runner.toml только сократить, но не увеличить, иначе он убил бы джобу позже, чем брокер вернёт её ресурсы. Выполнявшаяся на нём джоба, не отчитавшаяся за timeout_s от момента Started плюс льготный срок политики ([grace] lost_min, по умолчанию 3 минуты), переходит в lost: память, CPU и теги возвращаются в бюджет пула, hub получает результат lost. Срок, после которого раннер сам убивает джобы при недоступном брокере, брокер передаёт при регистрации, раннер хранит его локально и может переопределить в runner.toml.
  • Мёртвый отправитель через машины. Hub следит за процессом-отправителем на своей машине и при его гибели отменяет заказы у брокера (submit --detach и ручки сохраняют смысл).
  • ci на другой машине. Джоба GitHub вызывает run через hub машины с раннером al-ci; hub подключён к брокеру своим ключом с ярлыком ci, особых сообщений для CI в протоколе нет.

3.10 Настройки раннера: потолок таймаута и кэш

У каждого раннера свой файл настроек владельца (runner.toml в его каталоге состояния). Ядро в нём ничего не знает про сборки: кэш для него — именованные каталоги с размером и временем последнего использования. Формат черновой. Ключ или секция, которые никто не читает (обычно опечатка), раннер не останавливают: они печатаются предупреждением при старте и в doctor.

name    = "linux-heavy"
platforms = ["linux", "android"]
tags    = ["gradle", "emulator"]
mem_mb  = 16384                # необязательно: по умолчанию вся память хоста
cpu     = 8                    # необязательно: по умолчанию все ядра хоста
allow_elevated = false         # запуск от root/администратора (раздел 3.12)
allow_same_user_as_broker = false  # раннер под пользователем брокера с чужими клиентами (3.12)

[env]                          # обязательно: PATH джоб и поиск [programs]; другие переменные джоб — в [job_env] (разделы 3.14, 13.4)
path = "/usr/local/bin:/usr/bin:/bin"

[accept]                       # необязательно: резерв раннера под тяжёлые заказы
min_mem_mb = 8192

[programs]                     # что искать и чем проверять
git    = {}
adb    = {}
gradle = { check = "gradle --version" }

[limits]
max_job_timeout_s = 3600     # потолок таймаута джобы на этом раннере
enforce       = "kill"      # необязательно: off | warn | kill; заменяет режим брокера (3.14)
mem_headroom  = 1.25        # необязательно: запас к заявленному mem_mb, от 1.0 до 100.0
disk_headroom = 1.5         # необязательно: запас к заявленному disk_mb, от 1.0 до 100.0

[cache]
max_size_gb    = 40          # общий размер кэша раннера
retention_days = 14          # удалять записи, которыми не пользовались дольше
evict          = "lru"       # при нехватке места — самые давние первыми

[workspace]
max_size_gb    = 20          # checkout'ы проектов
retention_days = 7

[commands]                   # необязательно: названия для клиентов с [commands] mode = "named"
build = "make all"           # название = командная строка раннера

[job_env]                    # необязательно: дополнительные переменные каждой джобы, службы и хука очистки (3.14)
JAVA_HOME = "/opt/jdk"
GRADLE_OPTS = "-Dorg.gradle.daemon=false"

[[cleanup]]                  # необязательно: команда после каждой джобы (3.14)
name      = "labelled-containers"
command   = "sh -c 'docker rm -f $(docker ps -aq --filter label=$LOCALRUNNER_JOB_LABEL)'"
timeout_s = 60               # от 1 до 3600, по умолчанию 60
on        = ["passed", "failed", "killed", "cancelled", "timeout"]   # по умолчанию все
  • Имя. --name побеждает name из файла, без обоих берётся имя машины. Имя раннера — это и имя его каталога состояния, поэтому имена из одних точек и с разделителями пути отклоняются. --count N (от 1 до 64) запускает имя-1 … имя-N с общим шаблоном runner.toml, у каждого свой каталог.
  • Ресурсы. mem_mb и cpu — то, что раннер предлагает пулу. Без них раннер объявляет всю память и все ядра хоста. Раннер выполняет одну джобу за раз и отдаёт ей все заявленные ресурсы; чтобы делить машину между джобами, владелец запускает несколько раннеров (--count) с меньшими значениями. Ноль и значения больше, чем у хоста, — ошибка при старте; если память хоста измерить не удалось, mem_mb обязателен.
  • Повышенные права. allow_elevated (по умолчанию false) — единственный способ запустить раннер от root, администратора или SYSTEM (раздел 3.12). Если права процесса определить не удалось, он считается повышенным.
  • Пользователь брокера. allow_same_user_as_broker (по умолчанию false) разрешает раннеру стартовать под тем же пользователем ОС, что и брокер не-служба, принимающий чужих клиентов; без него такой раннер не стартует (раздел 3.12).
  • Потолок таймаута. max_job_timeout_s ограничивает джобу на этом раннере. Таймаут профиля — требование заказа, молча он не урезается. Джоба, чей таймаут больше потолка раннера, этому раннеру не подходит (раннер не берёт её молча с урезанным таймаутом), а в причине ожидания сказано «нужен таймаут 7200 с, потолок раннера 3600 с». Поведение «подрезать вместо отказа» включает политика брокера: при [limits] timeout_above_max = "trim" (по умолчанию "reject") заказ с таймаутом больше max_job_timeout_s принимается с таймаутом, урезанным до этого предела (таймауты шагов — тоже не больше него); брокер сообщает новый таймаут в Accepted (необязательное поле timeout_trimmed_to), а hub пишет в копию лога и тому, кто ждёт, строку «=== timeout trimmed by the broker policy: 7200 s -> 3600 s ===». Подрезка касается только предела брокера: раннер с потолком меньше таймаута по-прежнему не подходит. Профиль по-прежнему обязан задавать timeout_s. Предел брокера (max_job_timeout_s в policy.toml) отклоняет заказ при приёме с причиной; hub таймаут не меняет.
  • Лимиты, окружение и очистка. [limits] enforce, mem_headroom, disk_headroom, [job_env] и [[cleanup]] описаны в 3.14 со значениями по умолчанию и проверками. Неверное значение — ошибка файла, раннер не запускается.
  • Кэш. Профиль может перечислить именованные кэши (cache = ["gradle", "cargo"]). Раннер хранит для каждого клиента, проекта и имени постоянный каталог между запусками (ключ кэша «ключ клиента, проект, имя»; общий кэш нескольких клиентов включает владелец правилом [cache] share = "project" в policy.toml, по умолчанию share = "client", чтобы один клиент не подложил артефакт в сборку другого; проект — атрибут, заявленный клиентом (3.5), поэтому при share = "project" общий кэш проекта получает любой клиент, назвавший этот проект, в том числе клиент с [commands] mode = "named") и сообщает джобе его путь переменной окружения (LOCALRUNNER_CACHE_<ИМЯ>); что в нём лежит и как использовать, решает команда джобы. Ядро не знает, что это кэш Gradle или Cargo.
  • Размер и хранение. Перед запуском джобы и по таймеру раннер удаляет записи, не использованные дольше retention_days, и, если кэш превышает max_size_gb, самые давние (lru) до нужного размера. Кэш, которым пользуется выполняющаяся джоба, никогда не удаляется; джоба, которой не хватает места даже после очистки, ждёт или падает с причиной.
  • Названия команд. [commands] сопоставляет названию командную строку. Раннер сообщает брокеру только названия, строки остаются на раннере. Клиенту, которому политика брокера задаёт [commands] mode = "named" (3.5), в команде каждого шага разрешено только название: раннер исполняет свою строку и никогда текст заказа, а название без описания в [commands] — отказ без запуска. Пустая строка команды — ошибка файла.
  • Рабочие копии. Checkout'ы удалённых джоб (раздел 3.7) подчиняются тем же правилам: хранение и размер в [workspace].
  • Раннер сообщает брокеру потолок таймаута, размер кэша и его заполнение; они видны на странице «Раннеры» и в метриках.

3.11 Сервисы раннера: политика с гарантиями

Программа, которую джобе нужно держать запущенной (демон сборки, эмулятор), описывается как сервис раннера. Когда её поднимать и гасить, решает политика владельца; гарантии безопасности зашиты в код и политикой не отключаются. Ядро по-прежнему не знает, что за программа внутри. Формат черновой; по умолчанию сервисов нет, и джоба сама запускает всё, что ей нужно (шаги профиля).

[service.build-daemon]
start        = "gradle --daemon"
ready_check  = "gradle --status"
stop         = "gradle --stop"
ready_timeout_s = 60
memory_mb    = 2048            # учитывается в бюджете пула, пока сервис жив
lifetime     = "idle"          # per_job | idle | keep
idle_timeout_s  = 900
max_lifetime_s  = 14400        # обязателен всегда
reuse        = "same_client"   # same_client | same_project | any
  • Где что описано. Сами сервисы (команды запуска, проверки и остановки, память, время жизни, reuse) описывает владелец раннера в runner.toml в разделах [service.*]: программы и команды лежат на раннере. Правила брокера (кому разрешено запрашивать сервис, вытеснение простаивающих) — в policy.toml: 
    [services]
evict_idle = true   # головному заказу не хватает ресурсов, а их держат простаивающие сервисы: остановить сервисы
  • Вытеснение. Если голове очереди не хватает памяти, а часть занята тёплыми сервисами без работы, брокер приказывает раннеру их остановить штатным stop. Сервис, который работает на джобе, не трогается; следующая джоба поднимет сервис заново. Включено по умолчанию (evict_idle), владелец может отключить.
  • Резервирование. Сервис стартует только в составе заказа и только после того, как брокер зарезервировал его память в бюджете пула; раннер сам ничего не стартует «про запас».
  • Политика решает: какие сервисы есть, как они стартуют и проверяются, правило жизни (per_job — гасится после джобы; idle — после простоя; keep — живёт, пока жив раннер), и кто может переиспользовать тёплый сервис (reuse). Профиль просит сервис по имени: services = ["build-daemon"].
  • Гарантии, которые политика не отключает:
    1. Ограниченная жизнь. У каждого сервиса обязателен max_lifetime_s, как и таймаут джобы: бессрочных сервисов нет.
    2. Учёт ресурсов. Память живого сервиса входит в бюджет пула; брокер не выдаёт её другим заказам, пока сервис жив. CPU сервиса не резервируется: ключа cpu у [service.*] нет, процессор раннера уже учтён за джобой (cpu заказа), а простаивающий сервис его почти не занимает. Тёплый сервис не может незаметно перегрузить машину.
    3. Полная уборка. Сервис запускается в контейнере процессов (Job Object, cgroup, группа процессов). Остановка завершает всё дерево; если stop завис, сервис убивается принудительно. Полная гарантия, включая отсоединившихся потомков (setsid, двойной fork), есть в Windows (Job Object) и в Linux с cgroup v2. Без cgroup и в macOS гарантия «лучшее усилие»: группа процессов и обход потомков по родителю, а отсоединившиеся потомки закрываются штатной командой stop сервиса и проверкой при старте.
    4. Не переживает раннер. При остановке раннера, сбое и перезапуске сервисы гасятся; осиротевшие процессы прошлого запуска находятся по записи в каталоге состояния и убиваются при старте.
    5. Готовность обязательна. Заказ не получает сервис, пока не пройдена проверка готовности; провал старта или проверки — джоба завершается с причиной «сервис не поднялся», а не зависает. Упавший сервис перезапускается ограниченное число раз, затем помечается недоступным и раннер перестаёт подходить заказам, которым он нужен.
    6. Изоляция. Тёплый сервис переиспользуется только в пределах reuse: по умолчанию тот же клиент. Состояние одного клиента не протекает к другому.
    7. Видимость. Каждый старт, остановка, перезапуск и причина попадают в лог и метрики (service_up, service_starts_total), а на странице «Раннеры» видны живые сервисы, их память и оставшаяся жизнь.
  • Требования заказа к сервису входят в допустимость раннера (3.7): раннер без нужного сервиса или с недоступным сервисом заказу не подходит.

3.12 Пользователь раннера

  • По умолчанию раннер работает под тем пользователем ОС, который его запустил (up), и все процессы джоб работают под ним же. Так он видит инструменты, кэши, устройства и рабочие каталоги пользователя; для заказов «та же машина» это необходимо. (Решение пользователя.)
  • Код пользователя не переключает. Если нужна изоляция, владелец заводит отдельного пользователя ОС (например, lr-runner) и запускает раннер под ним средствами ОС. Раннер, который принимает заказы от чужих клиентов или с удалённых машин, рекомендуется держать под отдельным ограниченным пользователем: он выполняет команды из заказа и не должен видеть чужие файлы.
  • Раннер под пользователем брокера. Если брокер работает не службой, а под тем же пользователем ОС, что и раннер, и политика разрешает клиентам любые команды ([commands] не named), команда из заказа любого клиента получает права владельца пула: открывает admin-канал брокера (выпуск кодов, удаление раннеров и клиентов, правка и перезагрузка политики), видит историю всех клиентов и читает ключ брокера и его базы, то есть может выдать себя за брокер. Поэтому, когда брокер принимает клиентов, кроме владельца (есть адрес [listen] или запись [[local_user]] с другим пользователем ОС; запись самого владельца, которую пишет init, не считается; без policy.toml действует политика по умолчанию), раннер этой установки отказывается стартовать: runner run, up (раннер не запускается, код выхода 1, остальные роли стартуют) и autostart on runner завершаются ошибкой «the runner refuses to start: … or set allow_same_user_as_broker = true in runner.toml to accept the risk», а doctor отмечает раннер ошибкой. Владелец, который принимает риск, пишет в runner.toml allow_same_user_as_broker = true (по умолчанию false): тогда раннер стартует, а doctor, up и сам раннер предупреждают. Одиночная установка (брокер принимает только владельца) не затронута: ни отказа, ни предупреждения. Тот же пользователь ОС определяется по установке: раннер и брокер одного каталога состояния; раннер того же пользователя из другого каталога состояния не распознаётся. Снять риск: раннер под отдельным пользователем, брокер службой ОС или [commands] default = "named".
  • Гарантия, которую нельзя отключить: раннер отказывается стартовать от root или администратора (SYSTEM в Windows), пока владелец явно не разрешит это в runner.toml (allow_elevated = true).
  • Брокер — исключение: служба ОС. Брокер ничего не исполняет, поэтому может и должен работать как служба, не зависящая от входа пользователей: служба Windows, системный юнит systemd, LaunchDaemon. Работает под отдельной непривилегированной учётной записью (не root, не SYSTEM); каталог состояния и policy.toml принадлежат ей, правит их владелец машины с правами администратора. Раннеры и hub остаются пользовательскими процессами. Если пользователь вышел, пропадают только его раннеры и hub, а пул других пользователей продолжает работать.
  • Windows. Раннеру с эмулятором или графикой нужна интерактивная сессия пользователя, поэтому такой раннер, как и ci, не служба системы. Служба подходит только раннерам без графики и работает под учётной записью службы, не под SYSTEM.

3.13 Секреты джоб

Секрет — значение, которое джобе нужно в окружении (доступ к приватному реестру пакетов, ключ подписи), но которого не должно быть в заказе. (Решение пользователя: секреты живут только на раннере.)

[secret.registry_auth]
from = "env:REGISTRY_AUTH"         # переменная окружения процесса раннера

[secret.signing_key]
from = "keychain:release-signing"  # хранилище ОС (Credential Manager, Keychain, libsecret)
  • Профиль просит секрет по имени: secrets = ["registry_auth"]. Значение подставляется в окружение джобы на раннере, а в заказе, outbox, истории и логах системы есть только имя.
  • Допуск решает политика брокера: какому клиенту (ярлыку) какие секреты можно запрашивать. Проверку делает брокер при приёме заказа, как сервер у GitHub: запрос недопустимого секрета отклоняет заказ сразу с причиной («секрет signing_key не разрешён ярлыку agent»), до очереди. Допущенные имена брокер кладёт в задание раннеру (Assign); раннер политики не знает, он только достаёт значения этих имён из своего хранилища и подставляет в окружение джобы.
  • Гарантии: значение секрета не пишется ни в один лог и метрику системы; раннер маскирует точные значения секретов в выводе джобы до отправки брокеру (маскировка защищает от случайной печати, а не от команды, которая намеренно преобразует значение); секрет виден только процессам той джобы и только на шагах, которые его запросили; сервисы раннера получают секрет только при явном запросе.
  • Чистое окружение. Окружение джобы строится с нуля: белый список (PATH из настроек раннера, HOME, TEMP, TMP и TMPDIR (все три указывают на личный временный каталог джобы, см. 3.14), переменные LOCALRUNNER_*) плюс запрошенные секреты; окружение процесса раннера, в том числе источники секретов env:, джоба не наследует. Это не защищает от команды, читающей хранилище ключей или файлы того же пользователя ОС, поэтому допуск секретов по ярлыку надёжен только вместе с [commands] mode = "named" или с раннером под отдельным пользователем ОС (3.12).
  • Секрет можно запросить и на отдельном шаге: { name = "publish", command = "...", secrets = ["signing_key"] }. Сервис, получивший секрет, нельзя переиспользовать шире reuse = "same_client".
  • Если источник секрета недоступен (переменной нет, хранилище заблокировано), джоба завершается с причиной «секрет не найден: имя», а не запускается без него.
  • В истории и на дашборде видны имена запрошенных секретов, но не значения.

3.14 Лимиты джобы, очистка после неё и чужая нагрузка

Заявленные в профиле cpu, mem_mb и disk_mb раньше служили только планировщику. Этот раздел описывает, что заставляет саму джобу им подчиняться, как убирается то, что осталось вне джобы, и как учитывается реальная нагрузка машины. Лимиты по умолчанию включены в режиме warn: без настройки раннер записывает пики каждой джобы, пишет предупреждение в лог джобы, когда превышен потолок заявленного mem_mb или disk_mb (на 1.25), ограничивает долю CPU заявленным cpu и число процессов; ничего не убивается, пока владелец не выберет kill. Чтобы всё выключить, задайте mode = "off" в [resources] брокера или enforce = "off" в [limits] раннера. Допуск по чужой нагрузке по умолчанию остаётся выключенным. Ядро остаётся универсальным: оно не знает контейнеров, демонов сборки и инструментов; всё конкретное — команда или число, которые пишет владелец.

# policy.toml брокера (все таблицы необязательны)
[resources]
mode          = "warn"       # off | warn | kill; warn по умолчанию; "off" выключает лимиты
mem_headroom  = 1.25         # потолок = заявленный mem_mb x запас
disk_headroom = 1.25         # потолок = заявленный disk_mb x запас

[admission]
foreign_load    = "off"      # off | wait
mem_headroom_mb = 256        # сколько памяти должно остаться свободной сверх mem_mb заказа

# runner.toml: [limits] enforce / mem_headroom / disk_headroom, [job_env], [[cleanup]] (см. 3.10)
  • Кто решает. [resources] брокера уходит раннеру с каждым назначением. Владелец раннера переопределяет его в runner.toml: [limits] enforce заменяет mode, mem_headroom и disk_headroom заменяют запасы; значение владельца машины сильнее значения брокера. mode — off, warn или kill (по умолчанию warn, в том числе когда [resources] есть без mode или таблицы нет вовсе); запас — число от 1.0 до 100.0 (по умолчанию 1.25); всё остальное — ошибка файла (брокер отклоняет политику, раннер не запускается). policy check предупреждает о запасе, который при mode = "off" ни на что не влияет.
  • Потолки. Применяются, только если режим не off, и только к ресурсу, который джоба заявила (заявленный 0 — без лимита). Память: mem_mb на mem_headroom. Диск: disk_mb на disk_headroom. CPU: заявленные cpu ядер процессорного времени; это доля, а не привязка к ядрам: джоба может запустить любое число потоков, но в сумме получит не больше, и это жёсткий предел. CPU никогда не приводит к убийству джобы, она лишь работает медленнее. Число процессов: max(512, cpu x 256).
  • Режимы. off (выбирается явно) ничего не ограничивает и только записывает пики. warn (по умолчанию) пишет строку-предупреждение в лог джобы, когда потолок превышен, и даёт джобе идти дальше. kill завершает всё дерево процессов; джоба становится failed с причиной resource_exceeded и текстом превышен заявленный mem_mb: заявлено X МБ, пик Y МБ (или disk_mb). kill стоит включать, когда накопилась история пиков (раздел 8): владельцу следует перейти с умолчания warn на kill, когда пики в истории подтвердили, что заявленные значения верны. Внимание: это умолчание меняет поведение существующих установок; предел CPU и предел числа процессов действуют с этого момента, хотя ничего не убивается. Джоба, завершившаяся с кодом 0 при пике выше потолка, остаётся passed.
  • Механизмы памяти, CPU и процессов (lr-exec):
ХостenforcementКак
Windowsosдерево процессов джобы в Job Object: предел памяти JOB_MEMORY, жёсткий предел доли CPU, ActiveProcessLimit
Linux, контроллеры cgroup v2 делегированы пользователюosscope, созданный systemd-run со свойствами MemoryMax, CPUQuota, TasksMax
Linux без делегированных контроллеровwatcherнаблюдатель в пользовательском пространстве
macOSwatcher (всегда)наблюдатель в пользовательском пространстве; механизма ОС здесь нет
  • Наблюдатель. Примерно раз в 250 мс он замеряет дерево процессов джобы: резидентную память (RSS) в Unix, поэтому значение приблизительное, и зафиксированную (commit) память в Windows. В режиме наблюдателя CPU снижается приоритетом процесса (nice), а предел числа процессов не действует. Наблюдатель — арбитр убийства по памяти в любом режиме; где есть лимит ОС, он лишь страховка на 10 % выше потолка, чтобы джоба завершилась с правильной причиной раньше, чем ОС откажет в выделении. Раннер сообщает механизм в возможностях (enforcement: os или watcher); он виден в runners и на дашборде. На macOS все цифры памяти приблизительны.
  • Диск. Наблюдатель примерно раз в 2 секунды суммирует размеры файлов в рабочем каталоге джобы и в её личном временном каталоге <каталог состояния раннера>/tmp/lr-<job-id> (общий системный temp не измеряется; символические ссылки не разворачиваются); потолок — disk_mb на запас, режимы те же. Допуск тоже использует запас: раннер сверяет свободное место тома рабочего каталога с disk_mb на запас (настроенный запас действует и при mode = "off"). Дисковые квоты ОС не используются.
  • Личный временный каталог. Каждая джоба получает каталог <каталог состояния раннера>/tmp/lr-<job-id> (не внутри системного temp; используется всегда, от настроенного temp не зависит); TEMP, TMP и TMPDIR джобы указывают на него. Он создаётся до первого шага, входит в измеряемый диск джобы вместе с рабочим каталогом и удаляется после джобы, в том числе после kill и отмены: до 8 попыток с паузой 250 мс (в Windows файлы только что убитого процесса недолго заняты). После сбоя раннера при его запуске (восстановление) удаляется всё содержимое <каталог состояния>/tmp. Раньше джоба писала во временный каталог системы; теперь временные файлы попадают в этот каталог, и команды, рассчитывавшие на общий temp, этого не увидят.
  • Пики. Пиковая память и пиковый диск каждой завершённой джобы пишутся в историю в любом режиме (раздел 8).
  • Очистка после джобы. Джоба и её дерево ограничены, но контейнеры, запущенные через демон, демоны сборки и подобные остатки живут вне джобы. [[cleanup]] в runner.toml перечисляет команды, которые запускаются после любого исхода джобы: name (уникальное, обязательно), command (обязательна, раннер её не интерпретирует), timeout_s (от 1 до 3600, по умолчанию 60), on (непустой список из passed, failed, killed, cancelled, timeout; по умолчанию все пять; killed — это resource_exceeded или потерянный брокер). Хуки идут друг за другом в порядке файла, с окружением джобы плюс LOCALRUNNER_JOB_ID и LOCALRUNNER_JOB_LABEL (lr-<job-id>, уникальна для джобы). Сбой хука не меняет результат джобы: в лог джобы идёт строка-предупреждение, в диагностику раннера — запись. Джоба, прерванная падением или перезапуском раннера, получает свои хуки один раз при следующем запуске как killed (до отправки её результата runner_restarted; идентификатор джобы берётся из маркера активной джобы), поэтому хук должен быть идемпотентным. Хуки не запускаются для заказа, отклонённого при приёме. Примеры (удалить контейнеры с меткой джобы, остановить демон сборки) — команды владельца, а не поведение ядра.
  • Окружение джобы. [job_env] добавляет переменные каждой джобе и каждому хуку (например, чтобы отключить повторное использование демона). Имена проверяются (буквы, цифры, _, не с цифры); PATH, TEMP, TMP, TMPDIR и LOCALRUNNER_* запрещены; HOME разрешён. Значение владельца заменяет переменную с тем же именем, уже имеющуюся в окружении. LOCALRUNNER_JOB_LABEL добавляется в окружение джобы, только если есть хотя бы один [[cleanup]].
  • Чужая нагрузка. Раннеры присылают реальную нагрузку своей машины вместе с heartbeat: свободную память (МБ), занятую долю CPU (%) и число ядер. С [admission] foreign_load = "wait" (по умолчанию off) заказ ждёт, пока на машине выбранного раннера свободной памяти меньше, чем mem_mb плюс mem_headroom_mb (по умолчанию 256), или свободных ядер меньше, чем cpu заказа. Причина видна в status и explain: занято чужими процессами: свободно 800 МБ, нужно 2000 или занято чужими процессами: CPU 95%, нужно 4 ядер. Заявленный cpu выполняющихся джоб этого же брокера на той же машине вычитается из занятой доли, а память, заявленная джобами, назначенными после последнего замера, — из свободной, поэтому ничего не считается дважды. Выполняющиеся джобы не приостанавливаются и не притормаживаются. На macOS читаются vm_stat (свободные, неактивные и спекулятивные страницы) и ps -A -o %cpu (сумма по процессам, делённая на логические ядра). Раннер без данных о нагрузке (старый) допускается как раньше. policy check предупреждает, если mem_headroom_mb задан при foreign_load = "off" или не меньше памяти пула.
  • В этой версии нет: лимитов дискового ввода-вывода, привязки к ядрам, приостановки выполняющихся джоб, прокси Docker-сокета, дисковых квот ОС; предела числа процессов в режиме наблюдателя.

  • Допуск раннера. Владелец раннера может зарезервировать его правилом [accept] в runner.toml: принимать только заказы с требованиями не меньше заданных (лёгкие джобы не займут «тяжёлый» раннер). Допуск по ярлыку клиента — правило политики брокера.
  • Приоритет не выводится из характеристик. Его задают правила политики по ярлыку клиента из записи ключа и по заявленным атрибутам заказа (источник, теги, размер) в сочетании с ярлыком. По умолчанию действует правило: ярлык клиента ci получает приоритет 100.
  • Имена раннеров вроде light и heavy — просто имена. Другая градация не требует изменения программы: меняются профили и runner.toml.

5. Профили и шаги

Профиль лежит в .localrunner/profiles.toml репозитория потребителя. Это требования джобы, а не настройки машины.

[profile.rust-unit]
command = "cargo test --workspace"
timeout_s = 900
mem_mb = 4096
cpu = 4
tags = ["cargo"]

[profile.android-tier]
command = "pwsh scripts/android-tier.ps1"
timeout_s = 3600
mem_mb = 12288
cpu = 6
tags = ["gradle", "emulator"]
exclusive = ["gradle", "emulator"]
  • timeout_s обязателен; значения по умолчанию и неограниченного запуска нет. Верхний предел задают политика брокера (отказ при приёме) и потолок раннера (раннер с меньшим потолком не подходит, раздел 3.10); таймаут молча не урезается.
  • mem_mb и cpu профиля можно заменить на один запуск флагами submit --mem 6g --cpu 4 (память в МБ — 6144 — или с единицей: 512m, 6g; CPU — целое число ядер, не меньше 1). Профиль при этом не меняется; значение флага больше пула брокер отклоняет кодом rejected_override_above_pool (3.1).
  • cache — именованные кэши, сохраняемые на раннере между запусками этого проекта (раздел 3.10); ядро не знает их содержимого.
  • tags — ресурсы, которые джоба держит на время прогона; exclusive — теги, которые больше никто из запущенных джоб держать не может.
  • Ядро не интерпретирует command, оно только запускает процесс. Несколько команд — steps. Требования к раннеру (память, CPU, диск, программы, платформы, теги) профиль перечисляет сам (раздел 4).

5.1 Шаги

В профиле либо command (один шаг), либо steps (упорядоченная последовательность), но не оба.

[profile.rust-gate]
timeout_s = 1800
tags = ["cargo"]
steps = [
  { name = "fmt",    command = "cargo fmt --all --check", timeout_s = 120 },
  { name = "clippy", command = "cargo clippy --workspace --all-targets -- -D warnings", timeout_s = 600 },
  { name = "test",   command = "cargo test --workspace", timeout_s = 900, mem_mb = 8192 },
]
  • Одна джоба — одно место в очереди: шаги идут подряд, между ними другие джобы на том же раннере не стартуют.
  • Ресурсы берутся один раз: максимум по шагам (память, CPU) и объединение тегов и exclusive; шаг может переопределить mem_mb и cpu, а свои tags только добавляет к тегам профиля. Захвата по шагам нет, значит нет частичного удержания и взаимной блокировки.
  • У каждого шага свой обязательный timeout_s, он идёт внутри оставшегося таймаута джобы (тоже обязательного); шаг убивается по более раннему из двух.
  • Упавший шаг останавливает джобу, остальные шаги skipped. continue_on_failure = true позволяет продолжить, результат джобы остаётся failed.
  • Ветвления, условия и зависимости между шагами в ядро не входят — используйте скрипт внутри command.
  • Несколько независимых джоб из одной сессии — несколько submit: каждая ставится отдельно, между ними могут идти джобы других сессий.

6. Очередь и планирование

  • Очередь заказов живёт на брокере. Порядок выдачи определяет политика; по умолчанию строгий приоритет (заказы клиента ci раньше остальных), внутри приоритета порядок постановки (FIFO). Джоба стартует, когда свободен раннер, удовлетворяющий требованиям заказа, и планировщик выдаёт память, CPU и теги.
  • Заполнение дыр с предсказанием. Каждая джоба обязана иметь timeout_s, поэтому время, когда идущая джоба точно освободит раннер, память, CPU и теги, известно заранее: старт плюс timeout_s (верхняя граница; на деле джоба часто кончается раньше). По этим срокам брокер вычисляет для головного заказа самый ранний возможный старт и считает его зарезервированным. Следующий заказ может обойти головной, только если он не задержит этот старт: он помещается в свободные ресурсы сейчас и либо заведомо закончится до резервации (его timeout_s не больше времени до неё), либо не занимает ничего из того, что понадобится головному (другой раннер, оставшаяся память). Если такого заказа нет, пул ждёт головной. Если у головного заказа нет предсказуемого старта (все подходящие раннеры не на связи), резервации он не создаёт, и её получает первый из следующих заказов, у которого старт предсказуем: так недоступный раннер не останавливает очередь. Резервация пересчитывается при каждом событии: если идущая джоба кончилась раньше срока, головной стартует раньше. Так тяжёлый заказ не голодает без отдельного порога, а пул не простаивает без причины. Простаивающие тёплые сервисы при расчёте считаются свободными, если разрешено вытеснение. Резервация учитывает [reserve], [quota] и [accept] раннеров. Порядок решает политика, а старение (age_after_min) поднимает давно ждущий заказ в голову. Из-за прогноза по таймаутам мелкие заказы с длинным timeout_s обходят реже, поэтому профилям стоит ставить реалистичные таймауты.
  • Без вытеснения: заказ высокого приоритета никогда не останавливает запущенную джобу, он идёт первым и ждёт ресурсов.
  • Ожидание из-за чужой нагрузки. С [admission] foreign_load = "wait" заказ ждёт и тогда, когда реальная нагрузка машины раннера оставляет слишком мало места. Причина: занято чужими процессами: свободно 800 МБ, нужно 2000 или занято чужими процессами: CPU 95%, нужно 4 ядер; видна в status и explain. Выполняющиеся джобы никогда не приостанавливаются (3.14).
  • Старение (по умолчанию 30 минут, правило политики): джоба, ждавшая дольше порога, упорядочивается как высший определённый приоритет. Возраст считается от постановки в hub (передаётся в заказе) и не обнуляется при перевыборе брокера.
  • Джоба, которая не поместится в лимиты пула никогда, отклоняется при приёме с причиной.
  • Состояния: queued → running → passed | failed | timeout | cancelled | lost; при отмене выполняющейся джобы промежуточное cancelling; шаг — passed | failed | timeout | skipped | cancelled.
  • Каждая джоба пишет stdout и stderr в temp/runner/<job-id>.log каталога отправителя с заголовком на шаг; submit возвращает идентификатор, ожидание стримит ход и возвращает код выхода.
  • Отмена и таймаут убивают дерево процессов: Windows Job Object и Linux cgroup v2 — полностью, иначе группа процессов и обход потомков (лучшее усилие, раздел 10). Осиротевшие процессы после сбоя ищутся по паре «pid плюс время старта», чтобы не убить чужой процесс с переиспользованным номером.
  • Устойчивость: правило мёртвого отправителя описано в разделе 7; мёртвая джоба убирается.

7. Отправитель и отмена

Каждая джоба говорит, кто её отправил, чтобы очередь, страница и лог отвечали на вопрос «чья это».

7.1 Идентичность

  • --as <имя> обязателен для submit и run из сессии или терминала (внутри GitHub Actions получает значение по умолчанию). Это свободная метка вызывающего (claude:session-3, alex); ядро агентов не перечисляет и не интерпретирует. Необязательный --note <текст> (до 200 символов) говорит, зачем запуск.
  • CLI собирает сам и без возможности переопределить: пользователя ОС, хост, идентификатор и время старта процесса-отправителя, рабочий каталог, а для git-worktree ещё ветку и корень. Это общие данные git и ОС, без знания об агентах.
  • Показывается в status, HTML-снимке, дашборде и заголовке лога: проект, источник, метка, заметка, ветка, каталог, возраст джобы.
  • Идентичность — подсказка, а не аутентификация: любой локальный процесс того же пользователя ОС может отправить под любой меткой. Граница — IPC, доступный только пользователю ОС. Для брокера границей служит ключ клиента.
  • Отмена: по умолчанию только джобы с той же меткой --as и тем же пользователем ОС; чужая метка требует --force, что записывается в лог отменённой джобы вместе с меткой отменившего. Эта проверка локальная, она в hub. Брокер сам разрешает отмену только заказов того же ключа клиента; отмена чужих заказов — право из политики ([cancel] others), по умолчанию им обладает только владелец брокера через локальный канал.

7.2 Проект и источник

  • project: нормализованный origin (owner/repo) каталога отправителя; без remote — имя корня репозитория; вне git — имя каталога. Записываются также корень репозитория и worktree, чтобы различать два worktree одного проекта.
  • source: session (терминал или сессия агента: метка, процесс, каталог) или github (джоба GitHub Actions, определяется по GITHUB_ACTIONS=true: репозиторий, workflow, job, run id и attempt, ref, actor, URL запуска; --as по умолчанию github:<workflow>/<job>).
  • Чтение окружения CI живёт в адаптере источника github; ядро видит только нормализованные поля. Другая CI-система — другой адаптер, не изменение ядра.
  • У джобы github процесс-отправитель — run, который вызвал ci-раннер GitHub на машине hub: reaper следит за ним как за любым другим. Отменённый workflow завершает процесс шага, а значит и run, после чего reaper отменяет заказ (если не --detach).
  • Везде показываются project, source и метка вместе (например, Al.Browser · session · claude:fix-12); github ссылается на URL запуска. Фильтры: status --project, --source session|github, --as; те же поля есть в --json.

7.3 Свои джобы и ранняя отмена

  • submit печатает идентификатор и пишет ручку temp/runner/<job-id>.json в каталоге отправителя (метка, идентификатор, профиль, время). После потери контекста или перезапуска агент находит свои джобы по ручкам и по hub.
  • localrunner jobs --mine — джобы вызывающего (тот же пользователь ОС и метка --as; метка задана или читается из последней ручки в каталоге); --active оставляет только queued и running; есть --json.
  • localrunner cancel <job-id> отменяет одну джобу, cancel --mine — все активные джобы вызывающего; проверка владельца по 7.1, чужая метка — --force. cancel --mine, down --cancel, runner remove и client remove разрушают работу, поэтому перед действием спрашивают подтверждение: --yes или ввод yes в терминале; без терминала и без --yes команда ничего не делает, пишет «…; confirm with --yes» и возвращает 1. Отмена одной джобы и down без --cancel не спрашивают.
  • Таймаут. По истечении timeout_s раннер сразу убивает дерево процессов джобы, без мягкого сигнала и льготного периода (они только для отмены), и шлёт результат timeout. Брокер при этом ничего не ждёт: его запас [grace] lost_min нужен лишь на случай, когда раннер не смог отчитаться.
  • Эффект отмены: queued снимается из очереди сразу; выданный, но не стартовавший заказ (в том числе на шаге source) отменяется как running; running получает мягкий сигнал (Ctrl+Break в Windows, SIGTERM в остальных ОС), после льготного периода (10 секунд по умолчанию) дерево убивается, выполняющийся шаг cancelled, остальные skipped, джоба cancelled, ресурсы освобождаются только когда дерево мертво; уже завершённая джоба — отчёт о конечном состоянии без действий.
  • Причина отмены пишется в заголовок лога: кто, когда и --reason, если задан.
  • wait — только наблюдатель: прерывание wait (Ctrl+C, таймаут инструмента агента) ничего не отменяет. Отменяет только cancel, таймаут или правило мёртвого отправителя.
  • Процесс-отправитель — тот, что вызвал CLI (родитель короткоживущего localrunner, записанный со временем старта), а не сам CLI, иначе каждая джоба умирала бы после возврата submit. submit сообщает hub о завершении сообщением Done (CLI → hub; не путать с сетевым Bye раннера и hub) сразу после получения идентификатора, а wait работает на своём соединении. (Решение автора.)
  • Мёртвый отправитель: когда процесс-отправитель исчез, его ждущие заказы снимаются, выполняющиеся убиваются, чтобы освободить машину. submit --detach позволяет заказу, ждущему и выполняющемуся, пережить вызвавшего (reaper его не трогает; ждущий отсоединённый заказ снимает только явная отмена или долгое отсутствие hub по [orphans]); она остаётся видимой и отменяемой по метке. Джоба github отменяется отменой запуска workflow или оператором через cancel --force.
  • Определение живости: родитель CLI, пара pid и время старта (в Linux относительно загрузки, из /proc starttime), отправитель считается мёртвым, если при двух проверках подряд с интервалом 2 секунды процесса с таким pid нет или время его старта не совпадает с записанным (так переиспользованный pid не убьёт чужую джобу). Проверка живости идёт каждые 5 секунд, подтверждается вторым проходом через 2 секунды. Время старта берётся в Linux из /proc/<pid>/stat (starttime, пересчитанное в абсолютное), в macOS из proc_pidinfo (PROC_PIDTBSDINFO), в Windows из GetProcessTimes; если время старта получить не удалось, джоба не убивается, а в лог пишется предупреждение. Короткоживущий shell агента убьёт его джобы, поэтому скилы предписывают submit --wait или --detach.

8. История

Завершённые джобы хранятся и доступны позже из любой сессии и для любого проекта.

  • Хранилище. SQLite broker.db в каталоге состояния брокера (одна база: история запусков, реестр машин, очередь заказов) (SQLite в общественном достоянии, что проектное правило о лицензиях допускает; обёртка — крейт rusqlite, MIT). Строка на джобу со всем известным: идентификатор, клиент (ключ, MachineId, ярлык), проект, источник, метка, заметка, ветка, каталоги, профиль, времена постановки, старта и финиша, результат, код выхода, кто отменил и почему, раннер; строка на шаг: состояние, времена, код, таймаут. Запись создаётся при постановке и обновляется при каждой смене состояния, поэтому сбой теряет не более последнего обновления.
  • Чья история. Брокер — источник истины для запусков на своих раннерах, включая то, с какого клиента запуск пришёл. Hub хранит только outbox недоставленных заказов и копию лога в каталоге отправителя; историю и подробности запрашивает у брокеров. Если ноутбук выключен, история его запусков остаётся на брокере и доступна другим hub в пределах политики видимости. (Решение пользователя; «брокер ничего не знает о hub» относится к коду, а не к данным.)
  • Логи. Полный лог хранится у брокера в logs/, копия — temp/runner/<job-id>.log каталога отправителя; для github хранится и URL запуска.
  • Пики. Каждая завершённая джоба получает пиковую память и пиковое занятое место на диске в МБ (peak_mem_mb, peak_disk_mb) в любом режиме принуждения; пик диска измеряется только у джобы, заявившей disk_mb. Они видны в history (столбцы PEAK_MEM_MB и PEAK_DISK_MB перед BROKER, - если неизвестно), history show, jobs, explain, status --json и в карточке дашборда. По ним подбирают честные mem_mb и disk_mb до включения kill (3.14).
  • Хранение. По возрасту и суммарному размеру, что наступит раньше: по умолчанию 30 дней и 2 ГБ логов, 365 дней строк (политика брокера). Чистка идёт с самых старых и не трогает активные джобы. Брокер на общей машине ограничивает объём политикой, чтобы один клиент не заполнил диск пула. Пределы в коде, значения меняет политика: лог одной джобы 256 МБ (сверх — обрезка с пометкой), outbox брокера на получателя 512 МБ (сверх сбрасываются чанки вывода, результат сохраняется), 100 активных заказов на ключ клиента, ограничение частоты запросов API: не больше 1200 заказов и запросов чтения на ключ клиента за любые 60 секунд ([limits] api_requests_per_min); сверх него заказ отклоняется кодом rejected_rate_limited, а запрос чтения получает отказ с тем же кодом; отмена, отписка, прекращение слежения за логом, подтверждения и heartbeat не ограничиваются, а отклонённый запрос и повторно досланный уже принятый заказ (outbox hub после переподключения) в счёт не идут: повтор получает прежний ответ.
  • CLI. history [--project P] [--source session|github] [--as L] [--profile N] [--result R] [--since D] [--limit N] [--platform] [--runner] [--client C], новые первыми, --json; history show <job-id> — полная запись; log <job-id> [--step NAME] [--tail N] [-f] читает сохранённый лог, с -f для незавершённой джобы следит за ним до конца. Команды идут через hub к брокерам, которые он знает, и по умолчанию показывают запуски этого клиента; history --all показывает всё, что разрешает политика видимости брокера, --client C — запуски названного клиента. Время печатается в UTC; --since принимает возраст (30m, 2h, 7d) или дату (2026-11-01). Лог перед выводом проходит маскировку секретов CLI по целым строкам (встроенные имена и [redact] fields из logging.toml каталога конфигурации, с которым запущен CLI; поля из конфигурации брокера-службы сюда не попадают), поэтому секрет, разрезанный между порциями, тоже скрыт. Так же маскируются вывод run и wait и последние строки выполняющихся джоб в status и status --json. Отклонённый приказ тоже записывается: в history он виден как rejected (фильтр --result rejected) с кодом и текстом причины, на дашборде то же состояние; повторная отправка того же приказа снова отклоняется с той же причиной.
  • Представления. status --html --history добавляет таблицу истории в снимок; у дашборда есть вкладка «История» с теми же фильтрами; каждая строка ведёт к логу.
  • Статистика. localrunner stats [--project P] [--profile N] [--client C] и страница «Статистика»: запуски, доля успехов, время ожидания и длительность (медиана и 95-й процентиль) по профилям и шагам, доля таймаутов и отмен, насыщение пула по клиентам. Считается брокером по его истории; владелец брокера видит весь пул, клиент — свои данные. Цель — выставить честные timeout_s и увидеть, где ждёт очередь.
  • История читается представлениями и не уходит за пределы сети: брокер отдаёт её только аутентифицированным клиентам по политике видимости.

9. Просмотр очереди и дашборд

9.1 Три формы одних данных

  • localrunner status — текст, --json для агентов и скриптов.
  • status --html [путь] — дашборд одним самодостаточным HTML-файлом с вшитыми данными (по умолчанию temp/runner/queue.html). Снимок: не нужен слушатель, открывается с диска. Завершённые джобы (до 100 на брокер) попадают в него только с --history, логи выполняющихся и завершённых джоб (последние 500 строк) — только с --with-logs: CLI читает их через hub, брокер отдаёт лишь те, что разрешает его политика видимости, а текст проходит маскировку секретов; недоступный лог просто не вшивается. Последние строки выполняющихся джоб в снимке и в живом дашборде проходят ту же маскировку, как и хвост копии лога, который живой дашборд читает с диска (строка, разрезанная началом хвоста, отбрасывается). Файл снимка доступен только его владельцу (0600 на Unix, DACL владельца на Windows).
  • localrunner dashboard — живой вид в браузере. Hub отдаёт страницу и JSON/SSE-поток на 127.0.0.1 на случайном свободном порту; URL несёт случайный токен запуска, запросы без него или с чужого origin отклоняются. Запускается по требованию, останавливается Ctrl+C или down: раз в секунду проверяет, что hub отвечает, и завершается, когда остановленный hub не ответил на две проверки подряд; если hub не отвечал с запуска dashboard, остановка — только Ctrl+C.

Каждая вкладка есть в CLI. Страница ничего не показывает такого, чего нельзя увидеть командой; у каждой команды есть --json.

9.2 Страница

Одна интерактивная страница обслуживает и живой дашборд, и статический снимок: снимок вшивает данные JSON и выполняет тот же код с выключенными обновлениями и действиями. Доставка: одна самодостаточная страница, вшитая в hub, без внешних скриптов, шрифтов и сетевых запросов (работает офлайн). Светлая и тёмная тема следуют системе; вёрстка работает на ширине телефона; управление с клавиатуры с видимым фокусом.

  • Очередь — выполняющиеся и ждущие джобы. Строка раскрывается в карточку: проект, источник, метка, заметка, ветка, каталог, профиль, раннер, причина ожидания и лента шагов (полоса на шаг относительно таймаута, текущий шаг анимирован, skipped серый). Рядом живой лог выбранного шага: слежение, пауза, поиск по тексту, копирование, скачивание; кнопка отмены.
  • История — завершённые джобы, новые первыми; щелчок открывает ту же карточку с сохранённым логом. В карточке видны пиковая память и пиковый диск джобы.
  • Статистика — по профилю и шагу: доля успехов, ожидание и длительность (медиана, 95-й процентиль) встроенными SVG-диаграммами, диаграмма полос по раннерам за день (кто занимал раннер, простои, ожидание) и насыщение: сколько джоб и сколько времени ожидания приходится на каждую причину (раннер занят, память, CPU, exclusive-тег, нет раннера, правило политики), чтобы владелец видел, какой лимит поднять.
  • Раннеры — по брокеру и пулу, затем по раннеру: online/offline с последней активностью, платформа, длина очереди, шкалы памяти и CPU, занятые и exclusive-теги с их держателями; для раннеров, не прошедших проверку программ или диска, — невыполненные характеристики. В таблице раннеров есть столбец enforcement (os или watcher, 3.14).

Общее для вкладок: фильтры (проект, источник, метка, раннер, профиль, результат, период, свободный текст), сортируемые столбцы; состояние в хеше URL, поэтому вид — ссылка, а последние фильтры восстанавливаются из localStorage. ?as=<метка> подсвечивает и закрепляет джобы метки. Живые обновления одним SSE-потоком с автопереподключением и видимым состоянием соединения; кнопка «Пауза» замораживает вид, новые события при паузе считаются счётчиком. Экспорт отфильтрованной таблицы в CSV или JSON и Save snapshot. Горячие клавиши: / поиск, j/k перемещение, Enter открыть, Esc закрыть, g q|h|s|r вкладки, ? список.

9.3 Источники данных

  • Страница и сервер читают через один интерфейс DataSource. Дашборд hub берёт всё из API брокеров: раннеры, нагрузку пулов, очередь, выполняющиеся заказы, историю запусков и логи. Когда брокер недоступен, дашборд показывает копии логов и заказы, ждущие в outbox. Дашборд не настраивается списком раннеров, а раннеры не знают адреса дашборда.
  • Одна модель данных для всех трёх форм — view-типы DashboardSnapshot, DashboardJob и DashboardEvent в lr-proto (dashboard.rs): их строит hub, а живая страница, снимок и экспорт JSON только читают.
  • Если брокер недоступен, его данные помечены как устаревшие; остаются заказы в outbox этого hub и копии логов. Дашборд на другой машине — тот же дашборд своего hub: он читает брокеры, которые знает этот hub.

9.4 Действия и безопасность дашборда

  • Отмена ждущей или выполняющейся джобы после подтверждения с названием джобы. Отмена со страницы считается --force: она записывается в лог и историю как отмена dashboard:<пользователь ОС> с причиной из диалога; на брокере действует то же правило ключа: дашборд hub отменяет только заказы своего ключа. Отмена всех джоб проекта или метки — отдельное явное действие со списком в диалоге. Нет отправки, правки профилей и конфигурации, запуска и остановки раннеров со страницы.
  • Случайный порт, токен на запуск; токен обменивается на сессионный cookie (HttpOnly, SameSite=Strict) при первом запросе и убирается из адресной строки.
  • Только localhost без возможности изменить: сокет на 127.0.0.1 (и ::1), никогда 0.0.0.0, :: или адрес LAN; нет опции, ключа конфигурации или переменной окружения, которые это расширят. Дашборд не публикуется и не туннелируется плагином.
  • Защита от DNS rebinding: запрос с Host, не равным localhost, 127.0.0.1 или [::1] с портом дашборда, отклоняется, как и запрос с чужим Origin. При старте hub проверяет фактический адрес и завершается с ошибкой, если он не loopback.
  • Ничего не покидает машину: hub, CLI и страница не делают исходящих запросов, не шлют телеметрию, не загружают логи, историю и снимки. Единственные исходящие соединения ролей системы (установщик — отдельная программа, которую владелец запускает вручную, см. 10.1): ci-раннер GitHub Actions к GitHub (собственный протокол, без данных системы), соединения hub и раннеров с брокерами, git fetch раннера из репозитория джобы и необязательный получатель логов и метрик (OTLP), который владелец включил в logging.toml.
  • Любой запрос, меняющий состояние, — POST с заголовком против подделки и проверкой Origin/Host; чтения и поток требуют сессионный cookie. Текст логов и полей выводится как текст, не как разметка; строгая CSP без выполнения встроенных скриптов; логи не индексируются и не кэшируются. Снимок содержит логи только с --with-logs, потому что в логах могут быть секреты из команд профиля.

Запуск. Доступны оба способа, и они не исключают друг друга. Вручную: up запускает hub, брокер и раннеры, down останавливает. Автозапуск: по умолчанию выключен, включается явной командой autostart on [роль] и выключается autostart off; он настраивается средствами ОС из таблицы выше и работает под пользователем, который его включил (раздел 3.12). Для брокера autostart on broker — то же, что broker install-service: служба ОС под отдельной учётной записью, нужны права администратора; up broker при работающей службе второго брокера не запускает. Автозапуск можно включить для одной роли: например, брокер и раннеры на выделенной машине всегда, а hub на ноутбуке вручную. У автозапуска окружение беднее, чем у терминала, поэтому PATH раннера и пути программ задаются в runner.toml явно. up при уже работающей роли ничего не дублирует.

ci-раннер нигде не служба системы: он должен работать в пользовательской сессии, чтобы видеть инструменты, кэши и устройства пользователя. Код выбирает ОС-специфичные части за одним внутренним интерфейсом; профили потребителя остаются нейтральными к ОС, где могут, и используют варианты command на ОС там, где не могут. Демон Windows стартует с CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP, поэтому джобы наследуют скрытую консоль и работает Ctrl+Break; раннер, запущенный без консоли (автозапуск, --background), заводит себе скрытую консоль сам, чтобы мягкая остановка доходила до его шагов (брокер шагов не исполняет, ему консоль для этого не нужна); именованный канал содержит SID пользователя и проверку владельца; пул по умолчанию — вся память хоста брокера и все его логические ядра (как в 3.5) (Docker и виртуалки входят в пул, но память измеряется на хосте брокера; владелец уточняет лимиты в политике).

broker install-service копирует бинарник в каталог службы (служба не зависит от каталога пользователя) и создаёт учётную запись службы. Каталог состояния службы он сначала проверяет: если каталог уже есть и он ссылка или junction, принадлежит не администраторам, не SYSTEM (root) и не службе, или его ACL явно пускает кого-то ещё (в Unix — запись для группы или всех), установка отказывает, ничего туда не копируя. Отсутствующий каталог сразу создаётся закрытым (в Windows — с защищённым дескриптором безопасности службы, в Unix — с режимом 0700), без промежутка, когда он открыт. Файл с несколькими жёсткими ссылками в каталоге отвергается так же, как ссылка: второе имя может принадлежать чужому файлу. Затем каталог закрывается целиком: в Windows защищённый DACL (полный доступ только у учётной записи службы, администраторов и SYSTEM, ничего не наследуется), владелец — учётная запись службы, у всего содержимого явные записи снимаются; в Linux режим 0700, в macOS 0710 (группе открыт только проход к ipc/ с режимом 0750), файлы без прав группы и всех, у службы брокера UMask=0077 (в launchd — Umask 63); пользовательские юниты и LaunchAgent hub и раннеров umask не задают, их процессы наследуют umask пользователя. Только после этого туда копируются policy.toml и logging.toml, если их там нет (существующий файл чужого владельца отвергается), и в [[local_user]] вносится установивший пользователь: при sudo — тот, кто его вызвал, при UAC в Windows — пользователь сеанса, даже если права дала другая учётная запись администратора. В Linux этот пользователь добавляется в группу al-localrunner (действует после повторного входа). Системные программы (sc.exe, schtasks.exe, powershell.exe, systemctl, chown и другие) запускаются по абсолютному пути из System32 или /usr/sbin, /usr/bin, /sbin, /bin, а не поиском рядом с бинарником. Если брокер внутри службы завершился сам или не стартовал, служба сообщает менеджеру ошибку (тот перезапускает её через 5 секунд), причина пишется в logs/service.log каталога службы. Административный канал службы принимает её владельца и администраторов; владельцем брокера (3.5, 3.9) считаются учётная запись, под которой он работает, и администраторы машины (в Windows — члены группы «Администраторы» и SYSTEM, в Unix — root); сетевым участникам это прав не добавляет. В Windows служба регистрируется (sc create) до проверки каталога, потому что учётная запись службы появляется только вместе с ней, но с ручным запуском: на автоматический запуск при загрузке она переводится последним шагом, после всех проверок и копирования. Если любой шаг отказал, служба, которую зарегистрировал этот запуск, удаляется; служба, существовавшая раньше, остаётся и после неудачной переустановки стоит на ручном запуске. Состояние службы autostart off broker и uninstall не удаляют.

Автозапуск hub и раннера запускает их с --background. В Windows это задача планировщика под самим пользователем: триггер — его вход, запуск в его сессии без повышения прав, перезапуск через минуту после сбоя (до 999 раз), без ограничения времени и с работой от батареи. Задача запускает localrunnerw.exe — запускатель без консоли, который стартует localrunner.exe рядом с собой со скрытой консолью и возвращает его код выхода, поэтому окно не появляется даже на мгновение. Задача создаётся без прав администратора; если политика машины это запрещает, команда завершается понятной ошибкой с подсказкой, а не переходит молча на другой способ. Имя задачи — Al.LocalRunner <роль> <SID пользователя>: папка планировщика общая для всех пользователей машины, и SID не даёт им заменить или удалить задачи друг друга; повторный autostart on заменяет только задачу этого пользователя, autostart off и uninstall удаляют только его задачи. Перезапуск при сбое задачи планировщика ещё нужно проверить на чистой ВМ.

У hub один каталог состояния, у каждого раннера свой: runner/<имя> внутри каталога установки со своими runner.toml, runner.db и ключом; up запускает раннеры по именам из этого каталога, а machine-id у них общий (он принадлежит установке). В каталоге состояния: machine-id, конфигурации, базы (broker.db, hub.db, runner.db), logs/, сертификат брокера и секретные ключи участника. Секретные ключи и базы доступны только владельцу каталога (права 0600 и аналог ACL в Windows).

10.4 Docker и Compose

Образ содержит только бинарник и работает не от root. Инструментов потребителя (gradle, adb, эмулятор) в нём нет: владелец строит свой образ на основе нашего (FROM) и добавляет нужное. Пример для брокера и одного раннера:

services:
  broker:
    image: al-localrunner:версия
    command: ["localrunner", "broker", "run"]
    ports: ["7443:7443"]
    volumes:
      - broker-state:/var/lib/al-localrunner
      - ./policy.toml:/etc/al-localrunner/policy.toml:ro
    restart: unless-stopped
  runner:
    image: al-localrunner:версия
    command: ["localrunner", "runner", "run"]
    volumes:
      - runner-state:/var/lib/al-localrunner
      - ./runner.toml:/etc/al-localrunner/runner.toml:ro
    depends_on: [broker]
    restart: unless-stopped
volumes:
  broker-state: {}
  runner-state: {}
  • Вступление. Код выдаёт docker compose exec broker localrunner broker add, раннер вступает командой runner join broker:7443 код; ключи и сертификат лежат в томах и переживают пересоздание контейнеров.
  • Политика. Владелец правит смонтированный policy.toml и вызывает docker compose exec broker localrunner policy reload: локальным каналом считается доступ внутри контейнера.
  • Конфигурация в контейнере. Каталог конфигураций задаётся --config-dir или LOCALRUNNER_CONFIG_DIR (в примере /etc/al-localrunner); сеть Compose (например 172.18.0.0/16) владелец добавляет в [networks]. Сервис раннера в compose.yaml поднимают после runner join, иначе контейнер перезапускается по кругу.
  • Границы. Контейнерный раннер файлов хоста не видит, поэтому берёт только заказы с коммитом. Его сети в списке [networks] владелец относит к сети хоста. В контейнере брокер слушает [listen] address = "container" (все интерфейсы контейнера: адрес в сети Compose заранее неизвестен), а границу наружу задаёт ports: в compose.yaml: порт 7443 публикуется явно, лучше на конкретный интерфейс хоста ("192.168.1.10:7443:7443"). Вне контейнера значение container отвергается, подстановочные адреса по-прежнему не допускаются.
  • Версия. Тег образа всегда явный; обновление — смена тега и docker compose up -d.

Архивы al-localrunner-<ос>-<арх>.tar.gz (linux-x64 и linux-arm64 (статические сборки musl, не зависят от версии glibc), macos-x64, macos-arm64; в корне архива localrunner) и al-localrunner-windows-x64.zip (localrunner.exe, localrunnerw.exe), рядом SHA256SUMS и SHA256SUMS.sig. Сеть pool с подсетью 172.30.57.0/24 (она же в [networks] примера policy.toml), порт брокера опубликован на 127.0.0.1:7443 — для других машин владелец меняет адрес на интерфейс хоста; у раннера hostname: runner. Вступление: docker compose up -d broker, docker compose exec broker localrunner broker add --runners 1 --address broker:7443, docker compose run --rm runner localrunner runner join broker:7443 код, затем docker compose up -d runner.

10.5 Обновление, удаление, перенос

  • Обновление. На машине с localrunner путь такой: install.sh --upgrade или install.ps1 --upgrade (подпись проверяется, как при установке): скачанный бинарник запускает localrunner upgrade, он сравнивает установленную и новую версии, показывает идущие джобы и ожидающие заказы и спрашивает (при идущих джобах: дождаться их, отменить через --cancel или отказаться; один --yes ждёт), сначала останавливает раннеры (drain или отмена), ждёт их, и только потом останавливает хаб и брокер, запущенный вручную (Ctrl+C во время ожидания ничего не заменяет и оставляет оба работать), копирует себя поверх установленного бинарника и запускает те же роли из него; более старый бинарник отклоняется, та же версия ничего не меняет, а если копирование не удалось, остановленные роли запускаются из старого бинарника. Служба брокера в ОС держит свою копию бинарника и обновляется вручную с правами администратора (остановить службу, заменить копию, запустить). Иначе: заменить бинарник или образ любым способом из 10.1 и перезапустить роль (down и up, перезапуск службы или контейнера). Перед заменой лучше остановить раннеры штатно (down работает как --drain): идущие джобы доделаются. Перезапуск брокера короче [grace] lost_min безопасен: джобы раннеров доживают, а таймеры считаются заново от первого heartbeat после старта. Совместимость по версии протокола (3.9). Схемы баз обновляются при старте автоматически с резервной копией; откат на более старую версию с более новой схемой не поддерживается и завершается понятным отказом.
  • Удаление. localrunner uninstall останавливает роли установки, как down --cancel: идущие джобы раннеров отменяются (кому нужен их итог, сначала вызывает down), выхода раннеров после отмены ждёт не дольше 30 с, затем останавливаются hub и брокер, запущенные вручную; брокер-служба снимается вместе со службой. Если какая-то роль не остановилась, uninstall ничего не удаляет, называет причину и возвращает 1. Затем uninstall выключает автозапуск, удаляет службу, бинарник и его каталог из PATH пользователя; ключи и история остаются. uninstall --purge после подтверждения удаляет и каталог состояния; ключ раннера на брокере он не отзывает, раннер остаётся offline до runner remove. Резервная копия схемы при миграции лежит рядом с базой (broker.db.bak-<версия>), хранится одна последняя.
  • Перенос брокера. Остановить службу, скопировать каталог состояния (broker.db, logs/, сертификат, policy.toml; machine-id не копируется: у новой машины своя установка и свой идентификатор) и поправить в policy.toml [listen] под адрес новой машины (адрес остаётся прежним, только если IP переехал вместе с брокером) на новую машину и запустить с тем же адресом: hub и раннеры, подключённые по сети, подключаются без повторного вступления, пока сертификат тот же; hub и раннеры старой машины, ходившие по IPC, теперь удалённые и вступают заново по коду. При смене адреса его нужно обновить в списке hub и в настройке раннеров.

12. Логирование и метрики

Диагностика самой системы идёт через фасад логирования, а куда она попадёт, решает владелец конфигурацией. По умолчанию это файл на диске; Grafana подключается необязательным получателем.

  • Фасад в коде. Роли пишут структурированные события в трейт LogSink, а метрики в трейт Meter (оба в lr-abstractions), и ничего не знают о получателях. Это аналог ILogger. Получатели, уровни и редактирование полей подключает один общий крейт (lr-obs), а не код ролей; роли от lr-obs не зависят, реализации им передаёт lr-cli. (Уточнение реализации: вместо крейта tracing фасадом служат свои трейты: так роли зависят только от контрактов, а заглушки для тестов уже есть.)
  • Что логируется. Диагностика hub, брокера и раннера: подключения и обрывы, приём и выдача заказов, сработавшие правила политики, перезагрузка политики, отказы, работа outbox, очистка хранилища. Вывод джоб сюда не входит: он хранится как данные запуска (раздел 8) и в получатели не уходит. (Решение пользователя: в Grafana идут диагностические логи и метрики.)
  • Поля события: время, уровень, роль (hub, broker, runner), компонент, MachineId, сообщение и по месту job_id, раннер, ярлык клиента, имя сработавшего правила. Не пишутся: команды и переменные окружения джоб, вывод джоб, ключи, коды подключения и токены. Список редактируемых полей задаётся конфигурацией.

otlpOpenTelemetry-совместимый приёмник (Grafana Alloy → Loki, Mimir)выключен по умолчанию; единственный сетевой получатель; TLS
  • Альтернатива без сетевого получателя: Grafana Alloy или Promtail читает JSON-файл на той же машине. Процессы системы при этом не делают исходящих соединений.
  • Получатель никогда не блокирует работу: запись асинхронная, буфер ограничен, при переполнении события отбрасываются, а потеря считается счётчиком. Недоступный приёмник не останавливает и не замедляет брокер, hub или раннер.
  • Библиотеки только под разрешёнными лицензиями. OTLP кодируется самим lr-obs (OTLP/HTTP JSON поверх rustls, Apache-2.0/MIT/ISC), без тяжёлого стека OpenTelemetry для Rust.

Уточнения реализации (lr-obs):

  • Ключи. Неизвестные ключи, виды получателей, уровни и сигналы отвергаются. Файл без [[sink]] означает файл по умолчанию. [redact] fields только дополняет встроенный список, ослабить его нельзя. Перезагрузка с ошибкой оставляет прежнюю конфигурацию; после остановки перезагрузка отвергается. Журнал, которого нет в ОС, — ошибка конфигурации.
  • Редактирование выполняется до любого получателя (получатели принимают только отредактированную запись). Маскируются (***): значения секретов, полученные раннером через SecretSource (обёртка RedactingSecrets), где бы они ни встретились; блоки PEM с PRIVATE KEY; коды подключения lrj1.…; учётные данные в URL; Bearer/Basic; значение после чувствительного имени и = или : в тексте, в том числе в экранированном JSON любой глубины ({\"token\":\"…\"}, {\\\"token\\\":…}): значение в кавычках до такой же закрывающей кавычки, вложенные {…}/[…] целиком, значение без кавычек после = до пробела или , ; & ) } ] " ', после : и у имён Authorization/auth — до конца строки (password: my pass phrase и password: ab,cd маскируются целиком) (token …, Digest …, Basic …); всё значение поля с чувствительным именем. Встроенные имена: token, key, password, passwd, secret, authorization, auth, cookie, credential, credentials, command, env, environment, join_code; совпадение по частям имени, которые делятся по _ - ., camelCase, аббревиатурам и смене буквы на цифру (api_token, X-Api-Key, privateKey, APIKey, token2 — да; exit_code, keyboard — нет). Кроме того, имя чувствительно, если без разделителей содержит одну из частей token, secret, passw, apikey, passphrase, pwd, credential, bearer, auth (PGPASSWORD, accesstoken, dbPwd, OAuthHeader). Ruling: из этого правила (и только из него) исключены ложные срабатывания tokens_used, author, authority, unauthorized, authenticated (список NOT_SENSITIVE, проверен тестами); встроенные имена и [redact] fields исключения не ослабляют (token_count маскируется по части token, настроенное authority маскируется); другие слова с этими частями маскируются — лишняя маска дешевле утечки. Зарегистрированные значения ищутся одним автоматом Aho-Corasick: protect только помечает его устаревшим, следующее редактирование перестраивает его вне блокировки, и редактирование, начатое после возврата protect, всегда видит новое значение. Перекрывающиеся совпадения объединяются по ходу поиска, без хвостов; больше 65 536 совпадений в одном тексте (вырожденный набор) — остаток текста маскируется. Пределы: сообщение 16 КиБ, значение поля 4 КиБ, имя поля 128 байт (к обрезанному имени добавляется #номер поля, чтобы длинные имена не слились), 64 поля; из повторяющихся имён в записи остаётся последнее значение; отброшенные поля (сверх 64 и повторы) считаются (Redactor::dropped_fields). До редактирования вход обрезается до предела плюс длина самого длинного зарегистрированного значения, и место обрезки сдвигается назад, пока не устоится, к началу рассечённого зарегистрированного значения и к началу рассечённого токена (токен кончается только пробельным символом: в userinfo URL допустимы , и ;): каждый шаблон судится по целому токену, поэтому учётные данные URL, Basic или пара «имя=значение» на границе выбрасываются целиком, а не выводятся префиксом. Текст, первый токен которого длиннее предела, становится одной пометкой ...[truncated]. После редактирования — обрезка до предела с пометкой ...[truncated]. Ограничения: незарегистрированный секрет без чувствительного имени рядом не распознаётся; значение без кавычек после = кончается на первом разделителе, поэтому у token=ab&cd остаётся &cd; значение в незакрытой кавычке маскируется до конца текста; значения короче 4 символов не регистрируются; закодированные формы (base64, URL) не ищутся; хранится до 4096 значений, старые забываются.
  • Строки. JSON-строка: time (RFC 3339 UTC, мс), level, role, component, machine_id, message, fields. Управляющие символы (C0, DEL, C1), bidi-символы и разделители U+2028/2029 экранируются в обоих форматах, поэтому поле не может подделать вторую запись или раскрасить терминал. В тексте сообщение всегда в кавычках, а значение — когда в нём пробел, ", =, \ или экранируемый символ; внутри кавычек \ и " экранируются, поэтому сообщение вроде job_id=evil не подделает поле. format = "text" пишет ту же строку, что консоль.
  • Ротация файла: перед строкой, с которой файл превысил бы rotate_mb МиБ, и через сутки после открытия активный файл переименовывается в daemon-YYYYMMDD-HHMMSS-mmm[-n].log (UTC). Удаляются повёрнутые файлы старше keep_days по времени в имени, затем лишние сверх keep_files (по умолчанию 10); другие файлы каталога не трогаются. Путь только относительный внутри каталога состояния, без .., диска и имён устройств Windows. В Unix каталоги создаются с правами 0700, файлы 0600; в Windows наследуется ACL каталога состояния. Ошибка ввода-вывода не роняет процесс: она считается, событие теряется и считается в log_dropped_total вместе со строками, которые оставались в буфере с последнего удачного сброса, файл открывается заново; отказ переименования повторяется через минуту. При перезагрузке прежний файл закрывается до открытия нового, поэтому на одном пути никогда нет двух писателей: замена, закрытие старых получателей и запуск новых потоков идут под одной блокировкой, которую берут и сброс, и остановка, а закрытый получатель больше не трогает свой писатель. События, записанные во время перезагрузки, ставятся в очередь того набора получателей, который текущий в момент постановки, поэтому в закрытую очередь они не попадают; поздние события в закрытой очереди считаются в log_dropped_total.
  • Буфер: у каждого получателя своя очередь до 10 000 событий и 8 МиБ; при переполнении отбрасываются самые старые. Запись идёт в рабочем потоке получателя, файл сбрасывается на диск раз в секунду и при остановке. Пока получатель не готов (пауза OTLP), поток спит по секунде и не просыпается от новых событий, поэтому пауза не загружает процессор. Если поток получателя не удалось запустить, это пишется событием error в остальные получатели и считается в ошибках; такой получатель доставляет только при явном сбросе.
  • OTLP: OTLP/HTTP JSON на <endpoint>/v1/logs и /v1/metrics, только https, TLS 1.3, сертификат приёмника проверяется по ca_file; учётные данные, запрос и фрагмент в endpoint запрещены, текст ошибки адрес не повторяет. Отдельной аутентификации нет: приёмник с аутентификацией ставится за локальным Alloy. Пачки до 512 событий; неудачная отправка теряет пачку (считается) и включает паузу 5 с с удвоением до 300 с. Метрики отправляются раз в 60 с, накопительно. timeout_s ограничивает подключение и каждую операцию чтения и записи.
  • Журнал ОС: syslog (его собирает journald) в Unix, Windows Event Log (журнал Application, источник Al.LocalRunner) в Windows; строка без времени. В Windows строка обрезается до 31 839 единиц UTF-16 (предел строки подстановки ReportEventW) с пометкой ...[truncated].

Уточнения реализации (lr-obs):

  • Метки по-английски: platform, pool, runner, reason, result, service, role, sink. У cache_used_mb только runner, у cache_evicted_total — runner и reason. saturation_wait_seconds — датчик (gauge); метрики без _total и без пометки «гистограмма» — датчики.
  • Допустимые значения: reason насыщения — runner_busy, memory, cpu, tag, rule; reason вытеснения — size, age; result заказов и длительности — passed, failed, timeout, cancelled, lost, rejected; result перезагрузки — ok, error; role — hub, broker, runner; sink — file, console, journal, otlp.
  • Принимаются только имена каталога и ровно их наборы меток; значение метки до 128 байт без управляющих символов; не больше 256 серий на метрику; отвергнутые обновления считаются. Серии исчезнувшего раннера, сервиса или пула удаляются вызовом Meter::forget(метка, значение), что освобождает место под пределом серий. Счётчики насыщаются, а не переполняются; датчик не принимает NaN и бесконечность, гистограмма — отрицательные значения.
  • Границы гистограмм, с: 1, 5, 15, 30, 60, 120, 300, 600, 1800, 3600, 7200, 14400. Единицы UCUM: s, MBy, {order} и т. п.
  • Метка client разрешена только при [metrics] client_label = true в logging.toml и только у queue_wait_seconds, orders_total, job_duration_seconds; при выключенной настройке она отбрасывается.

Уточнения реализации (роли):

  • Роли получают Meter через BrokerDeps, HubDeps, RunnerDeps; lr-cli передаёт реестр того же логгера, чей получатель otlp его публикует. Имена и ключи меток — константы lr_abstractions::metric; тест lr-obs сверяет их с каталогом.
  • Брокер. orders_total растёт при каждом конечном состоянии (passed, failed, timeout, cancelled, lost), в том числе когда брокер возвращает заказ «та же машина» без живого раннера (cancelled, код rejected_no_runner_on_machine), и при отказе на приёме (rejected); job_duration_seconds — от старта до конечного состояния, только у стартовавших. Ожидание считается по часам брокера, а не hub: queue_wait_seconds — от последней постановки в очередь (приём заказа, восстановление после перезапуска или возврат в очередь от пропавшего раннера) до выдачи раннеру; возвращённый в очередь заказ даёт второе наблюдение. platform — платформа заказа, same_machine у заказа без платформы, other, если платформу не объявляет ни один известный раннер (так текст отклонённого заказа не становится серией); метка фиксируется при выдаче раннеру, и результат джобы идёт с той же меткой. Датчики (queue_length, running_jobs, pool_memory_used_mb, pool_cpu_used, runner_online, saturation_wait_seconds) пересчитываются после каждого планирования и раз в секунду; pool — всегда default (у брокера один пул); runner_online = 1, пока у раннера есть соединение. saturation_wait_seconds{reason} — сколько с последней постановки в очередь ждёт самый давний заказ, который сейчас ждёт по этой причине, 0 без таких; runner_busy ← раннер занят, memory/cpu ← не хватает пула, tag ← занятый exclusive-тег, rule ← резерв или квота правила; ожидание offline-раннера, отсутствие раннера и резерв старта головы очереди насыщением не считаются. policy_reload_total считает и отказ чтения policy.toml. Удалённый раннер забывается (Meter::forget("runner", имя)).
  • Outbox. Каждая роль раз в 15 с и при старте берёт из хранилища число неподтверждённых записей и время самой старой (outbox_backlog, results_backlog у брокера — по всем клиентам, без чтения содержимого); возраст 0, когда записей нет.
  • Раннер. cache_used_mb — размер именованных кэшей (без зеркал рабочих деревьев) при каждом подсчёте ёмкости и после очистки; cache_evicted_total — удалённые очисткой именованные кэши: age — старше retention_days, size — вытеснены по max_size_gb; удаление зеркал рабочих деревьев сюда не входит. Метка runner — имя раннера.
  • Сервисы раннера (3.11). Ключи [service.*]: start и ready_check обязательны, stop необязателен (без него дерево сразу убивается); ready_timeout_s по умолчанию 60, stop_timeout_s (льготный срок после stop) — 10, restart (сколько раз сервис поднимается заново после сбоев) — 3, memory_mb — 0, lifetime — per_job, reuse — same_client; max_lifetime_s обязателен при любом lifetime, idle_timeout_s — при idle; неизвестный ключ — ошибка. Сервис с секретами (secrets = [...], значения из хранилища раннера) переиспользуется только тем же клиентом, какой бы reuse ни был задан; same_project — тот же проект при любом клиенте. start работает на переднем плане, пока сервис жив: жизнь сервиса — жизнь его корневого процесса, поэтому команда, которая запускает демон и завершается, не поддерживается (такой сервис при следующей выдаче считается упавшим). Окружение start, ready_check и stop — только PATH, HOME, TEMP раннера, рабочий каталог — services/<имя> в каталоге состояния; перед каждым новым экземпляром он очищается, чтобы следующий клиент не увидел файлов прежнего. Сервис стартует перед шагами джобы и записывается в реестр до проверки готовности; ready_check повторяется раз в секунду до кода 0 или до ready_timeout_s. Провал старта или готовности завершает джобу failed с service_failed и считается сбоем; упавший тёплый сервис обнаруживается при следующей выдаче и тоже считается сбоем. Сбой номер restart + 1 делает сервис недоступным до перезапуска раннера (возможности: unavailable). После джобы per_job-сервис и сервис, переживший max_lifetime_s, останавливаются до отправки результата; остальные остаются тёплыми и гасятся по простою или max_lifetime_s. Остановка: stop, ожидание конца процесса до stop_timeout_s, затем убийство всего дерева в любом случае. Команда брокера «остановить сервис» не трогает сервис, занятый джобой. При drain и отказе в авторизации раннер гасит все сервисы, включая уже останавливаемые таймером или брокером, и ждёт их ухода (не дольше самого длинного stop_timeout_s плюс 30 с) до Bye; heartbeat в это время идёт. Отчёт о сервисах уходит после welcome и при каждом изменении. Раннер объявляет memory_mb каждого сервиса в возможностях (необязательное поле service_mem_mb). Брокер вычитает из [pool] mem_mb (и при проверке правил резерва) память сервисов, которых раннеры отчитали как starting, idle, busy или stopping, и планирует заказ с сервисами с добавкой их объявленной памяти — наименьшей по раннерам, которые берут работу и предлагают все эти сервисы, без сервисов, уже живых на раннере (их переиспользование); если проход планирования ставит заказ на раннер, где его сервисы стоят больше и не помещаются в остаток пула или раннера, этот раннер исключается из прохода и проход повторяется. Добавка выданной джобы держится, пока раннер не отчитается о сервисе. Так память резервируется до старта сервиса и не удваивается при переиспользовании. На приёме заказ с сервисами проверяется с той же добавкой без учёта живых экземпляров (наименьшей по всем зарегистрированным раннерам, предлагающим сервисы): пул, резервы и квоты видят джобу плюс сервисы, каждый раннер — джобу плюс свои сервисы; заказ, который так не помещается никогда, получает rejected_pool_memory, rejected_quota или rejected_no_matching_runner с числами «джоба + сервисы», а не ждёт вечно. Квота max_mem_mb считает память сервисов, которые заказ запустит, и на приёме, и в очереди; память уже живых сервисов в квоту не входит. pool_memory_used_mb раннера включает его живые сервисы. Метрики: service_starts_total — каждая попытка старта, service_failures_total — каждый сбой, service_up — 1 после готовности, 0 после остановки; метка service — только имена из runner.toml, серии сервиса, которого больше нет в runner.toml, забываются при старте раннера только для этого раннера (Meter::forget_series по паре runner, service), одноимённый сервис другого раннера того же процесса свои серии сохраняет.
  • Ни одна роль не кладёт в метки JobId, проект, ветку, ярлык джобы, ключ или имя пользователя клиента, пути, команды и секреты.
  • Отзыв ключа. runner remove и client remove сначала отзывают ключ в реестре, затем движок разрывает соединения ключа. Ждущие заказы клиента получают cancelled с причиной client_removed (кто отменил — broker); выполняющиеся, в том числе выданные и не стартовавшие, при [orphans] running = "cancel" получают отмену раннеру с той же причиной, при "finish" доходят до итога; выданный и не стартовавший, который после потери раннера или рестарта брокера возвращается в очередь, вместо очереди получает cancelled с client_removed и другому раннеру не выдаётся. Hub отозванного ключа о client_removed и об итогах своих заказов не узнаёт: outbox ключа удалён, и ни одно сообщение о запусках, принятых до отзыва, в outbox больше не пишется (итоги видны только в истории брокера; hub закрывает такие заказы своим сроком outbox). Правило держится и после повторного вступления под тем же именем: новый hub получает только исходы заказов, принятых после вступления, а отменённые и завершённые при отзыве запуски ему не воспроизводятся. При старте брокер считает запуск принадлежащим отозванному ключу, если запись машины с именем его клиента отозвана или вступила позже, чем запуск принят; такие ждущие заказы отменяются с client_removed, выполняющиеся идут по [orphans] running, поэтому падение брокера между отзывом в реестре и командой движку не возвращает их в очередь. Заказы других клиентов не затрагиваются.
  • Хранение. Движок проверяет срок прохода хранения при каждой команде, включая тик; первый проход запускается при первой команде после старта, следующие — не чаще раза в 10 минут. Проход идёт вне задачи движка, не больше одного за раз; паника прохода снимает отметку «идёт», и следующий проход выполняется по расписанию: expire_results удаляет записи outbox старше [results] keep_hours, prune чистит логи и строки завершённых запусков по [history] (logs_max_gb в ГиБ); активные запуски не трогаются. Значения берутся из действующей политики на момент прохода, ошибка хранилища пишется в лог предупреждением и повторяется следующим проходом.
  • Миграция схемы. Перед миграцией любой базы (broker.db, hub.db, runner.db) на новую версию схемы файл копируется (VACUUM INTO) в <имя>.bak-<старая версия> рядом с ним, в Unix с правами 0600; копия той же версии от прошлой попытки заменяется, а после удачной копии копии других версий удаляются: хранится одна последняя (10.5). Копия делается, только когда миграция действительно пойдёт; если её не удалось сделать, миграция не начинается и открытие базы завершается ошибкой с путём копии.

13.2 Внутри брокера

Уточнения движка там, где разделы выше не задают поведение:

  • Клиент локального IPC получает ключ local:<пользователь ОС>; он же служит идентификатором его машины и ссылкой «та же машина» для его раннеров. Сетевой раннер ссылки «та же машина» не получает, что бы он ни сообщил о себе.
  • Соединение, молчащее 45 секунд (три пропущенных heartbeat по 15 секунд), брокер закрывает; раннер на таком соединении становится offline, невыданные ему заказы возвращаются в очередь.
  • Локальный раннер живёт только в памяти сессии брокера: строку раннера в broker.db пишет лишь раннер с ключом машины.
  • Отклонённый при приёме заказ в историю не пишется: hub получает отказ с причиной, и только.
  • Отказ в отмене (чужой или неизвестный заказ) отправитель получает сразу, как cancel_ack без записи в outbox: такой ответ не повторяется после переподключения, зато поток чужих JobId не наполняет outbox. Применённая отмена и отмена своего заказа идут через outbox.
  • Когда один JobId есть у нескольких клиентов, отмена владельцем брокера и запросы history show, explain, log принимают необязательный ключ клиента (client); без него берётся свой запуск, иначе единственный видимый, а при нескольких брокер отказывает и перечисляет клиентов.
  • Повтор заказа с уже принятым ключом и JobId отвечает тем же Accepted только при seq не больше принятого (обычно 1) и счётчик не двигает; заказ с большим seq отклоняется как malformed, чтобы не занять номер следующей отмены.
  • Сбой хранилища при приёме заказа или отмены брокер пишет в свой лог и отвечает ошибкой unavailable; hub повторяет позже.
  • Уровень «сводка» для чужих заказов показывает состояние, причину и код выхода, но скрывает проект, ярлык, профиль, причину ожидания и шаги; фильтр истории по скрытому полю такие заказы не находит. На уровне «скрыто» занятые теги раннера показываются без JobId.
  • Позиция в очереди в status считается по всей очереди в порядке политики, включая скрытые от читателя заказы.
  • Ссылка «та же машина» локального раннера (local:<пользователь ОС>) видна в списке раннеров и в ответе на опрос возможностей только самому этому клиенту и владельцу брокера.
  • Локальный раннер регистрируется под именем local:<имя>. Имя сетевого раннера двоеточия содержать не может, поэтому локальный раннер не займёт имя сетевого и не попадёт в историю под его именем.
  • Входящее соединение в режиме вступления отклоняется как unauthorized, пока в брокер не подключён реестр кодов вступления.
  • Очереди ограничены: команды соединений к движку ждут места в общей очереди (читатель соединения не читает дальше, пока движок не освободит место), у каждого соединения не больше 1024 исходящих кадров, а соединение, у которого очередь переполнилась, брокер закрывает как медленное и пишет об этом в свой лог. У одного соединения не больше 16 подписок на события; лишняя получает отказ. Досылка outbox после resume, ответы log и сообщения outbox, пришедшие во время досылки, идут к соединению порциями: в очереди соединения одновременно не больше 256 таких кадров, следующая порция уходит, когда очередь опустела наполовину; порядок сохраняется, а больше 100 000 ждущих кадров означают медленное соединение.
  • Когда приём соединений раз за разом завершается ошибкой, после трёх ошибок подряд брокер ждёт перед следующей попыткой: от 100 мс, удваивая паузу до 5 с.
  • log --step выбирает вывод шага по строкам-заголовкам === step <имя> ... ===, которые раннер пишет в начале шага, включая строку об отмене шага. log -f отдаёт сохранённый лог и дальше присылает новые чанки джобы, пока она не завершится (последняя порция с end); слежение занимает место подписки (вместе не больше 16 на соединение) и идёт порциями по тем же правилам, что досылка outbox; для завершённой джобы ответ — сохранённый лог целиком. Если лог идущей джобы (или выбранного шага) пока пуст, первой приходит пустая порция без end: слежение началось.
  • Запрос чтения unfollow с номером запроса слежения снимает это слежение своего соединения и освобождает место подписки (ответ unsubscribed, для чужого или неизвестного номера — not_found). Hub шлёт его, когда CLI ушёл до конца лога: одно соединение hub с брокером обслуживает всех его зрителей, и брошенное слежение иначе держало бы место до конца джобы. Брокер прежней минорной версии этого запроса не знает и отвечает как на неизвестный; слежение тогда живёт до конца джобы.
  • Фильтр истории mine (необязательное поле, по умолчанию false) просит только запуски спрашивающего: брокер подставляет ключ клиента соединения вместо поля client, поэтому CLI не нужно знать свой ключ. Видимость при этом не меняется: mine только сужает выборку.
  • Канал CLI к hub: лог (log, log -f) hub пересылает порциями log_chunk (имя брокера, текст, end) в порядке брокера, без общего таймаута запроса для слежения; отказ брокера приходит обычным ответом чтения, разрыв соединения с брокером или отставание потока — ошибкой unavailable. Запрос shutdown (ответ stopping) останавливает hub, административная команда shutdown — брокера; брокер, запущенный менеджером служб ОС, не останавливается и отвечает предупреждением. Обе существуют только на локальном IPC. Запросы чтения subscribe, unsubscribe и unfollow hub от CLI не пересылает (отказ malformed): подписками и слежениями на своих соединениях с брокерами управляет только он сам, поэтому один процесс не снимет чужое слежение и не займёт места подписок. Слежение, которое отстало (CLI не успевает читать и очередь потока hub переполнилась), заканчивается ошибкой unavailable, и hub снимает его у брокера тем же unfollow.
  • Поток событий для дашборда: на каждом соединении с брокером hub первым делом подписывается на темы очереди и раннеров (одно из мест подписок соединения) и кладёт их события в свою шину. Каждое событие брокер уже замаскировал по видимости для ключа этого hub. Запрос CLI events отвечает watching и затем пересылает события шины ответами event (имя брокера и событие), пока соединение открыто. Повторный events на том же соединении снова отвечает watching, второго потока не открывает. Событие unknown значит, что события могли потеряться и состояние надо перечитать. Hub шлёт его от имени брокера, когда соединение с этим брокером пропало или восстановилось, и от имени hub, когда соединение CLI отстало от шины. Hub прежней минорной версии запрос events не знает и молча пропускает. Если watching не пришёл за 5 с, дашборд переходит на тики обновления раз в 2 с.
  • Сроки брокер проверяет при каждом событии и раз в секунду. Выполняющаяся джоба получает lost (причина runner_lost) ровно в момент Started + timeout_s + [grace] lost_min по часам брокера, даже если соединение раннера живо; так же завершается джоба в cancelling. Если запись в broker.db при lost, возврате в очередь или отмене ждущего заказа не удалась, брокер пишет ошибку в свой лог, держит запуск у себя и повторяет запись раз в секунду; заказ при этом никому не выдаётся. Так же повторяется запись старта джобы: started подтверждается раннеру сразу, время старта — время отчёта, повторный started той же джобы ничего не меняет. Пока старт не записан, отмена записывается в запуск без смены состояния, а lost и итог раннера ждут: сначала пишется старт (и cancelling, если джобу отменили), потом итог, ровно один раз. Повторяются только сбои самого хранилища; отказ хранилища по состоянию запуска пишется в лог ошибкой и не повторяется. Перезапуск брокера во время того же сбоя может выполнить джобу дважды: незаписанный старт не виден после перезапуска, и запуск возвращается в очередь. Первая неудача пишется в лог по запуску, каждый следующий неудачный круг повторов — одной строкой с числом ждущих записей. Отмена запуска, ждущего повторного возврата в очередь, принимается (applied), записывается в запуск и закрывает его после удачного возврата; запуск, ждущий записи lost или отмены, отмену подтверждает и завершается своим путём. Отмена ждущего, ещё не выданного заказа, запись которой не удалась, живёт только в памяти: перезапуск брокера во время сбоя хранилища возвращает такой заказ в очередь неотменённым.
  • При старте брокер читает из broker.db раннеры (как offline; память и CPU раннера в строке не хранятся, поэтому до его возвращения его ёмкостью считается бюджет пула, а зона — remote) и активные запуски не больше 100 000: ждущие встают в очередь, выданные и не стартовавшие держатся за своим раннером льготный срок [grace] lost_min от старта брокера и только потом возвращаются в очередь (подробнее в разделе о причинах завершения), стартовавшие ждут отчёта раннера до срока lost. Отмена выданного, но не стартовавшего заказа (своя, владельца или hub_absent) записывается в запуск сразу (кто и почему, без смены состояния), поэтому после перезапуска такой заказ сразу получает cancelled и никому не выдаётся; если джоба всё же завершилась passed, failed или timeout, не побывав в cancelling, записанная отмена снимается. Адрес сетевого клиента восстановленного заказа уточняется при подключении его hub.
  • Заказ «та же машина», у установки которого не осталось раннера на связи (последний ушёл, пропал или в drain), брокер возвращает hub сообщением returned с причиной rejected_no_runner_on_machine, а в истории запуск получает cancelled с той же причиной. После перезапуска брокер ждёт возвращения раннеров один льготный срок [grace] lost_min и только потом возвращает такие заказы.
  • После drain раннер не получает новых заказов и при приёме считается offline (обычный заказ ждёт, заказ «та же машина» отклоняется); строка раннера — draining до Bye или нового подключения.
  • Срок absent_after_min идёт, пока у клиента нет соединения, от его последнего сообщения (после перезапуска брокера — от старта). queued = "cancel" отменяет ждущие заказы с причиной hub_absent, running = "cancel" шлёт раннерам отмену с той же причиной.
  • Секреты и сервисы проверяются при приёме по ярлыку клиента до проверки раннеров: первый недопущенный секрет даёт rejected_secret_not_allowed («секрет X не разрешён ярлыку Y»), сервис — rejected_service_not_allowed. Для клиента с [commands] mode = "named" команда каждого шага — название: заказ без шагов и заказ с названием, которого нет ни у одного известного брокеру раннера, отклоняются с rejected_command_not_allowed (в причине — первое такое название и названия раннеров). Принятый заказ несёт названия в требованиях (commands), поэтому подходит только раннеру, объявившему их все, и решение не пересматривается при policy reload; в Assign такому заказу ставится named_commands. Названия, присланные в заказе другого клиента, брокер отбрасывает. Названия, которые есть у разных раннеров по отдельности, но ни у одного все сразу, дают при приёме rejected_no_matching_runner с причинами по раннерам («команда X не описана»), как и другие требования к одному раннеру. Названия раннера в broker.db не хранятся: после перезапуска брокера они известны, когда раннер снова на связи, а до того заказ такого клиента отклоняется с причиной «раннеры ещё не вернулись после перезапуска брокера, повторите» (если раннеров с названиями нет и брокер не перезапускался — «раннеры этого брокера названий не сообщают»). Принятые заказы хранят названия в broker.db и после перезапуска остаются в режиме named.
  • capabilities_update заменяет возможности раннера целиком (ссылку «та же машина» назначает брокер) и сразу действует при приёме и выдаче. Отчёт о сервисах виден в списке раннеров; если голова очереди ждёт памяти (сервис CPU в бюджете не держит, поэтому нехватка CPU вытеснения не вызывает) и evict_idle включён, брокер один раз шлёт stop_service каждому простаивающему сервису раннеров на связи, не разбирая, подходит ли раннер голове очереди (событие service_changed шлётся только при смене состояния или памяти сервиса, не при отсчёте remaining_s). Память живых и назначенных сервисов планировщик держит в бюджете пула (3.11).
  • Служба брокера при старте отклоняет address = "container" вне контейнера.
  • Сообщение раннера о джобе, которая ему не выдана или уже завершена, брокер подтверждает, не применяет и пишет в свой лог.

13.3 Внутри hub

  • IPC-сервер принимает команды CLI; разбор профилей читает профиль из рабочего дерева или коммита и собирает заказ.
  • Клиент брокеров держит соединения с известными брокерами, выбирает брокера по hub-policy.toml, стримит вывод и результат обратно.
  • Reaper следит за процессом-отправителем и при его гибели отменяет заказы.
  • Хранилище hub.db (outbox, активные заказы, список брокеров) и копия логов в каталоге отправителя; шина событий питает SSE дашборда и wait; HTTP дашборда на loopback.

Уточнения hub там, где разделы выше не задают поведение:

  • Активный заказ хранит в active_order.spec_json заказ, как он был подан: после перезапуска hub возвращённый (returned) заказ снова предлагается другим брокерам с seq 1, а заказ «та же машина» завершается с подсказкой. hub_meta хранит наибольшее выданное время JobId (job_id_floor): после перезапуска JobId выдаются выше него, даже если часы ушли назад. Схема hub.db версии 2; файл версии 1 переводится миграцией.
  • Заказ, чья запись в hub.db не читается (испорченный JSON в outbox, или нет ни брокера, ни сохранённого заказа), завершается сразу отказом rejected_order_unreadable, при старте hub или при досылке. Восстановленная джоба с ждущей отменой в outbox считается отменённой: reaper и повторный cancel второй отмены не ставят; повторный cancel той же джобы отвечает её JobId и ничего не ставит.
  • Подтверждения брокера (accepted, ack, resume, cancel_ack) применяются не дальше наибольшего seq, реально отправленного этому брокеру по этой джобе. Не удавшаяся запись выбора брокера переводит заказ в ожидание с повтором через query_retry_s. Если после отказа брокера в допустимых зонах заказа брокеров не осталось, заказ получает причину последнего отказа, а не rejected_zone_not_served. Файл-хэндл пишется после записи заказа в outbox. cancel_ack denied вне outbox приходит с seq = 0 и в поток seq не входит.
  • Канал CLI принимается только по локальному IPC (PeerAccess::Local); пользователь ОС берётся из того, что сообщает ОС о собеседнике, и заменяет os_user в присланной идентичности. Сетевой собеседник получает refused (unauthorized).
  • Файл-хэндл temp/runner/<job-id>.json и копию лога пишет hub (он знает JobId и путь, active_order.handle_path). Каталог отправителя (cwd, worktree_root) должен быть абсолютным (в Windows — с буквой диска) и без . и .., JobId — из букв, цифр и дефиса, иначе заказ отклоняется ошибкой malformed. JobId hub выдаёт из своего времени в миллисекундах и счётчика.
  • Сразу, без JobId, отклоняются: ошибка профиля или флагов (error malformed, в том числе --timeout больше таймаута профиля и --mem или --cpu, равные нулю), незапушенный коммит заказа на платформу (rejected_commit_not_pushed), заказ «та же машина» без настроенного локального брокера (rejected_no_local_broker). Остальные отказы приходят после JobId: тому, кто ждёт (--wait), и в копию лога.
  • done принимается только на том соединении, где выдан JobId этой джобы, и ответа не имеет; иначе — ошибка. Reaper следит за каждой джобой без --detach независимо от done. wait на завершённую джобу отвечает её итогом, пока он в памяти (последние 1024 итога), иначе ошибкой; закрытие соединения wait ничего не отменяет.
  • Брокер без сообщённой зоны считается remote, локальный брокер — всегда local. Подходящими считаются только раннеры на связи; least_loaded выбирает брокера с наибольшим числом подходящих раннеров, при равенстве — раньшего по [brokers] order. Если ни один допустимый брокер не ответил, заказ ждёт в outbox и выбор повторяется через query_retry_s и при каждом подключении брокера.
  • Отклонённый (rejected) или возвращённый (returned) обычный заказ hub предлагает остальным брокерам; оба потока seq заказа начинаются заново с 1 (HubStore::rebroker); время постановки у нового брокера — момент его приёма по его часам (3.5), очередь у прежнего брокера не переносится. Если брокеров не осталось, заказ отклоняется с причиной последнего отказа. Заказ «та же машина» после отказа или возврата завершается отказом с подсказкой запустить localrunner up. Отказ локального брокера принять пользователя ОС (unauthorized) отклоняет ждущие заказы «та же машина» с rejected_local_user_unknown.
  • Сообщения брокера, который не держит этот заказ, hub подтверждает и не применяет. Повтор seq подтверждается снова; пропуск seq — ошибка seq_gap, соединение закрывается и устанавливается заново. После подключения hub шлёт resume с последним принятым seq по каждой джобе брокера и досылает свой outbox.
  • Отмена до выбора брокера завершает заказ на месте (cancelled). Отмена отправленного, но не принятого заказа убирает запись заказа из outbox и ставит отмену; отказ в ней (cancel_ack denied без seq) завершает заказ на месте. Отмена принятого заказа ждёт в outbox подтверждения, итог приходит от брокера. Чужой ярлык отменяется только с --force, кто и почему — в копии лога.
  • Срок [outbox] ttl_hours отсчитывается от записи заказа в outbox; при on_expire = "fail" заказ без accepted завершается rejected_outbox_expired без отправки отмены. Reaper проверяет отправителей при старте hub и раз в 5 с; неизвестный ответ (время старта не получить) не считается смертью, о нём пишется одно предупреждение.
  • Очереди ограничены: к одному брокеру не больше 1024 кадров (переполнение досылки откладывает остаток до следующей секунды, переполнение при подтверждении закрывает соединение), к одному соединению CLI — 256 ответов; медленный наблюдатель wait отключается (hub закрывает его соединение, CLI видит конец потока), полный вывод остаётся в копии лога; итог, вытесненный из последних 1024, забывается. Каждое такое переполнение пишется в диагностический лог hub с накопленным по его виду счётчиком (поле total). Переподключение к брокеру — с паузой от 1 с, удваивая до 30 с.
  • Команда CLI jobs (--mine) отвечает по активным джобам hub того же пользователя ОС и ярлыка, без --active — ещё и по итогам в памяти. Реальная реализация Repository (git) — в lr-cli.

13.4 Внутри раннера

Уточнения агента раннера там, где разделы выше не задают поведение:

  • Каждое сообщение о джобе (started, чанк, результат шага, итог) сначала пишется в outbox runner.db со следующим seq джобы и только потом отправляется; новое соединение после hello, welcome, resume и отчёта о сервисах заново шлёт все неподтверждённые записи по порядку. ack брокера снимает записи до своего seq, resume брокера — до указанного. Ошибка брокера seq_gap закрывает соединение: переподключение досылает всё с первого неподтверждённого. Записи started и итога при сбое хранилища повторяются раз в секунду, чанк и результат шага пишутся в лог ошибкой и отбрасываются; итог отказа в назначении пишется одной попыткой (при сбое — ошибка в логе), чтобы не останавливать сеанс. Запись outbox, которую не удаётся прочесть, заменяется чанком без шага с тем же seq («[localrunner: stored message N is unreadable]») и ошибкой в логе: дыры в seq не бывает. Каждая отправка ограничена тремя интервалами heartbeat: брокер, переставший читать, закрывается и получает переподключение.
  • Входящие assign и cancel проходят строгую проверку seq по джобе: повтор подтверждается и отбрасывается, пропуск получает ошибку seq_gap. Джобу, которую раннер уже выполнял, выполняет или о которой ещё держит результаты, он не запускает повторно, даже если брокер выдал её снова (после перезапуска): назначение подтверждается, а outbox досылает прежние результаты. Назначение, пришедшее во время другой джобы или после drain, завершается failed с текстом («runner is busy with job X», «runner is draining»), как и джоба с таймаутом выше потолка раннера («job timeout 7200 s is above the runner ceiling 3600 s»).
  • Соединение: heartbeat с интервалом из welcome (15 секунд, приводится к 1–3600 секундам); брокер, молчащий три интервала, считается пропавшим. Переподключение с паузой от 1 секунды с удвоением до 30. Срок убийства джобы при недоступном брокере берётся из welcome и settings_update (по умолчанию 180 секунд, не больше суток) и отсчитывается от обрыва сеанса, прошедшего welcome, — независимо от того, сколько длятся попытки соединения и ожидание welcome; [grace] broker_lost_kill_s в runner.toml его только сокращает. Убитая так джоба получает cancelled с причиной broker_unavailable; отказ в авторизации (unauthorized, key_revoked) убивает дерево сразу, удаляет outbox и останавливает агента.
  • Раннер помечает выполняемую джобу файлом active-job в каталоге состояния до подтверждения назначения; если метку записать не удалось, джоба не запускается и завершается failed («active job marker not written: …»); если при старте метка осталась, а итога в outbox нет, он отправляет failed с причиной runner_restarted и джобу не перезапускает. При старте раннер также убивает осиротевшие сервисы из реестра (только при совпадении pid и времени старта; без времени старта или при неизвестной жизни процесса — предупреждение без убийства). Из реестра сервис уходит только убитым или уже завершившимся, иначе запись остаётся; так же ведёт себя stop_service., забывает завершённые джобы старше суток и чистит кэш.
  • Шаг source. Для рабочего дерева — только рабочий каталог джобы, ничего не запускается; несуществующий каталог даёт failed. Для коммита адрес репозитория и ветка приходят в коде заказа (code.repo_url, code.branch, необязательные поля, совместимые с прежней версией); без адреса джоба падает. Каталог проекта {workspace} = <состояние>/workspace/<проект>-<хеш проекта и адреса> (у другого адреса — своё зеркало), зеркало — {workspace}/mirror.git, рабочая копия джобы {job_dir} = {workspace}/jobs/<джоба>-<хеш клиента и джобы>. mkdir раннер делает сам, затем шаги git clone --mirror -- <адрес> <зеркало> (только без зеркала), git -C <зеркало> fetch --prune -- origin, git -C <зеркало> worktree prune, git -C <зеркало> worktree add --detach -- <job_dir> <коммит> в каталоге проекта; затем шаги профиля в {job_dir}. Шаги по умолчанию не входят в нумерацию шагов заказа: их вывод идёт чанками без шага, провал даёт failed с текстом «source step failed: <имя>», а шаги профиля — skipped. Ведущие шаги заказа с именем source заменяют эту последовательность: это обычные шаги заказа (со своими результатами), они идут в каталоге проекта, а раннер подставляет в них {repo_url}, {commit}, {branch}, {workspace} и {job_dir}. Рабочая копия удаляется по окончании джобы, зеркало подчиняется [workspace] (запись в индексе кэша).
  • Безопасность команд source. Значения проверяются до подстановки: адрес — схемы https, http, ssh, git, file или форма user@host:path, только символы [A-Za-z0-9._~:/@+=,-], не длиннее 2048, без ведущего -, без :: (помощники удалённых репозиториев вроде ext::) и без хоста, начинающегося с -; коммит — 7–64 шестнадцатеричных знака; ветка — правила ссылок git на [A-Za-z0-9._/-]. Адрес, ветка и пути берутся в двойные кавычки; аргумент с ", $, `, %, !, ^, управляющими символами или завершающей обратной косой отвергается, а не экранируется; перед позиционными аргументами git стоит --.
  • Окружение и секреты. Окружение джобы: PATH (только [env] path в runner.toml; PATH процесса раннера джоба не наследует; [env] path обязателен: без него раннер не стартует, как при ошибке mem_mb и cpu («runner.toml has no [env] path: jobs get PATH only from it (spec 13.4); set [env] path»); init и runner join без шаблона пишут его со значением PATH оболочки, из которой запущены; второй рубеж — джоба, назначенная раннеру без PATH, завершается failed до запуска («runner.toml has no [env] path, so the job would get no PATH; set [env] path (spec 13.4)»); [programs] ищутся в том же [env] path), HOME, TEMP (а также TMP и TMPDIR; все три указывают на личный каталог джобы <каталог состояния>/tmp/lr-<job-id>), LOCALRUNNER_JOB_ID и LOCALRUNNER_CACHE_<ИМЯ>; на Windows к ним добавляются переменные, без которых не работает сама ОС (Winsock, CryptoAPI, поиск программ): SystemRoot, windir, ComSpec и PATHEXT со значениями из окружения раннера. Другие переменные джоб задаются в [job_env] как ИМЯ = "значение" (JAVA_HOME, CARGO_HOME); HOME, записанный там, заменяет определённое значение; PATH (для него есть [env] path), TEMP, TMP, TMPDIR и имена на LOCALRUNNER_ отклоняются при чтении runner.toml. Механизм для переменных один, поэтому в [env] только path; переменная под [env] попадает в предупреждение о неизвестном ключе. Проверки [programs] идут ровно в окружении джобы (с каталогом временных файлов процесса раннера вместо личного), каждая занимает до check_timeout_s секунд (по умолчанию 10), а раннер без нужной переменной программу не предлагает. У профиля нет поля env, и он не может потребовать переменную: окружение раннера принадлежит его владельцу, который задаёт его в runner.toml (init и runner join без шаблона записывают HOME своей оболочки в [job_env]; если в файле его нет, он берётся у пользователя ОС, от которого запущен процесс раннера). Брокер выбирает раннер только по programs, platforms, tags и ресурсам, поэтому различие между раннерами (например, JAVA_HOME, который есть не у всех) владелец объявляет программой с check или тегом. Это свойство ОС, а не потребителя; остальное окружение раннера джоба не наследует. Секрет передаётся переменной с именем секрета в верхнем регистре (не буквы и цифры — _): registry_auth → REGISTRY_AUTH. Секрет, названный шагом, получает только этот шаг; допущенный секрет, который не назвал ни один шаг, запрошен профилем и виден всем шагам. Секрет, чья переменная совпала бы с PATH, HOME, TEMP, TMP или начиналась бы с LOCALRUNNER_ (имя приводится к верхнему регистру, поэтому сравнение не зависит от регистра), завершает джобу failed до запуска («secret X would replace the reserved variable Y»). Шагам профиля после source достаётся остаток таймаута джобы, округлённый вверх до секунды.
  • Кэш. Каталог кэша — <состояние>/cache/<хеш ключа клиента>/<проект>/<имя> (части — безопасные имена с хешем). При [cache] share = "project" брокер шлёт в Assign вместо ключа клиента общий cache_client = "shared:project" (не похожий ни на ed25519:, ни на local:), и каталог у всех клиентов, заявивших этот проект, один (проект заявляет клиент, см. 3.5 и предупреждение policy check); ключ клиента остаётся в рабочем каталоге и переиспользовании сервисов. Политика берётся в момент выдачи, без поля раннер ведёт кэш по клиенту. Без max_size_gb и retention_days ограничений нет; evict знает только lru. Очистка — при старте, перед каждой джобой и раз в час, в том числе во время джобы; кэши и зеркало текущей джобы не удаляются (джоба занимает их до очистки, очистки и занятие идут по очереди). После джобы раннер обновляет размер и время использования и шлёт capabilities_update с заполнением кэша.
  • Диск. После очистки кэша перед джобой раннер сверяет disk_mb заказа со свободным местом тома (рабочего дерева — для рабочего дерева, каталога состояния — для коммита) за вычетом резервов других раннеров установки: каждый держит файл <раннер>.mb («МБ pid время-старта» своего процесса) в disk-reservations/ каталога состояния установки, пока идёт его джоба, а при старте убирает свой оставшийся файл. Раннер сначала записывает свой резерв, потом складывает чужие и при нехватке снимает свой: два раннера, решающие одновременно, могут оба отказать, но не займут одно место вдвоём. Резерв, чей процесс по pid и времени старта мёртв, не считается и удаляется; нечитаемый резерв считается занявшим всё место (отказ с его именем, ёмкость 0). Резервы считаются без различия томов. Не хватает места — джоба не ждёт, а завершается failed с кодом причины disk_insufficient и текстом «not enough disk: the job needs N MB, M MB are free on <путь> after the cache cleanup (K MB reserved by other runners)», шаги — skipped; том, который не удалось измерить, не проверяется (предупреждение в логе). Ёмкость раннера disk_mb — свободное место тома каталога состояния в момент отчёта за вычетом чужих резервов (если измерить нельзя — значение при старте).
  • Лимиты и очистка. Перед стартом раннер собирает лимиты джобы из [resources] брокера (приходят с назначением) и своего [limits], резервирует диск с запасом и передаёт лимиты исполнителю (lr-exec). После завершения джобы он запускает подходящие хуки [[cleanup]], каждый как короткую джобу в каталоге состояния, с окружением джобы, LOCALRUNNER_JOB_LABEL и переменными [job_env]. Вывод хука идёт в лог джобы под заголовком cleanup <имя>. Подробности — в 3.14.
  • Запрет сна (раздел 10) держится, пока выполняется джоба, и снимается по её окончании: в Windows отдельный поток держит SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED), в macOS работает /usr/bin/caffeinate -i -w <pid раннера>, в Linux ничего не делается. Завершение процесса раннера снимает запрет само.
  • Названия команд. Раннер объявляет в возможностях названия [commands] (поле commands). Назначение с named_commands раннер до метки active-job переводит в свои строки; название без описания — результат failed с кодом rejected_command_not_allowed, ни один шаг не запускается, все шаги получают skipped. Строки подставляются до шага source, поэтому его подстановки действуют и в строке раннера.

14. Данные

Одна база SQLite на сторону. У брокера broker.db: история запусков на его раннерах (с клиентом), реестр машин, раннеры, очередь заказов. У hub hub.db: outbox (заказы без Accepted и отмены), активные заказы и список брокеров. У раннера runner.db: outbox, реестр сервисов (для поиска сирот) и индекс кэша. Внутри broker.db связи — обычные внешние ключи; между hub.db и broker.db они логические, по JobId. Пулы и лимиты — в policy.toml, а не в базе. Полные логи — файлы в logs/<job-id>.log брокера.

  • Финальное состояние джобы пишется один раз: повторная доставка результата или второе конечное состояние не меняют строку. Для выполнявшейся джобы его определяет только отчёт раннера; отмена ждущего заказа снимает его сразу.
  • Запись запуска остаётся на брокере в пределах хранения. Hub хранит только outbox и копию лога: запись из outbox удаляется по Accepted брокера, а брокер не знает, что лежит в outbox hub.
  • Хранение истории на брокере: 30 дней и 2 ГБ логов, 365 дней строк по умолчанию (политика); чистка идёт с самых старых и не трогает активные джобы.
  • Схема broker.db — версии 2: в job добавлены peak_mem_mb и peak_disk_mb, в runner — enforcement. Старый файл переносится при первом запуске, копия остаётся как broker.db.bak-1. В выводе history перед BROKER появились два столбца, поэтому скрипты, читающие его по номеру столбца, нужно поправить. Дополнения протокола (лимиты в назначении, пики в результате, нагрузка машины в heartbeat, enforcement в возможностях) — необязательные поля: старые участники продолжают работать, версия протокола не изменилась.
  • order хранит только очередь до выдачи; состояние запуска ведёт job.state, и после выдачи строка заказа удаляется.
  • Принятый seq хранится рядом с тем, что он нумерует: у брокера в job.recv_seq_hub и job.recv_seq_runner (исходящий к раннеру — job.send_seq_runner; при повторной постановке в очередь счётчики раннера обнуляются), у hub в active_order.last_seq, у раннера в runner_recv (по строке на джобу; чистится вместе с завершёнными джобами по сроку хранения). Подтверждённая запись outbox не удаляется, а закрывается (acked_at), и остаётся закрытая запись с наибольшим seq джобы: следующий seq всегда на единицу больше, даже если очередь пуста.
  • В machine хранятся только публичные ключи и ярлыки клиентов; токен регистрации ci-раннера не пишется никуда.

15.5 Вступление и ключ

Причины завершения. Каждый финал и каждый отказ несёт код причины, видимый в history, explain и на дашборде: runner_stopped (раннер остановлен командой down --cancel), runner_removed (раннер удалён), broker_unavailable (брокер не вернулся за льготный срок, джоба прервана), runner_lost (раннер пропал, срок вышел), client_removed (ключ клиента отозван), sender_gone (reaper отменил заказ мёртвого отправителя), hub_absent (hub отсутствовал дольше absent_after_min), service_failed, secret_missing, runner_restarted (раннер перезапущен при живой джобе, результат failed), cancelled_by_user, disk_insufficient (раннеру не хватило свободного места под disk_mb джобы даже после очистки кэша, результат failed), resource_exceeded (раннер завершил джобу за превышение заявленного mem_mb или disk_mb в режиме kill, результат failed, текст превышен заявленный mem_mb: заявлено X МБ, пик Y МБ), rejected_* (отказ при приёме с названием причины, например rejected_pool_memory — профиль просит больше памяти, чем есть в пуле, или rejected_override_above_pool — больше пула просит значение --mem или --cpu этого запуска). Выданный раннеру, но не стартовавший заказ при потере раннера возвращается в очередь: сразу, если раннер ещё не подтвердил выдачу (ack на assign); подтверждённая выдача держится за этим раннером льготный срок [grace] lost_min от потери связи (столько же раннер сам ждёт брокер, прежде чем убить свою джобу) и возвращается в очередь, только если раннер за этот срок не вернулся с started, итогом или resume, где названа эта джоба (hello без сведений о джобе срок не снимает; resume без неё значит, что раннер её не получал, и выдача возвращается в очередь сразу), так что одна выдача не исполняется двумя раннерами одновременно. После рестарта брокера выданная, но не начатая джоба держится за своим раннером тот же срок от старта брокера (подтверждение выдачи не хранится, поэтому считается подтверждённой). Остаётся окно: если связь рвётся, когда ack раннера ещё в пути, выдача возвращается в очередь сразу и может исполниться дважды; позднее сообщение о джобе, уже получившей конечное состояние, не меняет его и пишется в лог. Джоба в cancelling на раннере, который пропал, завершается через lost.

Остальные сущности просты и описаны таблицей выше: шаг повторяет состояния джобы, заказ после выдачи становится джобой, связь hub с брокером бывает доступна или недоступна.

16. Сценарии

Сценарии использования по ролям в виде диаграмм последовательности. Сплошная стрелка — сообщение, пунктирная — ответ, блок с рамкой — ветка отказа или условие. Участник «Пользователь» — человек или сессия агента.

Установка и доступ

16.1 Первый запуск на одной машине

Роли: владелец машины. Команда up поднимает три роли отдельными процессами; все связаны по локальному IPC.

16.2 Вступление раннера на другой машине

Роли: владелец. Раннер сам подключается к брокеру: входящие порты на его машине не нужны. Адрес брокера владелец вводит вручную; срок кода задаёт [join] code_ttl_min (по умолчанию 1 час).

16.3 Вступление hub клиентской машины

Роли: владелец, пользователь. Hub вступает как клиент со своим ключом; ярлык (например, ci) владелец задаёт при выдаче кода. Hub на машине брокера кода не требует.

16.4 Отзыв ключа и удаление раннера

Роли: владелец. Каждый участник имеет свой ключ, поэтому отзыв точечный.

16.5 Служба брокера на выделенной машине

Роли: владелец. Брокер ничего не исполняет, поэтому работает как служба ОС под отдельной учётной записью и не зависит от того, кто вошёл в систему.

16.6 Несколько раннеров на одной машине

Роли: владелец. Параллельность — это несколько раннеров: один код на N вступлений, у каждого раннера свой ключ, имя и каталог состояния.

16.7 Несколько пользователей ОС на одном брокере

Роли: владелец, пользователи. Пул один, брокер один. Hub и раннеры пользователей подключаются к службе по локальному IPC; «та же машина» работает только внутри одного пользователя ОС.

16.8 Ноутбук меняет сеть

Роли: hub. Зону hub определяет брокер по адресу подключения, сверяя его с [networks]; пользователь ничего не вводит. Мобильная сеть — это remote.

16.9 Docker Compose: брокер и раннер в контейнерах

Роли: владелец. Состояние лежит в томах: пересоздание контейнеров повторного вступления не требует.

16.10 Обновление, удаление и перенос узла

Роли: владелец. Обновление заменяет бинарник, схемы баз мигрируют сами. Удаление по умолчанию сохраняет ключи и историю.

Выполнение

16.11 Запуск на той же машине (рабочее дерево)

Роли: пользователь, агент. Профиль читается из рабочего дерева, раннер работает в каталоге отправителя. Заказ никогда не уходит в сеть.

16.12 Удалённый запуск коммита на другой платформе

Роли: пользователь, агент. Раннер другой установки работает с запушенным коммитом. Платформа в команде одна; вторая платформа — вторая джоба отдельной командой.

16.13 Выбор брокера и отказ «нет подходящего раннера»

Роли: hub. Граница зоны заказа жёсткая: заказ «та же машина» не уходит в сеть, заказ с зоной lan не уходит на remote.

16.14 Ожидание в очереди: приоритеты и заполнение дыр

Роли: брокер. Порядок решает политика; мелкий заказ обходит тяжёлый, только если не задержит его зарезервированный старт, который вычислен по таймаутам идущих джоб.

16.15 Джоба с сервисом, кэшем и секретом

Роли: раннер, брокер. Сервис стартует только в составе заказа после резервирования ресурсов; окружение джобы строится с нуля.

16.16 Запуск из GitHub Actions

Роли: ci. ci-раннер GitHub ресурсов не берёт: его джоба ставит обычный заказ через hub своей машины с ярлыком ci.

Отмена и сбои

16.17 Отмена джобы

Роли: пользователь, агент. Проверку метки и пользователя ОС делает hub; брокер разрешает отмену только заказов того же ключа.

16.18 Мёртвый отправитель

Роли: hub (reaper). Отправитель — процесс, вызвавший CLI. Джоба с --detach переживает его.

16.19 Обрыв связи hub и возвращение

Роли: hub. Заказ принадлежит ключу hub, а не соединению: короткий обрыв (сон ноутбука, смена сети) ничего не отменяет.

16.20 Падение и возвращение брокера

Роли: брокер. Заказы без Accepted ждут в outbox hub, принятые хранятся на брокере, результаты раннера ждут в его outbox.

16.21 Потеря раннера и таймаут джобы

Роли: брокер, раннер. Брокер сам освобождает ресурсы потерянной джобы; срок потери раннер получает при регистрации.

Управление и просмотр

16.22 Смена политики

Роли: владелец. Правит только тот, кто сидит за машиной брокера; ошибка оставляет прежнюю политику.

16.23 Просмотр состояния и дашборд

Роли: пользователь, агент. Дашборд только дополнение: всё, что на нём, есть в CLI с --json.

16.24 Остановка раннера

Роли: владелец. Два способа: доделать текущую джобу или отменить её.

16.25 Автозапуск по ролям

Роли: владелец. Необязателен и независим от ручного up. Брокер ставится службой ОС, hub и раннеры работают под пользователем.

18. Вне рамок

  • Телефоны и физические устройства по USB/ADB. Джобы android и ios идут на эмуляторе или симуляторе, который предоставляет машина раннера.
  • NAT-обход и туннели: брокер вне локальной сети должен иметь доступный адрес.
  • Отправка джоб, правка профилей и конфигурации, запуск и остановка раннеров с веб-страницы (на ней только отмена).
  • Удалённая правка политики и упаковка коммита через брокера.
  • Любое знание о конкретной команде или инструментах потребителя внутри ядра.
  • Лимиты дискового ввода-вывода, привязка джобы к ядрам, приостановка выполняющихся джоб, прокси Docker-сокета и дисковые квоты ОС (отдельный том, VHD, tmpfs); ядро не знает контейнеров и демонов сборки, очистка — команда, написанная владельцем (3.14).
