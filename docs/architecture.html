Al.LocalRunner — архитектура

Очередь запусков тестов и сборок на нескольких машинах. Документ описывает, как система устроена: окружение, компоненты, данные и потоки. Источники: docs/design.md (что должно быть) и docs/superpowers/plans/2026-11-09-localrunner.md (как строится).

Глоссарий

Все термины определены здесь один раз. Подчёркнутое точками слово в тексте и на схемах показывает определение из этого раздела при наведении мыши или фокусе с клавиатуры; отдельной копии текста определений нет.

Узлы и роли

Компьютер
Физическая машина. На ней может стоять несколько установок: те, что работают одновременно (основная ОС, Docker, виртуалки), образуют один пул, а взаимоисключающие (двойная загрузка) — разные пулы.
Установка
Один экземпляр программы со своим каталогом состояния, MachineId и ключами: основная ОС, контейнер Docker или виртуалка. Один компьютер может нести несколько установок.
MachineId
Случайный идентификатор установки. Создаётся один раз при первом запуске демона и хранится в файле machine-id. По нему определяется, чья это джоба и кто вправе её отменить.
Hub (хаб)
Роль клиентской стороны: превращает профили проекта в заказы, отправляет их брокерам, ведёт историю, логи и дашборд и следит за процессом-отправителем. Джобы не исполняет и очереди ресурсов не держит. Стоит на машине пользователя; у каждой клиентской машины свой hub.
Брокер пула
Роль, один на пул: показывает, какие раннеры с какими характеристиками есть в пуле, принимает заказы, держит их очередь и раздаёт раннерам по политике. Отдаёт API: приём заказов и чтение состояния. Про hub не знает: клиент для него — любое аутентифицированное соединение.
Заказ
Просьба выполнить джобу: требования к раннеру (платформа, уровень, теги, ресурсы), коммит и команды, желаемый приоритет. Приоритет в заказе — только пожелание, порядок решает политика. Живёт, пока открыто соединение клиента; после обрыва и льготного окна отменяется.
Политика
Правила владельца в policy.toml на брокере: порядок выдачи, веса и квоты групп, резерв ресурсов, допуск клиентов, выбор раннера, окна ожидания, хранение. Код содержит только механизм и встроенные стратегии; неизвестное правило — отказ при загрузке, ошибка перезагрузки оставляет прежнюю политику.
Раннер
Роль и отдельный процесс: подключается к брокеру, исполняет выданные им джобы и возвращает результаты и логи. На одной установке может работать несколько раннеров, например light и heavy.
Клиент
Клиентская машина: на ней стоят только hub и сессии агентов, джобы она не исполняет. Для брокера её соединение — обычный клиент с ярлыком, который владелец задал при выдаче ключа.
Демон
Фоновый процесс al-localrunner на установке, который держит роль hub или брокера. Запускается командой up.
ci-раннер
Настоящий self-hosted раннер GitHub Actions с меткой al-ci. Перед запуском берёт ресурсы у брокера (acquire), чтобы не пересекаться с локальными прогонами. Не путать с нашим раннером.
Дашборд
Страница в браузере: очередь, история, живой лог, статистика, раннеры. Слушает только 127.0.0.1 своей машины. Раннеры, нагрузку и очередь берёт из API брокеров, историю запусков — у своего hub.

Очередь и ресурсы

Джоб
Один запуск профиля: очередь, шаги, результат. Имеет JobId; джобы одной команды по нескольким платформам образуют группу с GroupId.
Профиль
Описание запуска в .localrunner/profiles.toml проекта: уровень, команда или шаги, таймаут, память, CPU, теги. Это требования джобы, а не настройки машины.
Уровень
Метка, которая говорит, какие джобы принимает раннер и с каким приоритетом. По умолчанию light, heavy и ci. Владелец определяет уровни в levels.toml вместе с требованиями к машине.
ci
Уровень по умолчанию с наивысшим приоритетом (100). Его джобы берутся первыми, но уже работающие джобы не вытесняют.
Приоритет
Порядок выдачи решает политика, а не код: приоритет из заказа и уровня — лишь входные данные для правил. Политика по умолчанию: строгий приоритет по уровню, внутри приоритета порядок постановки, джоба старше 30 минут поднимается до высшего приоритета.
Пул
Набор установок, которые работают одновременно и делят общий бюджет: лимиты памяти и CPU и набор exclusive-тегов. Лимиты задаёт владелец в политике брокера, а не проект; брокер у пула один. На одном компьютере может быть несколько пулов, если они взаимоисключающие (двойная загрузка): у каждого лимиты всего компьютера.
Воркер
Сколько джоб раннер выполняет одновременно. Параллельность ограничена дважды: воркерами раннера и лимитами пула; действует более строгое.
Платформа
Непрозрачная метка владельца (macos, ios, android...). Ядро только сравнивает метки на равенство. Если в профиле несколько платформ, на каждую создаётся своя джоба.
Тег
Ресурс, который джоба удерживает на время прогона (gradle, emulator). Теги раннера означают заявленные им возможности.
exclusive
Тег, который одновременно не может держать никто другой. Действует внутри пула.
Зона
Расстояние от отправителя до раннера: local, lan или remote. Среди подходящих раннеров по умолчанию предпочитается ближайший (это правило политики), но занятый ближайший не блокирует свободный дальний.
Аренда (acquire)
Захват ресурсов ci-раннером у брокера перед запуском GitHub-джобы. Освобождается, когда раннер завершился или связь оборвалась.
Отправитель
Процесс, вызвавший CLI (родитель al-localrunner), вместе с меткой --as и MachineId. По нему определяется право отмены и правило мёртвого отправителя.
Мёртвый отправитель
Когда процесс-отправитель завершился, его ожидающие джобы снимаются, а выполняющиеся убиваются. Флаг --detach отключает правило для идущей джобы.

Связь

Код подключения
Одноразовый код (живёт 1 час), который выдаёт брокер, чтобы раннер или hub вступил. После вступления машина использует собственную пару ключей.
network
Метка сети машины, по ней считается зона lan. Брокер выводит её из адреса подключения, владелец может задать вручную.
Heartbeat
Сигнал живости раннера каждые 15 секунд. После трёх пропусков раннер считается offline.
IPC
Локальный канал между CLI, демоном и раннером на одной установке: именованный канал в Windows, Unix-сокет в других ОС. Доступ только у пользователя ОС.
TLS
Шифрованное соединение раннера или hub с брокером по сети. Сертификат брокера закреплён отпечатком, который входит в код подключения.

1. Принципы

  • Универсальное ядро. Очередь, планировщик и демон не знают про язык, тестовый фреймворк и платформы. Названия платформ, метки и команды приходят от владельца машины и из профилей проекта.
  • Роли разделены. Hub — клиент: превращает профили в заказы, ведёт историю и дашборд, джобы не исполняет и очереди ресурсов не держит. Брокер пула знает только свои раннеры и заказы и ничего не знает о hub. Раннер исполняет и не решает, что запускать. Интерфейсов два: протокол раннера (раннер ↔ брокер) и API брокера (заказы и чтение; hub ↔ брокер).
  • Решает политика. Порядок выдачи, квоты, допуск, выбор раннера, окна ожидания и хранение — правила владельца в policy.toml на брокере. В коде только механизм и проверки безопасности (протокол, ключи, изоляция процессов).
  • Один бинарник, три роли. al-localrunner работает как hub (профили, история, дашборд), брокер (раннеры, очередь заказов, политика) и раннер (выполняет джобы). На одной машине up запускает все три отдельными процессами.
  • Раннер сам подключается к брокеру, как у GitHub self-hosted: входящие порты на раннере не нужны.
  • Ресурсы считаются по пулу — набору установок, которые работают одновременно и делят бюджет, а не по раннеру. Docker и виртуалки остаются отдельными установками со своим ID, но входят в пул хоста; у пула один брокер. Взаимоисключающие установки (двойная загрузка) — разные пулы на одном компьютере.
  • Локальный раннер тестирует рабочее дерево, удалённый — запушенный коммит.
  • Ничего не уходит наружу. Дашборд слушает только loopback; телеметрии и загрузок нет.

2. Архитектура: машины и связи

Этап 1 — всё в одной локальной сети. Раннеры на VPS и за чужим роутером — следующий этап; схема им не мешает.

Синие линии — постоянные соединения с брокером: заказы идут вниз, состояние и результаты вверх (по IPC на своей машине, по сети через общую шину TLS). Серые — IPC и HTTP на loopback между сессиями, браузером и hub. Пунктирные рамки — компьютеры; рамка внутри — установка со своим ID. Точечные синие рамки — пулы: у каждого пула один брокер, установки внутри рамки делят ресурсы, два пула на одном компьютере взаимоисключающие. Зелёные — раннеры. Брокер ничего не знает о hub: для него hub — клиентское соединение; какому брокеру отправить заказ, hub решает по своей политике (платформа, доступность).

Что где работает

  • Запуск джобов с любого компьютера. У каждой клиентской машины свой hub. Сессии агентов говорят с ним по IPC, а он отправляет заказы нужным брокерам. Очередь заказов живёт на брокере пула, порядок выдачи решает его политика.
  • Дашборд с любого компьютера. Дашборд слушает loopback своего hub и собирает вид сам: раннеры, нагрузку и очередь — из API брокеров, историю запусков — из истории hub. Если брокер недоступен, на дашборде видно, что его данные устарели.
  • Переключение между Windows и Mac. У каждой клиентской машины свой hub, а брокеры стоят на компьютерах пулов. Выключили ноутбук — пропали только его заказы; остальные клиенты и пул работают.
  • Несколько раннеров на одной ОС. На Windows и на Linux работают по два отдельных процесса: раннер light и раннер heavy. У каждого своё имя, уровни, воркеры и регистрация на брокере; пул общий, память и CPU считаются вместе.
  • Один компьютер — несколько установок. Windows, Docker и виртуалка на компьютере 1 — три установки с тремя ID, один пул и один брокер.
  • Разные ОС. Платформа раннера — метка владельца (windows, linux, macos, ios, android); ядро сравнивает метки на равенство.

Ключевые решения

  • Hub выбирает пользователь; на каждой клиентской машине он свой. Брокеры стоят на компьютерах пулов; hub видит брокеры, ключи к которым получил. На одной машине up запускает hub, брокер и раннер.
  • Брокер выдаёт заказ подходящему раннеру: по уровню, платформе, меткам и ресурсам; среди подходящих по умолчанию ближайшему по зоне (local, lan, remote). Всё это правила политики.
  • Приоритет решает политика. По умолчанию ci идёт первым без вытеснения запущенных, а заказ без ci, ждущий больше 30 минут, упорядочивается как ci.
  • Заказ живёт, пока открыто соединение hub. После обрыва брокер держит его льготное окно и затем отменяет; уже запущенная джоба доживает, а результат ждёт переподключения.
  • Если брокер пропал на 10 минут, раннер убивает свои запущенные джобы; результаты завершённых хранит и отдаёт позже. Срок и действие — политика.

4. Данные

Две базы SQLite. history.db есть на каждой машине и хранит джобы, выполненные на ней. hub.db есть только у hub и хранит реестр машин, пулы, раннеры, очередь и аренды. Связи между базами логические, по идентификаторам: внешних ключей между файлами нет. Полные логи лежат файлами в logs/<job-id>.log.

  • Финальное состояние джоба пишется один раз: повторная доставка результата или второе конечное состояние не меняют строку.
  • Удалённый джоб записывается в history.db машины раннера; hub держит только queue_entry до старта и аренды lease.
  • Хранение: логи 30 дней и 2 ГБ, строки 365 дней; чистка идёт с самых старых и не трогает активные джобы.
  • В machine хранятся только публичные ключи; токен регистрации ci-раннера не пишется никуда.

6. Потоки

Локальный запуск

  1. CLI собирает идентичность (--as, пользователь ОС, ветка, проект) и читает профиль из рабочего дерева.
  2. По IPC уходит Submit; движок отклоняет джоб, который не поместится в пул, и ограничивает таймаут сверху.
  3. pick_next выбирает локальный раннер; планировщик выдаёт память, процессор и метки пула.
  4. run_job выполняет шаги в каталоге отправителя; вывод идёт в лог, в temp/runner/<id>.log и в шину событий.
  5. Результат пишется в history.db; ресурсы освобождаются только после того, как дерево процессов мертво.

Удалённый запуск на другой платформе

  1. CLI проверяет, что HEAD запушен (иначе просит закоммитить и запушить ветку без MR), читает профиль из коммита.
  2. На каждую платформу создаётся джоб в одной группе; команды берутся из platform.<имя>.
  3. pick_next отбирает раннеры по уровню, платформе, меткам и ресурсам пула, затем выбирает ближайшую зону.
  4. Hub шлёт Assign по TLS-каналу; раннер делает git fetch и чистый отсоединённый checkout.
  5. Раннер стримит Chunk с номером seq и пишет итог у себя; hub подтверждает Ack и ретранслирует вывод CLI и дашборду.
  6. После обрыва связи раннер повторяет неподтверждённое из Outbox; hub отбрасывает дубликаты по seq.
