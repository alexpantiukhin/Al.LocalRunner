Al.LocalRunner — архитектура и проектирование

Очередь запусков тестов и сборок на нескольких машинах. Это единственный документ проектирования: архитектура, требования, формат конфигурации и безопасность. Отдельных Markdown-описаний нет; план реализации — docs/superpowers/plans/2026-11-09-localrunner.md. Слева — содержание.

Глоссарий

Все термины определены здесь один раз. Подчёркнутое точками слово в тексте и на схемах показывает определение из этого раздела при наведении мыши или фокусе с клавиатуры; отдельной копии текста определений нет.

Узлы и роли

Компьютер
Физическая машина. На ней может стоять несколько установок: те, что работают одновременно (основная ОС, Docker, виртуалки), образуют один пул, а взаимоисключающие (двойная загрузка) — разные пулы.
Установка
Один экземпляр программы со своим каталогом состояния, MachineId и ключами: основная ОС, контейнер Docker или виртуалка. Один компьютер может нести несколько установок.
MachineId
Случайный идентификатор установки. Создаётся один раз при первом запуске демона и хранится в файле machine-id. По нему определяется, чья это джоба и кто вправе её отменить.
Hub (хаб)
Роль клиентской стороны: превращает профили проекта в заказы, отправляет их брокерам, ведёт outbox заказов, копию логов и дашборд и следит за процессом-отправителем. Джобы не исполняет и очереди ресурсов не держит. Стоит на машине пользователя; у каждой клиентской машины свой hub.
Брокер пула
Роль, один на пул: показывает, какие раннеры с какими характеристиками есть в пуле, принимает заказы, держит их очередь и раздаёт раннерам по политике. Отдаёт API: приём заказов и чтение состояния. Хранит историю запусков на своих раннерах и для каждого запуска записывает, с какого клиента он пришёл. В коде про hub ничего не знает: клиент для него — любое аутентифицированное соединение.
Заказ
Просьба выполнить джобу: требования к раннеру (платформа, уровень, теги, ресурсы), коммит и команды, желаемый приоритет. Приоритет в заказе — только пожелание, порядок решает политика. Живёт, пока открыто соединение клиента; после обрыва и льготного окна отменяется.
Политика
Правила владельца в policy.toml на брокере: порядок выдачи, веса и квоты групп, резерв ресурсов, допуск клиентов, выбор раннера, окна ожидания, хранение. Код содержит только механизм и встроенные стратегии; неизвестное правило — отказ при загрузке, ошибка перезагрузки оставляет прежнюю политику.
Раннер
Роль и отдельный процесс: подключается к брокеру, исполняет выданные им джобы и возвращает результаты и логи. На одной установке может работать несколько раннеров, например light и heavy.
Клиент
Клиентская машина: на ней стоят только hub и сессии агентов, джобы она не исполняет. Для брокера её соединение — обычный клиент с ярлыком, который владелец задал при выдаче ключа.
Демон
Фоновый процесс al-localrunner на установке, который держит роль hub или брокера. Запускается командой up.
ci-раннер
Настоящий self-hosted раннер GitHub Actions с меткой al-ci. Перед запуском берёт ресурсы у брокера (acquire), чтобы не пересекаться с локальными прогонами. Не путать с нашим раннером.
Дашборд
Страница в браузере: очередь, история, живой лог, статистика, раннеры. Слушает только 127.0.0.1 своей машины. Раннеры, нагрузку и очередь берёт из API брокеров, историю запусков — тоже из API брокеров.

Очередь и ресурсы

Джоб
Один запуск профиля: очередь, шаги, результат. Имеет JobId; джобы одной команды по нескольким платформам образуют группу с GroupId.
Профиль
Описание запуска в .localrunner/profiles.toml проекта: уровень, команда или шаги, таймаут, память, CPU, теги. Это требования джобы, а не настройки машины.
Уровень
Метка, которая говорит, какие джобы принимает раннер и с каким приоритетом. По умолчанию light, heavy и ci. Владелец определяет уровни в levels.toml вместе с требованиями к машине.
ci
Уровень по умолчанию с наивысшим приоритетом (100). Его джобы берутся первыми, но уже работающие джобы не вытесняют.
Приоритет
Порядок выдачи решает политика, а не код: приоритет из заказа и уровня — лишь входные данные для правил. Политика по умолчанию: строгий приоритет по уровню, внутри приоритета порядок постановки, джоба старше 30 минут поднимается до высшего приоритета.
Пул
Набор установок, которые работают одновременно и делят общий бюджет: лимиты памяти и CPU и набор exclusive-тегов. Лимиты задаёт владелец в политике брокера, а не проект; брокер у пула один. На одном компьютере может быть несколько пулов, если они взаимоисключающие (двойная загрузка): у каждого лимиты всего компьютера.
Воркер
Сколько джоб раннер выполняет одновременно. Параллельность ограничена дважды: воркерами раннера и лимитами пула; действует более строгое.
Платформа
Непрозрачная метка владельца (macos, ios, android...). Ядро только сравнивает метки на равенство. Если в профиле несколько платформ, на каждую создаётся своя джоба.
Тег
Ресурс, который джоба удерживает на время прогона (gradle, emulator). Теги раннера означают заявленные им возможности.
exclusive
Тег, который одновременно не может держать никто другой. Действует внутри пула.
Зона
Расстояние от отправителя до раннера: local, lan или remote. Среди подходящих раннеров по умолчанию предпочитается ближайший (это правило политики), но занятый ближайший не блокирует свободный дальний.
Аренда (acquire)
Захват ресурсов ci-раннером у брокера перед запуском GitHub-джобы. Освобождается, когда раннер завершился или связь оборвалась.
Отправитель
Процесс, вызвавший CLI (родитель al-localrunner), вместе с меткой --as и MachineId. По нему определяется право отмены и правило мёртвого отправителя.
Мёртвый отправитель
Когда процесс-отправитель завершился, его ожидающие джобы снимаются, а выполняющиеся убиваются. Флаг --detach отключает правило для идущей джобы.

Связь

Код подключения
Одноразовый код (живёт 1 час), который выдаёт брокер, чтобы раннер или hub вступил. После вступления машина использует собственную пару ключей.
network
Метка сети машины, по ней считается зона lan. Брокер выводит её из адреса подключения, владелец может задать вручную.
Heartbeat
Сигнал живости раннера каждые 15 секунд. После трёх пропусков раннер считается offline.
Outbox
Постоянная очередь исходящих сообщений на hub, брокере и раннере: заказы, отмены, вывод и результаты записываются на диск до подтверждения получателем и повторяются после обрыва; получатель отбрасывает дубликаты по идентификатору и номеру seq.
Получатель (sink)
Место, куда уходят события логирования и метрики: файл на диске (по умолчанию), консоль, журнал ОС или OTLP-приёмник вроде Grafana Alloy. Задаётся в logging.toml; сетевой получатель выключен, пока владелец его не включил.
Кэш раннера
Именованные каталоги, которые раннер хранит между запусками проекта и отдаёт джобе путём в переменной окружения. Размер и срок хранения задаёт владелец раннера в runner.toml; когда места не хватает, удаляются самые давно использованные. Ядро не знает, что в них лежит.
IPC
Локальный канал между CLI, демоном и раннером на одной установке: именованный канал в Windows, Unix-сокет в других ОС. Доступ только у пользователя ОС.
TLS
Шифрованное соединение раннера или hub с брокером по сети. Сертификат брокера закреплён отпечатком, который входит в код подключения.

1. Цели и принципы

  • Цели. Параллельные сессии агентов ставят запуски в очередь, а не перегружают машину. У каждого запуска обязательный таймаут; по истечении или отмене убивается всё дерево процессов. Ядро универсальное, потребитель поставляет профили.
  • Универсальное ядро. Очередь, планировщик и роли не знают про язык, тестовый фреймворк и платформы. Названия платформ, метки и команды приходят от владельца машины и из профилей проекта.
  • Роли разделены. Hub — клиент: превращает профили в заказы, ведёт outbox заказов и дашборд, джобы не исполняет и очереди ресурсов не держит. Брокер пула знает свои раннеры, заказы и историю запусков на них; о hub он ничего не знает в коде (логика не различает потребителей), а в данных записывает, с какого клиента пришёл каждый запуск. Раннер исполняет и не решает, что запускать. Интерфейсов два: протокол раннера (раннер ↔ брокер) и API брокера (заказы и чтение; hub ↔ брокер).
  • Решает политика. Порядок выдачи, квоты, допуск, выбор раннера, окна ожидания и хранение — правила владельца в policy.toml на брокере (и в hub-policy.toml у hub для выбора брокера). В коде только механизм и проверки безопасности (протокол, ключи, изоляция процессов).
  • Один бинарник, три роли. al-localrunner работает как hub (профили, outbox заказов, дашборд), брокер (раннеры, очередь заказов, история запусков, политика) и раннер (выполняет джобы). На одной машине up запускает все три отдельными процессами. Одна машина с этим набором — вариант по умолчанию, остальное включается по желанию.
  • Раннер сам подключается к брокеру, как у GitHub self-hosted: входящие порты на раннере не нужны.
  • Ресурсы считаются по пулу — набору установок, которые работают одновременно и делят бюджет, а не по раннеру. Docker и виртуалки остаются отдельными установками со своим ID, но входят в пул хоста; у пула один брокер. Взаимоисключающие установки (двойная загрузка) — разные пулы на одном компьютере.
  • Hub и брокеры — «многие ко многим». У каждого hub свой список брокеров, брокер не знает, сколько hub его используют.
  • Рабочее дерево — раннеру той же машины, коммит — удалённому.
  • Ничего не уходит наружу. Дашборд слушает только loopback; телеметрии и загрузок нет. Единственное исключение — сетевой получатель логов и метрик (OTLP), который владелец включает сам и явно.

2. Архитектура: машины и связи

Этап 1 — всё в одной локальной сети. Раннеры на VPS и за чужим роутером — следующий этап; схема им не мешает.

Синие линии — постоянные соединения с брокером: заказы идут вниз, состояние и результаты вверх (по IPC на своей машине, по сети через общую шину TLS). Серые — IPC и HTTP на loopback между сессиями, браузером и hub. Пунктирные рамки — компьютеры; рамка внутри — установка со своим ID. Точечные синие рамки — пулы: у каждого пула один брокер, установки внутри рамки делят ресурсы, два пула на одном компьютере взаимоисключающие. Зелёные — раннеры. Брокер не знает о hub в коде: для него hub — клиентское соединение, но в историю он записывает, с какого клиента пришёл запуск; у каждого hub свой список брокеров, который ему выдал владелец: разные hub могут знать разных брокеров или одних и тех же (на схеме у hub компьютера 1 нет mac-mini, у ноутбука есть все три). Какому из известных брокеров отправить заказ, hub решает по своей политике (платформа, доступность).

Что где работает

  • Запуск джобов с любого компьютера. У каждой клиентской машины свой hub. Сессии агентов говорят с ним по IPC, а он отправляет заказы нужным брокерам. Очередь заказов живёт на брокере пула, порядок выдачи решает его политика.
  • Дашборд с любого компьютера. Дашборд слушает loopback своего hub и собирает вид сам: раннеры, нагрузку, очередь и историю запусков — из API брокеров; заказы, которые брокер ещё не принял, hub держит в своём outbox. Если брокер недоступен, на дашборде видно, что его данные устарели.
  • Переключение между Windows и Mac. У каждой клиентской машины свой hub, а брокеры стоят на компьютерах пулов. Выключили ноутбук — пропали только его заказы; остальные клиенты и пул работают.
  • Несколько раннеров на одной ОС. На Windows и на Linux работают по два отдельных процесса: раннер light и раннер heavy. У каждого своё имя, уровни, воркеры и регистрация на брокере; пул общий, память и CPU считаются вместе.
  • Один компьютер — несколько установок. Windows, Docker и виртуалка на компьютере 1 — три установки с тремя ID, один пул и один брокер.
  • Разные ОС. Платформа раннера — метка владельца (windows, linux, macos, ios, android); ядро сравнивает метки на равенство.

Ключевые решения

  • Hub выбирает пользователь; на каждой клиентской машине он свой. Брокеры стоят на компьютерах пулов; hub видит брокеры, ключи к которым получил. На одной машине up запускает hub, брокер и раннер.
  • Hub и брокеры связаны «многие ко многим»: у каждого hub свой список брокеров (ключ и адрес на каждого), и брокер не знает, сколько hub его используют. Общий пул делят все hub, знающие его брокера; бюджет считает один брокер, поэтому раннер не перегружается, как бы много hub ни слали заказы.
  • Брокер выдаёт заказ подходящему раннеру: по уровню, платформе, меткам и ресурсам; среди подходящих по умолчанию ближайшему по зоне (local, lan, remote). Всё это правила политики.
  • Приоритет решает политика. По умолчанию ci идёт первым без вытеснения запущенных, а заказ без ci, ждущий больше 30 минут, упорядочивается как ci.
  • Заказ живёт, пока открыто соединение hub. После обрыва брокер держит его льготное окно и затем отменяет; уже запущенная джоба доживает, а результат ждёт переподключения.
  • Если брокер пропал на 10 минут, раннер убивает свои запущенные джобы; результаты завершённых хранит и отдаёт позже. Срок и действие — политика.

3. Роли и взаимодействие

Три роли — hub, брокер пула, раннер — и два интерфейса между ними. Всё, что можно решить политикой, решается политикой.

3.1 Hub

  • Живёт на клиентской машине, по одному на машину. Принимает команды CLI по IPC, читает профиль, превращает его в заказ и отправляет брокеру. Хранит outbox: исходящие заказы и отмены записываются на диск до подтверждения брокером и повторяются после обрыва; пока запуск активен, помнит его процесс-отправитель. Ведёт копию логов в каталоге отправителя, дашборд, проверку отправителя и право отмены.
  • Не исполняет джобы, не держит очередь ресурсов и не знает раннеров. Раннеры, нагрузку, очередь и историю он читает из API брокеров.
  • Выбор брокера. Зону каждого брокера hub знает с момента вступления: local (брокер на той же машине, MachineId совпадает), lan (метки network равны) или remote. Для каждого заказа hub действует так:
    1. Оставляет только брокеров, чья зона допустима заказу. Заказ с требованием «та же машина» (рабочее дерево) рассматривает только local и никогда не уходит в сеть: шаг 3 к нему не применяется, политикой это не отключается. Если локального брокера нет или он недоступен, заказ ждёт или отклоняется с причиной, а не переезжает на другую машину и не подменяется коммитом; заказ с ограничением zone = "lan" — local и lan и никогда не уходит на remote. Граница заказа — жёсткий инвариант, а не предпочтение: переход к следующей зоне (шаг 3) разрешён только внутри допустимых зон, и политикой границу расширить нельзя. Остальных брокеров он не опрашивает вовсе.
    2. Опрашивает брокеров первой зоны по порядку (параллельно, с коротким таймаутом из hub-policy.toml): раннеры, платформы, уровни, теги, потолки таймаута, online/offline. Данные не кэшируются, решение принимается по свежим сведениям.
    3. Если среди них есть подходящие, выбирает по политике и дальше не ходит. Если нет, переходит к следующей допустимой зоне. Порядок зон задаёт hub-policy.toml (zone_order): по умолчанию от ближней к дальней (["local", "lan", "remote"]), но можно и обратный (["remote", "lan", "local"], например чтобы разгрузить свою машину), или любой другой. Политика может также потребовать опрашивать все допустимые зоны сразу. Порядок меняет только очерёдность внутри допустимых зон; границу заказа он не расширяет.
    Брокер, не ответивший за таймаут, на этот выбор считается недоступным. Данные могут устареть между запросом и приёмом заказа, поэтому окончательно допустимость проверяет брокер, в том числе границу зоны (раннер за пределами допустимой зоны относительно клиента он заказу не выдаст): если он отклонил заказ, hub пробует следующего по политике. Если не ответил ни один допустимый брокер, заказ ждёт в outbox с причиной «брокеры недоступны», и выбор повторяется при появлении связи. (Решение пользователя.)
  • У hub свой список брокеров: адрес и ключ на каждого, выданные владельцем при вступлении. Разные hub могут знать разных брокеров или одних и тех же. Если подходят несколько брокеров, выбор делает политика hub: файл hub-policy.toml в каталоге состояния (список и порядок брокеров, стратегия выбора). По умолчанию «первый в списке, остальные запасные». (Решение пользователя.)
  • Outbox. Заказ и отмена сначала записываются в постоянную очередь hub и доставляются брокеру с повтором, пока не придёт подтверждение; получатель отбрасывает дубликаты по идентификатору заказа и номеру seq. Так заказ переживает недоступность брокера и перезапуск hub. Срок ожидания в outbox и действие по его истечении — правила hub-policy.toml; по умолчанию заказ ждёт, пока жив процесс-отправитель.
  • Заказ связан с соединением hub: пока соединение открыто, заказ живёт. Что будет при обрыве, определяет политика брокера (по умолчанию: подождать 5 минут, ждущие отменить, выполняющуюся дать закончить, результат ждёт переподключения).

3.2 Брокер пула

  • Один на пул. Знает только раннеры своего пула: имя, платформы, уровни, теги, ресурсы, нагрузку, состояние. Принимает заказы, держит очередь заказов, выдаёт их раннерам по политике и следит за бюджетом пула. Хранит outbox для каждого клиента: чанки вывода, результаты, подтверждения отмен — до подтверждения получателем. Хранит историю запусков на своих раннерах: запись на джобу и шаг, полные логи, и для каждого запуска — клиент (ключ, MachineId, ярлык). (Решение пользователя.)
  • В коде про hub не знает: логика не различает потребителей, не ветвится по ним и не требует от клиента ничего, кроме ключа. В данных клиент записывается как поле. Клиент для него — аутентифицированное соединение с ключом и ярлыком, который владелец задал при выдаче ключа. Ярлык и MachineId брокер берёт из записи ключа, а не из заказа, поэтому подписаться чужой машиной или чужим ярлыком нельзя.
  • Отдаёт API двух видов: приём заказов (создать, отменить, получать вывод и результат) и чтение состояния и истории (раннеры с характеристиками, нагрузка пула, очередь, выполняющиеся заказы, история запусков, логи, статистика). Чужие заказы, запуски и логи клиенту показываются без подробностей (команды, ветки, каталоги скрыты); что и от кого скрывать, задаёт политика. (Решение пользователя.)
  • По умолчанию на одной машине up запускает hub, брокер и раннер отдельными процессами одного бинарника, связанными по локальному каналу.
  • Один брокер на пул; пул, обслуживаемый одним брокером, — единица бюджета. Брокер остановился — пул простаивает, заказы ждут в outbox hub в состоянии «брокер недоступен», раннеры доживают текущие джобы и отдают результаты после переподключения.

3.3 Раннер

  • Отдельный процесс. Подключается к брокеру сам (входящих портов нет), регистрируется, исполняет выданные джобы, стримит вывод и возвращает результат. Что запускать, он не решает.
  • Настройки владельца раннера: потолок таймаута джобы, размер и хранение кэша и рабочих копий (раздел 3.10).
  • Атрибуты: levels (из определённых, только те, чьим характеристикам удовлетворяет машина), platforms (непрозрачные метки владельца), tags, workers (сколько джоб одновременно, по умолчанию 1), имя (уникально на брокере).
  • На одной установке может работать несколько раннеров (например, light и heavy); у каждого своё имя, уровни, платформы, теги и воркеры. Они делят пул установки.
  • Если брокер недоступен дольше льготного срока (по умолчанию 10 минут, политика), раннер убивает свои запущенные джобы; результаты завершённых хранит и отдаёт после переподключения.
  • Раннер принимает джобы только от брокера, к которому вступил, и выполняет команды из выданного заказа.

3.4 Заказ

Заказ — данные, не код: идентификатор от брокера, описательные поля (проект, ветка, каталог, метка, заметка, источник), которые брокер записывает в историю запуска вместе с клиентом, требования к раннеру (платформа или «та же машина, что у клиента», уровень, теги, память, CPU, exclusive, самая дальняя зона), источник кода (рабочее дерево или коммит), команды и шаги с таймаутами, желаемый приоритет. Приоритет в заказе — только пожелание, порядок решает политика.

  • Рабочее дерево. Джоба, которой нужны локальные файлы, несёт требование «выполнить на той же машине». Брокер сравнивает MachineId клиента (из ключа) с MachineId раннеров. Если подходящего раннера нет, заказ ждёт и в причине ожидания сказано «нужен раннер на вашей установке, подключённых нет». Подмены коммитом нет. (Решение пользователя.)
  • Коммит. Джоба на раннере другой установки проверяет запушенный коммит (подробнее в 3.7).

3.5 Политики

Принцип: ядро содержит механизм, решение принимает политика, которую пишет владелец. Своего кода и скриптов политика не содержит: это декларативные правила и именованные встроенные стратегии.

  • Что остаётся в коде и политикой не задаётся: протокол и версии, аутентификация и проверка ключей, изоляция процессов и kill дерева, целостность хранилища. Политика выбирает, что разрешено, а не как работает проверка.
  • Правит политику только тот, кто сидит за машиной брокера. Файл правится локально, policy reload принимается только по локальному каналу; удалённо поменять нельзя, скомпрометированный hub ничего не изменит. Особый удалённый ключ владельца — возможное расширение. (Решение пользователя.)
  • Защита от самих политик. Каждое правило проверяется при загрузке; битый файл — отказ, прежняя политика остаётся. Неизвестное имя стратегии — отказ. Любая задержка или отказ называет сработавшее правило (например, «правило ci-reserve: 2 из 8 ядер зарезервированы»). Пустой файл не ломает систему: действуют значения по умолчанию.
  • Перезагрузка без остановки: policy reload проверяет и применяет файл.
  • Команды в заказе. По умолчанию клиенту с ключом доверяют (как self-hosted раннеру GitHub); для отдельных ключей политика может ограничить заказы названиями из списка раннера. (Решение пользователя.)

3.6 Пулы и ресурсы

  • Пул — набор установок, которые работают одновременно и делят один бюджет: память, CPU и набор exclusive-тегов. Лимиты принадлежат владельцу машины и описаны в политике брокера, а не в проекте. Профили лишь говорят, что нужно джобе.
  • Раннеры одного пула делят лимиты и занятые теги. Windows-хост и раннер в Docker на нём — один пул, поэтому планировщик видит их нагрузку вместе. Совместное использование нельзя надёжно определить, его объявляет владелец.
  • Раннер входит в пул того брокера, к которому вступил. Раннер, не делящий ресурсы ни с кем, — это пул из одного раннера со своим брокером.
  • Пул — это общий предел машины, пулы не вкладываются. Два пула на одном компьютере — два независимых бюджета: это правильно для взаимоисключающих установок (двойная загрузка), а для одновременно работающих владелец объявляет один пул.
  • Параллелизм ограничен дважды: workers раннера и лимитами пула; действует более строгое. Лимиты — статические числа от владельца; брокер ведёт учёт и не измеряет реальную нагрузку, поэтому посторонняя работа вне очереди не считается.
  • ci-раннер входит в пул своей машины; его acquire учитывается вместе со всеми остальными раннерами.

3.7 Маршрутизация и доставка кода

  • Заказ подходит раннеру, если совпали уровень, одна из запрошенных платформ, все теги, таймаут не больше потолка раннера и пул может выдать ресурсы. Без платформы заказ идёт раннеру той же машины, что и клиент (MachineId).
  • Профиль может иметь несколько платформ и команду на каждую ([profile.X.platform.ios]). run --platform a,b,c создаёт по джобе на платформу в одной группе с одним GroupId. Джобы группы независимы и идут параллельно, группа passed только если прошли все; отмена группы отменяет все активные джобы по тому же правилу владельца. Таймаута группы нет, только у джоб.
  • Выбор среди подходящих по умолчанию: раннер на машине клиента, затем в локальной сети, затем удалённые; среди равных по зоне — с наибольшей свободной ёмкостью. Это правило политики брокера (zone_order), порядок можно обратить или задать любой; на границу заказа (3.1) он не влияет. Допустимость всегда первична: ближний неподходящий раннер не выбирается вместо дальнего подходящего. Предпочтение не резервирование: если ближний занят, а дальний свободен, заказ уходит на дальний сразу.
  • Зона — расстояние раннера от клиента: local (MachineId совпадает), lan (метки network равны), remote. Метку брокер выводит из адреса соединения (частная подсеть; публичный адрес получает собственную метку), владелец может задать её вручную. Проект может сузить зону полем zone. Приоритет заказов и предпочтение между раннерами независимы: первое упорядочивает очередь, второе выбирает раннер для головного заказа.
  • Заказ, которому не подходит ни один зарегистрированный раннер, отклоняется при приёме с причиной; если все подходящие раннеры offline, заказ ждёт и показывает причину.
  • Доставка кода. Раннер другой установки проверяет запушенный коммит. Hub отказывает в удалённом заказе, если HEAD недоступен из удалённой ветки, и просит закоммитить и запушить (MR не нужен); незакоммиченные изменения игнорируются с предупреждением. Раннер держит один checkout на проект, делает git fetch и чистый отсоединённый checkout; доступ к репозиторию — собственные учётные данные git на раннере, ядро их не хранит. Профиль для удалённого заказа читается из коммита (git show <commit>:...). Доставка через origin по умолчанию; упаковка коммита в файл через брокера — возможное расширение политикой. (Решение пользователя.)
  • Раннер принимает заказы любого проекта; ограничение — его собственные учётные данные git. Списка проектов нет.

3.8 Вступление в пул

Как у self-hosted раннеров GitHub: вступающий сам подключается к брокеру, входящий порт ему не нужен.

  • На брокере: al-localrunner broker add печатает адрес и одноразовый код (один раз, 1 час) с отпечатком сертификата брокера.
  • На новой машине: runner join <host:port> <код> --levels ... --platforms ... --tags ... --workers ... для раннера или hub join <host:port> <код> для hub. Вступающий создаёт свою пару ключей, брокер хранит публичный ключ, код погашен. Дальше аутентификация по ключу.
  • Канал — TLS с сертификатом брокера, закреплённым отпечатком из кода (самоподписанный, создаётся при первом запуске); посредник в сети не может ни вступить, ни подменить брокера.
  • runner list, client list, runner remove, client remove на брокере; удаление отзывает ключ сразу.
  • Брокер слушает сеть, только если включён и зарегистрирована хотя бы одна машина, на адресе из его конфигурации. По умолчанию 0.0.0.0 и подстановочных адресов нет. Дашборд всегда на loopback.
  • Раннер доверяет брокеру, к которому вступил; не направляйте раннер на брокер, который принимает заказы от тех, кому вы не доверяете.

3.9 Отказы и протокол

  • Протокол. Постоянное соединение с heartbeat каждые 15 секунд; раннер, пропустивший 3, считается offline. Сообщения: назначить, отменить, чанк лога, результат шага и джобы, heartbeat. Каждое сообщение о джобе идемпотентно по идентификатору заказа и номеру seq, поэтому повтор после переподключения ничего не меняет. В рукопожатии версия протокола; брокер отказывает несовместимой мажорной версии и сообщает об этом, так что обновлять всё одновременно внутри мажорной версии не нужно.
  • Живой лог. Раннер стримит чанки брокеру, брокер сохраняет лог и ретранслирует чанки hub; hub пишет temp/runner/<job-id>.log в каталоге отправителя, и агенты читают один файл. Раннер и брокер ведут каждый свой outbox: при разрыве раннер сбрасывает брокеру вывод и результаты по порядку без дублей, а брокер так же доставляет hub чанки, результаты и подтверждения отмен.
  • Hub пропал. Брокер держит заказы этого hub льготное окно, затем действует по политике; выполняющаяся джоба доживает, результат и вывод ждут в outbox брокера до возвращения hub (хранение и срок — политика).
  • Брокер пропал. Пул простаивает, заказы остаются у hub; раннер доживает джобы и по истечении срока убивает их.
  • Мёртвый отправитель через машины. Hub следит за процессом-отправителем на своей машине и при его гибели отменяет заказы у брокера (submit --detach и ручки сохраняют смысл).
  • ci на другой машине. Раннер al-ci делает acquire и освобождение через то же аутентифицированное соединение к брокеру и учитывается в пуле своей машины.

3.10 Настройки раннера: потолок таймаута и кэш

У каждого раннера свой файл настроек владельца (runner.toml в его каталоге состояния). Ядро в нём ничего не знает про сборки: кэш для него — именованные каталоги с размером и временем последнего использования. Формат черновой.

name    = "linux-heavy"
levels  = ["heavy"]
platforms = ["linux", "android"]
tags    = ["gradle", "emulator"]
workers = 1

[limits]
max_job_timeout_s = 3600     # потолок таймаута джобы на этом раннере

[cache]
max_size_gb    = 40          # общий размер кэша раннера
retention_days = 14          # удалять записи, которыми не пользовались дольше
evict          = "lru"       # при нехватке места — самые давние первыми

[workspace]
max_size_gb    = 20          # checkout'ы проектов
retention_days = 7
  • Потолок таймаута. max_job_timeout_s ограничивает джобу на этом раннере. Действует наименьший из трёх пределов: профиля, брокера и раннера. Джоба, чей таймаут больше потолка раннера, этому раннеру не подходит (раннер не берёт её молча с урезанным таймаутом), а в причине ожидания сказано «нужен таймаут 7200 с, потолок раннера 3600 с». Поведение «подрезать вместо отказа» можно включить правилом политики брокера. Профиль по-прежнему обязан задавать timeout_s.
  • Кэш. Профиль может перечислить именованные кэши (cache = ["gradle", "cargo"]). Раннер хранит для каждого проекта и имени постоянный каталог между запусками и сообщает джобе его путь переменной окружения (LOCALRUNNER_CACHE_<ИМЯ>); что в нём лежит и как использовать, решает команда джобы. Ядро не знает, что это кэш Gradle или Cargo.
  • Размер и хранение. Перед запуском джобы и по таймеру раннер удаляет записи, не использованные дольше retention_days, и, если кэш превышает max_size_gb, самые давние (lru) до нужного размера. Кэш, которым пользуется выполняющаяся джоба, никогда не удаляется; джоба, которой не хватает места даже после очистки, ждёт или падает с причиной.
  • Рабочие копии. Checkout'ы удалённых джоб (раздел 3.7) подчиняются тем же правилам: хранение и размер в [workspace].
  • Раннер сообщает брокеру потолок таймаута, размер кэша и его заполнение; они видны на странице «Раннеры» и в метриках.

4. Уровни (задаются вне кода)

Уровень — метка, которая говорит, какие джобы принимает раннер. В коде уровней нет: владелец определяет их в levels.toml в каталоге состояния брокера (файл владельца машины, не проекта). Без файла действуют три значения по умолчанию: light и heavy без требований и приоритета 0, ci с приоритетом 100. Ядро имён уровней не знает.

[level.light]
description = "single tests while working on one feature"
priority = 0

[level.heavy]
description = "whole test tiers, emulator runs"
priority = 0
min_memory_mb = 12288
min_cpu = 6
min_disk_mb = 51200
programs = ["git", "adb", { name = "gradle", check = "gradle --version" }]

[level.ci]
priority = 100
  • Определение: имя (строчные буквы, цифры, -, до 32 символов), необязательное описание, priority (выше — раньше, по умолчанию 0; это входные данные политики) и необязательные характеристики, которым должен удовлетворять раннер: min_memory_mb, min_cpu, min_disk_mb (свободное место там, где работает раннер), programs (исполняемые файлы в PATH раннера; запись с check ещё запускает команду, она должна завершиться с кодом 0 за 10 секунд). Ядро понимает только эти ключи и сравнивает числа.
  • Раннеру предлагается уровень, только если его машина удовлетворяет определению: память и CPU — лимиты пула, диск и программы проверяются на машине раннера при регистрации и при каждом up. Раннер, не прошедший уровень, регистрируется без него; страница «Раннеры» и команда levels показывают невыполненную характеристику с числами («нужно 12288 МБ, в пуле 8192 МБ», «adb не найден»). up --levels heavy на такой машине отказывает с тем же различием; остальные уровни раннера работают. Удалённый раннер проверяет себя сам и сообщает результат брокеру — то же доверие, что и к объявленным лимитам пула.
  • Профиль называет уровень; неопределённый уровень отклоняется при отправке со списком определённых. Другая градация — другой levels.toml: переименовать, добавить или убрать метки можно, не трогая программу и профили с прежними именами.
  • Приоритет берётся только из определения, не из имени: порядок очереди, аренда ci acquire (называет свой уровень, по умолчанию ci) и старение используют priority.

5. Профили и шаги

Профиль лежит в .localrunner/profiles.toml репозитория потребителя. Это требования джобы, а не настройки машины.

[profile.rust-unit]
level = "light"
command = "cargo test --workspace"
timeout_s = 900
mem_mb = 4096
cpu = 4
tags = ["cargo"]

[profile.android-tier]
level = "heavy"
command = "pwsh scripts/android-tier.ps1"
timeout_s = 3600
mem_mb = 12288
cpu = 6
tags = ["gradle", "emulator"]
exclusive = ["gradle", "emulator"]
  • timeout_s обязателен; значения по умолчанию и неограниченного запуска нет. Верхний предел задают конфигурация брокера и потолок раннера (max_job_timeout_s, раздел 3.10): действует наименьший.
  • cache — именованные кэши, сохраняемые на раннере между запусками этого проекта (раздел 3.10); ядро не знает их содержимого.
  • tags — ресурсы, которые джоба держит на время прогона; exclusive — теги, которые больше никто из запущенных джоб держать не может.
  • Ядро не интерпретирует command, оно только запускает процесс. Несколько команд — steps. Поле level задаёт требования; выбор по памяти, CPU и меткам без уровня — возможное расширение.

5.1 Шаги

В профиле либо command (один шаг), либо steps (упорядоченная последовательность), но не оба.

[profile.rust-gate]
level = "light"
timeout_s = 1800
tags = ["cargo"]
steps = [
  { name = "fmt",    command = "cargo fmt --all --check", timeout_s = 120 },
  { name = "clippy", command = "cargo clippy --workspace --all-targets -- -D warnings", timeout_s = 600 },
  { name = "test",   command = "cargo test --workspace", timeout_s = 900, mem_mb = 8192 },
]
  • Одна джоба — одно место в очереди: шаги идут подряд, между ними другие джобы уровня не стартуют.
  • Ресурсы берутся один раз: максимум по шагам (память, CPU) и объединение тегов и exclusive; шаг может переопределить mem_mb, cpu, tags. Захвата по шагам нет, значит нет частичного удержания и взаимной блокировки.
  • У каждого шага свой обязательный timeout_s, он идёт внутри оставшегося таймаута джобы (тоже обязательного); шаг убивается по более раннему из двух.
  • Упавший шаг останавливает джобу, остальные шаги skipped. continue_on_failure = true позволяет продолжить, результат джобы остаётся failed.
  • Ветвления, условия и зависимости между шагами в ядро не входят — используйте скрипт внутри command.
  • Несколько независимых джоб из одной сессии — несколько submit: каждая ставится отдельно, между ними могут идти джобы других сессий.

6. Очередь и планирование

  • Очередь заказов живёт на брокере. Порядок выдачи определяет политика; по умолчанию строгий приоритет по уровню (ci раньше остальных), внутри приоритета порядок постановки (FIFO). Джоба стартует, когда свободен раннер её уровня и платформы и планировщик выдаёт память, CPU и теги.
  • Без вытеснения: заказ высокого приоритета никогда не останавливает запущенную джобу, он идёт первым и ждёт ресурсов.
  • Старение (по умолчанию 30 минут, правило политики): джоба, ждавшая дольше порога, упорядочивается как высший определённый приоритет.
  • Джоба, которая не поместится в лимиты пула никогда, отклоняется при приёме с причиной.
  • Состояния: queued → running → passed | failed | timeout | cancelled; шаг — passed | failed | timeout | skipped.
  • Каждая джоба пишет stdout и stderr в temp/runner/<job-id>.log каталога отправителя с заголовком на шаг; submit возвращает идентификатор, ожидание стримит ход и возвращает код выхода.
  • Отмена и таймаут убивают дерево процессов (Windows Job Object; группа процессов в остальных ОС).
  • Устойчивость: правило мёртвого отправителя описано в разделе 7; мёртвая джоба убирается; аренды привязаны к процессам брокера.

7. Отправитель и отмена

Каждая джоба говорит, кто её отправил, чтобы очередь, страница и лог отвечали на вопрос «чья это».

7.1 Идентичность

  • --as <имя> обязателен для submit из сессии или терминала (внутри GitHub Actions получает значение по умолчанию). Это свободная метка вызывающего (claude:session-3, alex); ядро агентов не перечисляет и не интерпретирует. Необязательный --note <текст> (до 200 символов) говорит, зачем запуск.
  • CLI собирает сам и без возможности переопределить: пользователя ОС, хост, идентификатор и время старта процесса-отправителя, рабочий каталог, а для git-worktree ещё ветку и корень. Это общие данные git и ОС, без знания об агентах.
  • Показывается в status, HTML-снимке, дашборде и заголовке лога: проект, источник, метка, заметка, ветка, каталог, возраст джобы.
  • Идентичность — подсказка, а не аутентификация: любой локальный процесс того же пользователя ОС может отправить под любой меткой. Граница — IPC, доступный только пользователю ОС. Для брокера границей служит ключ клиента.
  • Отмена: по умолчанию только джобы с той же меткой --as и тем же пользователем ОС; чужая метка требует --force, что записывается в лог отменённой джобы вместе с меткой отменившего.

7.2 Проект и источник

  • project: нормализованный origin (owner/repo) каталога отправителя; без remote — имя корня репозитория; вне git — имя каталога. Записываются также корень репозитория и worktree, чтобы различать два worktree одного проекта.
  • source: session (терминал или сессия агента: метка, процесс, каталог) или github (джоба GitHub Actions, определяется по GITHUB_ACTIONS=true: репозиторий, workflow, job, run id и attempt, ref, actor, URL запуска; --as по умолчанию github:<workflow>/<job>).
  • Чтение окружения CI живёт в адаптере источника уровня ci; ядро видит только нормализованные поля. Другая CI-система — другой адаптер, не изменение ядра.
  • У джобы github нет локального процесса-отправителя; её жизнь определяется процессом раннера этой джобы, а отменённый workflow отменяет джобу.
  • Везде показываются project, source и метка вместе (например, Al.Browser · session · claude:fix-12); github ссылается на URL запуска. Фильтры: status --project, --source session|github, --as; те же поля есть в --json.

7.3 Свои джобы и ранняя отмена

  • submit печатает идентификатор и пишет ручку temp/runner/<job-id>.json в каталоге отправителя (метка, идентификатор, профиль, время). После потери контекста или перезапуска агент находит свои джобы по ручкам и по hub.
  • al-localrunner jobs --mine — джобы вызывающего (тот же пользователь ОС и метка --as; метка задана или читается из последней ручки в каталоге); --active оставляет только queued и running; есть --json.
  • al-localrunner cancel <job-id> отменяет одну джобу, cancel --mine — все активные джобы вызывающего; проверка владельца по 7.1, чужая метка — --force.
  • Эффект отмены: queued снимается из очереди сразу; running получает мягкий сигнал (Ctrl+Break в Windows, SIGTERM в остальных ОС), после льготного периода (10 секунд по умолчанию) дерево убивается, выполняющийся шаг cancelled, остальные skipped, джоба cancelled, ресурсы освобождаются только когда дерево мертво; уже завершённая джоба — отчёт о конечном состоянии без действий.
  • Причина отмены пишется в заголовок лога: кто, когда и --reason, если задан.
  • wait — только наблюдатель: прерывание wait (Ctrl+C, таймаут инструмента агента) ничего не отменяет. Отменяет только cancel, таймаут или правило мёртвого отправителя.
  • Процесс-отправитель — тот, что вызвал CLI (родитель короткоживущего al-localrunner, записанный со временем старта), а не сам CLI, иначе каждая джоба умирала бы после возврата submit. submit сообщает hub о завершении сообщением Bye сразу после получения идентификатора, а wait работает на своём соединении. (Решение автора.)
  • Мёртвый отправитель: когда процесс-отправитель исчез, его ждущие заказы снимаются, выполняющиеся убиваются, чтобы освободить машину. submit --detach позволяет выполняющейся джобе пережить вызвавшего; она остаётся видимой и отменяемой по метке. Джоба github отменяется отменой запуска workflow или оператором через cancel --force.
  • Определение живости: родитель CLI, пара pid и время старта (в Linux относительно загрузки, из /proc starttime), правило двух проходов; в Unix, кроме Linux, при несовпадении не убивается. Короткоживущий shell агента убьёт его джобы, поэтому скилы предписывают submit --wait или --detach.

8. История

Завершённые джобы хранятся и доступны позже из любой сессии и для любого проекта.

  • Хранилище. SQLite broker.db в каталоге состояния брокера (одна база: история запусков, реестр машин, очередь заказов, аренды) (библиотека в общественном достоянии, совместима с правилом о лицензиях). Строка на джобу со всем известным: идентификатор, клиент (ключ, MachineId, ярлык), проект, источник, метка, заметка, ветка, каталоги, профиль, уровень, времена постановки, старта и финиша, результат, код выхода, кто отменил и почему, раннер; строка на шаг: состояние, времена, код, таймаут. Запись создаётся при постановке и обновляется при каждой смене состояния, поэтому сбой теряет не более последнего обновления.
  • Чья история. Брокер — источник истины для запусков на своих раннерах, включая то, с какого клиента запуск пришёл. Hub хранит только outbox недоставленных заказов и копию лога в каталоге отправителя; историю и подробности запрашивает у брокеров. Если ноутбук выключен, история его запусков остаётся на брокере и доступна другим hub в пределах политики видимости. (Решение пользователя; «брокер ничего не знает о hub» относится к коду, а не к данным.)
  • Логи. Полный лог хранится у брокера в logs/, копия — temp/runner/<job-id>.log каталога отправителя; для github хранится и URL запуска.
  • Хранение. По возрасту и суммарному размеру, что наступит раньше: по умолчанию 30 дней и 2 ГБ логов, 365 дней строк (политика брокера). Чистка идёт с самых старых и не трогает активные джобы. Брокер на общей машине ограничивает объём политикой, чтобы один клиент не заполнил диск пула.
  • CLI. history [--project P] [--source session|github] [--as L] [--profile N] [--result R] [--since D] [--limit N] [--platform] [--runner] [--group] [--client C], новые первыми, --json; history show <job-id> — полная запись; log <job-id> [--step NAME] [--tail N] читает сохранённый лог, а для незавершённой джобы следит за ним. Команды идут через hub к брокерам, которые он знает, и по умолчанию показывают запуски этого клиента.
  • Представления. status --html --history добавляет таблицу истории в снимок; у дашборда есть вкладка «История» с теми же фильтрами; каждая строка ведёт к логу.
  • Статистика. al-localrunner stats [--project P] [--profile N] [--client C] и страница «Статистика»: запуски, доля успехов, время ожидания и длительность (медиана и 95-й процентиль) по профилям и шагам, доля таймаутов и отмен, насыщение пула по клиентам. Считается брокером по его истории; владелец брокера видит весь пул, клиент — свои данные. Цель — выставить честные timeout_s и увидеть, где ждёт очередь.
  • История читается представлениями и не уходит за пределы сети: брокер отдаёт её только аутентифицированным клиентам по политике видимости.

9. Просмотр очереди и дашборд

9.1 Три формы одних данных

  • al-localrunner status — текст, --json для агентов и скриптов.
  • status --html [путь] — дашборд одним самодостаточным HTML-файлом с вшитыми данными (по умолчанию temp/runner/queue.html). Снимок: не нужен слушатель, открывается с диска.
  • al-localrunner dashboard — живой вид в браузере. Hub отдаёт страницу и JSON/SSE-поток на 127.0.0.1 на случайном свободном порту; URL несёт случайный токен запуска, запросы без него или с чужого origin отклоняются. Запускается по требованию, останавливается Ctrl+C или down.

Что показывает страница: по уровням — раннеры up/down, свободные память и CPU, занятые теги; выполняющиеся джобы — идентификатор, проект, источник (со ссылкой на запуск), метка, профиль, каталог, уровень, прошедшее время относительно таймаута, список шагов с состоянием, время шага относительно его таймаута и последние строки текущего шага; очередь — позиция, проект, источник, метка, профиль, каталог, время ожидания и причина ожидания (воркер занят, память, CPU, занятый exclusive-тег и кем, правило политики); последние завершённые джобы со ссылкой на лог. Одна модель данных питает все три формы, новая форма не добавляет нового источника истины. С страницы доступна только отмена.

9.2 Страница

Одна интерактивная страница обслуживает и живой дашборд, и статический снимок: снимок вшивает данные JSON и выполняет тот же код с выключенными обновлениями и действиями. Доставка: одна самодостаточная страница, вшитая в hub, без внешних скриптов, шрифтов и сетевых запросов (работает офлайн). Светлая и тёмная тема следуют системе; вёрстка работает на ширине телефона; управление с клавиатуры с видимым фокусом.

  • Очередь — выполняющиеся и ждущие джобы. Строка раскрывается в карточку: проект, источник, метка, заметка, ветка, каталог, профиль, уровень, причина ожидания и лента шагов (полоса на шаг относительно таймаута, текущий шаг анимирован, skipped серый). Рядом живой лог выбранного шага: слежение, пауза, поиск по тексту, копирование, скачивание; кнопка отмены.
  • История — завершённые джобы, новые первыми; щелчок открывает ту же карточку с сохранённым логом.
  • Статистика — по профилю и шагу: доля успехов, ожидание и длительность (медиана, 95-й процентиль) встроенными SVG-диаграммами, диаграмма полос по уровням за день (кто держал воркер, простои, ожидание) и насыщение: сколько джоб и сколько времени ожидания приходится на каждую причину (воркер, память, CPU, exclusive-тег, нет раннера, правило политики), чтобы владелец видел, какой лимит поднять.
  • Раннеры — по брокеру и пулу, затем по уровню: раннеры online/offline с последней активностью, платформа, воркеры, длина очереди, шкалы памяти и CPU, занятые и exclusive-теги с их держателями; для не прошедших уровень — невыполненные характеристики.

Общее для вкладок: фильтры (проект, источник, метка, уровень, профиль, результат, период, свободный текст), сортируемые столбцы; состояние в хеше URL, поэтому вид — ссылка, а последние фильтры восстанавливаются из localStorage. ?as=<метка> подсвечивает и закрепляет джобы метки. Живые обновления одним SSE-потоком с автопереподключением и видимым состоянием соединения; кнопка «Пауза» замораживает вид, новые события при паузе считаются счётчиком. Экспорт отфильтрованной таблицы в CSV или JSON и Save snapshot. Горячие клавиши: / поиск, j/k перемещение, Enter открыть, Esc закрыть, g q|h|s|r вкладки, ? список.

9.3 Источники данных

  • Страница и сервер читают через один интерфейс DataSource. Дашборд hub берёт всё из API брокеров: раннеры, нагрузку пулов, очередь, выполняющиеся заказы, историю запусков и логи. Когда брокер недоступен, дашборд показывает копии логов и заказы, ждущие в outbox. Дашборд не настраивается списком раннеров, а раннеры не знают адреса дашборда.
  • Если брокер недоступен, его данные помечены как устаревшие; остаются заказы в outbox этого hub и копии логов. Дашборд на другой машине — тот же дашборд своего hub: он читает брокеры, которые знает этот hub.

9.4 Действия и безопасность дашборда

  • Отмена ждущей или выполняющейся джобы после подтверждения с названием джобы. Отмена со страницы считается --force: она записывается в лог и историю как отмена dashboard:<пользователь ОС> с причиной из диалога. Отмена всех джоб проекта или метки — отдельное явное действие со списком в диалоге. Нет отправки, правки профилей и конфигурации, запуска и остановки раннеров со страницы.
  • Случайный порт, токен на запуск; токен обменивается на сессионный cookie (HttpOnly, SameSite=Strict) при первом запросе и убирается из адресной строки.
  • Только localhost без возможности изменить: сокет на 127.0.0.1 (и ::1), никогда 0.0.0.0, :: или адрес LAN; нет опции, ключа конфигурации или переменной окружения, которые это расширят. Дашборд не публикуется и не туннелируется плагином.
  • Защита от DNS rebinding: запрос с Host, не равным localhost, 127.0.0.1 или [::1] с портом дашборда, отклоняется, как и запрос с чужим Origin. При старте hub проверяет фактический адрес и завершается с ошибкой, если он не loopback.
  • Ничего не покидает машину: hub, CLI и страница не делают исходящих запросов, не шлют телеметрию, не загружают логи, историю и снимки. Единственные исходящие соединения всей системы: ci-раннер GitHub Actions к GitHub (собственный протокол, без данных системы), соединения hub и раннеров с брокерами, git fetch раннера из репозитория джобы и необязательный получатель логов и метрик (OTLP), который владелец включил в logging.toml.
  • Любой запрос, меняющий состояние, — POST с заголовком против подделки и проверкой Origin/Host; чтения и поток требуют сессионный cookie. Текст логов и полей выводится как текст, не как разметка; строгая CSP без выполнения встроенных скриптов; логи не индексируются и не кэшируются. Снимок содержит логи только с --with-logs, потому что в логах могут быть секреты из команд профиля.

12. Логирование и метрики

Диагностика самой системы идёт через фасад логирования, а куда она попадёт, решает владелец конфигурацией. По умолчанию это файл на диске; Grafana подключается необязательным получателем.

  • Фасад в коде. Ядро и роли пишут структурированные события через крейт tracing (MIT) и ничего не знают о получателях. Это аналог ILogger. Получатели, уровни и редактирование полей подключает один общий крейт (lr-obs), а не код ролей.
  • Что логируется. Диагностика hub, брокера и раннера: подключения и обрывы, приём и выдача заказов, сработавшие правила политики, перезагрузка политики, отказы, работа outbox, очистка хранилища. Вывод джоб сюда не входит: он хранится как данные запуска (раздел 8) и в получатели не уходит. (Решение пользователя: в Grafana идут диагностические логи и метрики.)
  • Поля события: время, уровень, роль (hub, broker, runner), компонент, MachineId, сообщение и по месту order_id, job_id, раннер, ярлык клиента, имя сработавшего правила. Не пишутся: команды и переменные окружения джоб, вывод джоб, ключи, коды подключения и токены. Список редактируемых полей задаётся конфигурацией.

14. Данные

Одна база SQLite на сторону. У брокера broker.db: история запусков на его раннерах (с клиентом), реестр машин, раннеры, очередь заказов, аренды. У hub hub.db: outbox (недоставленные заказы и отмены), активные заказы и список брокеров. Связи между файлами логические, по идентификаторам: внешних ключей между файлами нет. Пулы и лимиты — в policy.toml, а не в базе. Полные логи — файлы в logs/<job-id>.log брокера.

  • Финальное состояние джобы пишется один раз: повторная доставка результата или второе конечное состояние не меняют строку.
  • Запись запуска остаётся на брокере в пределах хранения. Hub хранит только outbox и копию лога: запись из outbox удаляется после подтверждения брокером, а брокер не знает, что лежит в outbox hub.
  • Хранение истории на брокере: 30 дней и 2 ГБ логов, 365 дней строк по умолчанию (политика); чистка идёт с самых старых и не трогает активные джобы.
  • В machine хранятся только публичные ключи и ярлыки клиентов; токен регистрации ci-раннера не пишется никуда.

16. Потоки

15.1 Запуск на той же машине (рабочее дерево)

  1. CLI собирает идентичность (--as, пользователь ОС, ветка, проект) и читает профиль из рабочего дерева.
  2. По IPC уходит Submit в hub; hub собирает заказ с требованием «та же машина», ограничивает таймаут сверху, отбирает брокеров по зоне, запрашивает у первых по порядку зон актуальные возможности и выбирает брокера по hub-policy.toml. Заказ записывается в outbox и доставляется брокеру с повтором до подтверждения.
  3. Брокер проверяет допуск клиента, принимает заказ, отклоняет не помещающийся в пул и ставит в очередь по политике.
  4. Планировщик выбирает раннер с тем же MachineId и выдаёт память, процессор и теги пула.
  5. Раннер выполняет шаги в каталоге отправителя; брокер сохраняет вывод в лог запуска и ретранслирует его hub, а hub пишет temp/runner/<id>.log и шину событий.
  6. Брокер пишет запись запуска в broker.db вместе с клиентом и подтверждает hub; hub удаляет заказ из outbox и снимает активный заказ; ресурсы освобождаются только после того, как дерево процессов мертво.

15.2 Удалённый запуск на другой платформе

  1. CLI проверяет, что HEAD запушен (иначе просит закоммитить и запушить ветку без MR), читает профиль из коммита.
  2. На каждую платформу создаётся заказ в одной группе; команды берутся из platform.<имя>.
  3. Hub отбирает брокеров по зоне, запрашивает у первых по порядку зон актуальные возможности (раннеры, платформы, уровни, теги, потолки таймаута, online/offline) и выбирает брокера по hub-policy.toml; брокер отбирает раннеры по уровню, платформе, меткам и ресурсам пула, затем выбирает по политике (по умолчанию ближайшая зона).
  4. Брокер шлёт Assign по TLS-каналу; раннер делает git fetch и чистый отсоединённый checkout.
  5. Раннер стримит Chunk с номером seq; брокер сохраняет вывод в лог запуска и ретранслирует его hub, hub пишет копию и обновляет дашборд.
  6. После обрыва связи раннер повторяет неподтверждённое из Outbox; получатель отбрасывает дубликаты по seq.

15.3 Потеря hub

  1. Брокер видит обрыв соединения hub и запускает льготное окно из политики.
  2. В окне заказы остаются; hub вернулся — всё продолжается и результаты доставляются.
  3. Окно истекло: ждущие заказы отменяются, выполняющиеся доживают, результат ждёт переподключения (значения по умолчанию, меняются политикой).
