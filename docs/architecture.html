Al.LocalRunner — архитектура

Очередь запусков тестов и сборок на нескольких машинах. Документ описывает, как система устроена: окружение, компоненты, данные и потоки. Источники: docs/design.md (что должно быть) и docs/superpowers/plans/2026-11-09-localrunner.md (как строится).

Глоссарий

Все термины определены здесь один раз. Подчёркнутое точками слово в тексте и на схемах показывает определение из этого раздела при наведении мыши или фокусе с клавиатуры; отдельной копии текста определений нет.

Узлы и роли

Компьютер
Физическая машина. На ней может стоять несколько установок: те, что работают одновременно (основная ОС, Docker, виртуалки), образуют один пул, а взаимоисключающие (двойная загрузка) — разные пулы.
Установка
Один экземпляр программы со своим каталогом состояния, MachineId и ключами: основная ОС, контейнер Docker или виртуалка. Один компьютер может нести несколько установок.
MachineId
Случайный идентификатор установки. Создаётся один раз при первом запуске демона и хранится в файле machine-id. По нему определяется, чья это джоба и кто вправе её отменить.
Hub (хаб)
Роль: владеет очередью, планировщиком, историей и дашбордом и решает, какая джоба на какой раннер пойдёт. Сам джобы не исполняет. По умолчанию это машина пользователя; хабом может быть любая.
Раннер
Роль и отдельный процесс: исполняет выданные hub джобы и возвращает результаты и логи. На одной установке может работать несколько раннеров, например light и heavy.
Клиент
Роль: машина, которая только отправляет джобы и смотрит за ними. Вступает в hub так же, как раннер, и получает свой MachineId и ключ.
Демон
Фоновый процесс al-localrunner на установке, который держит роль hub. Запускается командой up.
ci-раннер
Настоящий self-hosted раннер GitHub Actions с меткой al-ci. Перед запуском берёт ресурсы у планировщика (acquire), чтобы не пересекаться с локальными прогонами. Не путать с нашим раннером.
Дашборд
Страница в браузере: очередь, история, живой лог, статистика, раннеры. Слушает только 127.0.0.1. Сейчас читает демон своей машины, на втором этапе будет читать hub.

Очередь и ресурсы

Джоб
Один запуск профиля: очередь, шаги, результат. Имеет JobId; джобы одной команды по нескольким платформам образуют группу с GroupId.
Профиль
Описание запуска в .localrunner/profiles.toml проекта: уровень, команда или шаги, таймаут, память, CPU, теги. Это требования джобы, а не настройки машины.
Уровень
Метка, которая говорит, какие джобы принимает раннер и с каким приоритетом. По умолчанию light, heavy и ci. Владелец определяет уровни в levels.toml вместе с требованиями к машине.
ci
Уровень по умолчанию с наивысшим приоритетом (100). Его джобы берутся первыми, но уже работающие джобы не вытесняют.
Приоритет
Порядок выдачи: выше приоритет, раньше джоба. Внутри одного приоритета порядок постановки. Джоба, ждавшая дольше 30 минут, поднимается до высшего приоритета.
Пул
Набор установок, которые работают одновременно и делят общий бюджет: лимиты памяти и CPU и набор exclusive-тегов. Лимиты задаёт владелец, а не проект. На одном компьютере может быть несколько пулов, если они взаимоисключающие (двойная загрузка): у каждого лимиты всего компьютера.
Воркер
Сколько джоб раннер выполняет одновременно. Параллельность ограничена дважды: воркерами раннера и лимитами пула; действует более строгое.
Платформа
Непрозрачная метка владельца (macos, ios, android...). Ядро только сравнивает метки на равенство. Если в профиле несколько платформ, на каждую создаётся своя джоба.
Тег
Ресурс, который джоба удерживает на время прогона (gradle, emulator). Теги раннера означают заявленные им возможности.
exclusive
Тег, который одновременно не может держать никто другой. Действует внутри пула.
Зона
Расстояние от отправителя до раннера: local, lan или remote. Среди подходящих раннеров предпочитается ближайший, но занятый ближайший не блокирует свободный дальний.
Аренда (acquire)
Захват ресурсов ci-раннером у планировщика перед запуском GitHub-джобы. Освобождается, когда раннер завершился или связь оборвалась.
Отправитель
Процесс, вызвавший CLI (родитель al-localrunner), вместе с меткой --as и MachineId. По нему определяется право отмены и правило мёртвого отправителя.
Мёртвый отправитель
Когда процесс-отправитель завершился, его ожидающие джобы снимаются, а выполняющиеся убиваются. Флаг --detach отключает правило для идущей джобы.

Связь

Код подключения
Одноразовый код (живёт 1 час), который выдаёт hub, чтобы раннер или клиент вступил. После вступления машина использует собственную пару ключей.
network
Метка сети машины, по ней считается зона lan. Hub выводит её из адреса подключения, владелец может задать вручную.
Heartbeat
Сигнал живости раннера каждые 15 секунд. После трёх пропусков раннер считается offline.
IPC
Локальный канал между CLI, демоном и раннером на одной установке: именованный канал в Windows, Unix-сокет в других ОС. Доступ только у пользователя ОС.
TLS
Шифрованное соединение раннера или клиента с hub по сети. Сертификат hub закреплён отпечатком, который входит в код подключения.

1. Принципы

  • Универсальное ядро. Очередь, планировщик и демон не знают про язык, тестовый фреймворк и платформы. Названия платформ, метки и команды приходят от владельца машины и из профилей проекта.
  • Роли разделены. hub не исполняет джобы и не содержит встроенного раннера; раннер не решает, что запускать. Между ними один интерфейс — протокол раннера. Локальный раннер — отдельный процесс, он подключается к hub по тому же протоколу через локальный канал.
  • Один бинарник, три роли. al-localrunner работает как hub (очередь, планировщик, дашборд), раннер (выполняет джобы) и клиент (отправляет и смотрит). По умолчанию каждая машина сама себе hub.
  • Раннер сам подключается к hub, как у GitHub self-hosted: входящие порты на раннере не нужны.
  • Ресурсы считаются по пулу — набору установок, которые работают одновременно и делят бюджет, а не по раннеру. Docker и виртуалки остаются отдельными установками со своим ID, но входят в пул хоста. Взаимоисключающие установки (двойная загрузка) — разные пулы на одном компьютере.
  • Локальный раннер тестирует рабочее дерево, удалённый — запушенный коммит.
  • Ничего не уходит наружу. Дашборд слушает только loopback; телеметрии и загрузок нет.

2. Архитектура: машины и связи

Этап 1 — всё в одной локальной сети. Раннеры на VPS и за чужим роутером — следующий этап; схема им не мешает.

Сплошные синие стрелки — постоянное TLS-соединение раннера или клиента к hub (проверка версии, heartbeat 15 с). Серые — локальный IPC и HTTP на loopback. Пунктирные рамки — физические компьютеры; каждая рамка внутри — отдельная установка программы со своим ID. Точечные синие рамки — пулы: установки внутри одной рамки работают одновременно и делят ресурсы; два пула на одном компьютере взаимоисключающие. Зелёные — установки в роли раннера. Docker и виртуалка стоят на компьютере 1, делят пул win-host с Windows, но остаются отдельными установками. Раннер Windows — отдельный процесс рядом с демоном hub: он подключается к hub по тому же протоколу, что и удалённые раннеры, а hub сам джобы не исполняет.

Что где работает

  • Запуск джобов с любого компьютера. Сессии агентов на компьютере 1 говорят с демоном по IPC, на компьютере 4 — через клиентское соединение к hub. Очередь одна, приоритет и учёт ресурсов у hub.
  • Дашборд с любого компьютера. Сейчас каждый дашборд читает демон своей машины по loopback. Дашборд на ноутбуке, который читает данные hub (живое состояние от hub, история удалённых машин по каналу раннера), — этап 2; для этого нужен только адрес hub.
  • Несколько раннеров на одной ОС. На Windows и на Linux работают по два отдельных процесса: раннер light и раннер heavy. У каждого своё имя, уровни, воркеры и регистрация на hub; пул у них общий, поэтому память и CPU считаются вместе.
  • Один компьютер — несколько установок. Windows, Docker и виртуалка на компьютере 1 — три установки с тремя ID, но один пул: память, CPU и exclusive-теги считаются вместе.
  • Разные ОС. Платформа раннера — метка владельца (windows, linux, macos, ios, android); ядро сравнивает метки на равенство.

Ключевые решения

  • Hub выбирает пользователь; по умолчанию это машина, с которой он работает. Любая другая машина тоже может быть hub. Несколько клиентов на одном hub дают общую очередь, раздельные hub — раздельные очереди.
  • Раннер выбирается по порядку: сначала подходящий по уровню, платформе, меткам и ресурсам; среди подходящих — ближайший по зоне (local, затем lan, затем remote). Зона считается относительно отправителя через метку network.
  • Приоритет у ci, без вытеснения запущенных; джоб без ci, который ждёт больше 30 минут, упорядочивается как ci.
  • Если hub пропал на 10 минут, раннер убивает свои запущенные джобы; результаты завершённых хранит и отдаёт позже.

4. Данные

Две базы SQLite. history.db есть на каждой машине и хранит джобы, выполненные на ней. hub.db есть только у hub и хранит реестр машин, пулы, раннеры, очередь и аренды. Связи между базами логические, по идентификаторам: внешних ключей между файлами нет. Полные логи лежат файлами в logs/<job-id>.log.

  • Финальное состояние джоба пишется один раз: повторная доставка результата или второе конечное состояние не меняют строку.
  • Удалённый джоб записывается в history.db машины раннера; hub держит только queue_entry до старта и аренды lease.
  • Хранение: логи 30 дней и 2 ГБ, строки 365 дней; чистка идёт с самых старых и не трогает активные джобы.
  • В machine хранятся только публичные ключи; токен регистрации ci-раннера не пишется никуда.

6. Потоки

Локальный запуск

  1. CLI собирает идентичность (--as, пользователь ОС, ветка, проект) и читает профиль из рабочего дерева.
  2. По IPC уходит Submit; движок отклоняет джоб, который не поместится в пул, и ограничивает таймаут сверху.
  3. pick_next выбирает локальный раннер; планировщик выдаёт память, процессор и метки пула.
  4. run_job выполняет шаги в каталоге отправителя; вывод идёт в лог, в temp/runner/<id>.log и в шину событий.
  5. Результат пишется в history.db; ресурсы освобождаются только после того, как дерево процессов мертво.

Удалённый запуск на другой платформе

  1. CLI проверяет, что HEAD запушен (иначе просит закоммитить и запушить ветку без MR), читает профиль из коммита.
  2. На каждую платформу создаётся джоб в одной группе; команды берутся из platform.<имя>.
  3. pick_next отбирает раннеры по уровню, платформе, меткам и ресурсам пула, затем выбирает ближайшую зону.
  4. Hub шлёт Assign по TLS-каналу; раннер делает git fetch и чистый отсоединённый checkout.
  5. Раннер стримит Chunk с номером seq и пишет итог у себя; hub подтверждает Ack и ретранслирует вывод CLI и дашборду.
  6. После обрыва связи раннер повторяет неподтверждённое из Outbox; hub отбрасывает дубликаты по seq.
