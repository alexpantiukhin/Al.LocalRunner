Al.LocalRunner — architecture and design

A resource-aware queue of heavy tasks for a developer and their AI agents, on one computer or on several. This is the single design document: architecture, requirements, configuration format and security. There are no separate Markdown descriptions; the implementation plan is docs/superpowers/plans/2026-11-09-localrunner.md. The table of contents is on the left.

Glossary

Every term is defined here once. A word underlined with dots in the text and in the diagrams shows its definition from this section on mouse hover or keyboard focus; there is no separate copy of the definitions.

Nodes and roles

Computer
A physical machine. Several installations can run on it: those that run at the same time (the main OS, Docker, virtual machines) form one pool, and mutually exclusive ones (dual boot) form different pools.
Installation
One instance of the program with its own state directory, MachineId and keys: the main OS, a Docker container or a virtual machine. One computer can carry several installations.
MachineId
A random identifier of an installation. It is created once, at the first initialization of the installation, and stored in the file machine-id. It serves accounting and history. The local IPC, not the equality of declared identifiers, determines the local zone; when joining over the network, the broker rejects a MachineId equal to its own.
Hub
A role of the client side: it turns project profiles into orders, sends them to brokers, keeps the order outbox, the copy of the logs and the dashboard, and watches the sender process. It does not run jobs and does not hold a resource queue. It runs on the user's machine; each client machine has its own hub.
Pool broker
A role, one per pool: it shows which runners with which characteristics exist in the pool, accepts orders, holds their queue and hands them out to runners according to the policy. It serves an API: order intake and state reads. It stores the history of runs on its runners and records for each run which client it came from. In code it knows nothing about the hub: for it, a client is any authenticated connection.
Order
A request to run a job: requirements for the runner (platform, resources, programs, tags), a commit and commands, and the desired priority. The priority in an order is only a wish; the policy decides the order. It belongs to the client key, not to the connection: a short connection drop (laptop sleep, network change) does not cancel it. A waiting order is canceled only if the hub has not appeared for longer than the policy period (6 hours by default).
Policy
The owner's rules in policy.toml on the broker: assignment order, group weights and quotas, resource reserve, client admission, runner choice, wait windows, retention. The code contains only the mechanism and built-in strategies; an unknown rule is a refusal at load time, and a reload error keeps the previous policy.
Runner
A role and a separate process: it connects to the broker, runs the jobs the broker assigns to it and returns results and logs. Several runners can work on one installation, for example light and heavy.
Client
A client machine: only the hub and agent sessions run on it, and it does not run jobs. For the broker, its connection is an ordinary client with a label that the owner set when issuing the key.
Daemon
The background localrunner process that holds one role: hub, broker or runner. It is started by the up command; the broker can be installed as an OS service (section 3.12).
ci runner
A real GitHub Actions self-hosted runner with the label al-ci. It takes no resources from the broker by itself: a GitHub job calls localrunner run through the hub of its machine, and the order goes into the shared queue of the broker like any other, under the label ci. Not to be confused with our runner.
Dashboard
A page in the browser: queue, history, live log, statistics, runners. It starts on demand and listens only on the loopback (127.0.0.1 and ::1) of its machine. It takes runners, load and queue from the brokers' APIs, and the run history also from the brokers' APIs.

Queue and resources

Job
One run of a profile: queue, steps, result. It has a JobId. A job goes to one platform; a second platform is a second job.
Profile
The description of a run in the project's .localrunner/profiles.toml: a command or steps, a timeout and requirements for the runner (memory, CPU, disk, programs, platforms, tags). These are the requirements of a job, not machine settings.
Order requirements
What a job needs from the runner: platform, memory, CPU, disk, programs, tags, timeout ceiling, zone. The order lists them itself; there are no label levels. The hub and the broker pick a runner that has everything required, otherwise they return an error with numbers.
Client label
A group tag that the broker owner assigns to a client key when issuing it. It is part of the key record, so the client cannot forge it; the policy uses the label to compute rights, quotas, weights and priority. Not to be confused with the --as tag, which the caller sets itself.
ci
The client label for GitHub Actions jobs: its owner assigns it to the hub key on the machine with the GitHub runner. The default policy gives it the highest priority (100): such orders are taken first, but jobs that are already running are not preempted.
Priority
The assignment order is decided by the broker policy from attributes: the client label from the key record and those declared by the order (source, tags, size), not by code. Declared attributes do not raise the priority by themselves. The default policy: strict priority (GitHub Actions jobs with the label ci go first), within a priority the order of submission, and a job older than 30 minutes is raised to the highest priority.
Pool
A set of installations that run at the same time and share a common budget: memory and CPU limits and a set of exclusive tags. The limits are set by the owner in the broker policy, not by the project; a pool has one broker. One computer can have several pools if they are mutually exclusive (dual boot): each has the limits of the whole computer.
Platform
An opaque owner label (macos, ios, android...). The core only compares labels for equality. A job goes to one platform; a second platform is a second job.
Tag
A resource that a job holds for the duration of a run (gradle, emulator). A runner's tags mean the capabilities it declares.
exclusive
A tag that nobody else can hold at the same time. It applies within a pool.
Zone
The distance from the sender to the runner: local, lan or remote. Among suitable runners the nearest is preferred by default (this is a policy rule), but a busy nearest runner does not block a free distant one.
Sender
The process that called the CLI (the parent of localrunner), together with the --as tag and the MachineId. It determines the right to cancel and the dead sender rule.
Head order
The order that stands first in the queue in policy order. If it does not fit into the free resources, the following orders can bypass it only if they do not delay its start (backfilling with prediction, section 6).
Handle
The file temp/runner/<job-id>.json in the sender's directory: tag, identifier, profile and start time. With it, an agent that has lost its context finds its jobs.
Reaper
The part of the hub that watches the sender process and, when it dies, cancels the orders at the broker.
Dead sender
When the sender process has exited, its waiting jobs are removed and its running jobs are killed. The --detach flag turns the rule off for the whole order: both a waiting and a running order outlive the sender.

Communication

Join code
A one-time code (valid for 1 hour by default, the period is set by the policy) that the broker issues so that a runner or a hub can join. After joining, the machine uses its own key pair.
network
The name of a network from the [networks] list in the broker configuration; the lan zone is computed from it. The broker determines it from the address of each connection; an address outside the list is the remote zone. The client and the runner neither store nor declare the label.
Heartbeat
The runner's liveness signal every 15 seconds. After three missed signals the runner is considered offline.
Outbox
A persistent queue of outgoing messages on the hub, the broker and the runner: orders, cancellations, output and results are written to disk until the receiver confirms them and are repeated after a drop; the receiver discards duplicates by identifier and seq number.
Sink
The place where logging events and metrics go: a file on disk (the default), the console, the OS journal or an OTLP receiver such as Grafana Alloy. It is set in logging.toml; a network sink is off until the owner turns it on.
Runner cache
Named directories that the runner keeps between runs of a project and passes to a job as a path in an environment variable. The size and retention period are set by the runner owner in runner.toml; when space runs out, the least recently used are deleted. The core does not know what they contain.
Runner service
A program that the runner starts and stops for jobs according to the owner's rules (a build daemon, an emulator). When and for whom is decided by the policy, and the guarantees (bounded lifetime, resource accounting, full cleanup, readiness check, isolation) are built into the code. The core does not know what is inside.
IPC
A local channel between the CLI, the hub, the broker and the runner on one installation: a named pipe on Windows, a Unix socket on other OSes. Only the OS user has access.
TLS
The encrypted connection of a runner or a hub to the broker over the network. The broker's certificate is pinned by a fingerprint that is part of the join code.

1. Goals and principles

  • Goals. Parallel agent sessions put runs in a queue instead of overloading the machine. Every run has a mandatory timeout; on expiry or cancellation the whole process tree is killed. The core is generic, and the consumer supplies profiles.
  • Generic core. The queue, the scheduler and the roles know nothing about the language, the test framework or the platforms. Platform names, labels and commands come from the machine owner and from project profiles.
  • Roles are separated. The hub is a client: it turns profiles into orders, keeps the order outbox and the dashboard, does not run jobs and does not hold a resource queue. The pool broker knows its runners, the orders and the history of runs on them; in code it knows nothing about the hub (the logic does not distinguish consumers), while in data it records which client each run came from. The runner executes and does not decide what to run. There are two interfaces: the runner protocol (runner ↔ broker) and the broker API (orders and reads; hub ↔ broker).
  • Roles depend on abstractions. The roles get storage, network, processes, time, secrets and log sinks through traits from lr-abstractions; implementations are wired in only by the composition root lr-cli, so the logic is tested on stubs (section 13).
  • The policy decides. Assignment order, quotas, admission, runner choice, wait windows and retention are the owner's rules in policy.toml on the broker (and in hub-policy.toml at the hub for broker choice). The code has only the mechanism and the security checks (protocol, keys, process isolation).
  • One binary, three roles. localrunner works as a hub (profiles, order outbox, dashboard), a broker (runners, order queue, run history, policy) and a runner (runs jobs). On one machine up starts all three as separate processes. One machine with this set is the default variant; the rest is enabled on request.
  • The runner connects to the broker itself, as with GitHub self-hosted runners: no incoming ports are needed on the runner.
  • Resources are counted per pool — a set of installations that run at the same time and share a budget — not per runner. Docker and virtual machines remain separate installations with their own ID but belong to the host pool; a pool has one broker. Mutually exclusive installations (dual boot) are different pools on one computer.
  • Hubs and brokers are many-to-many. Each hub has its own list of brokers; a broker does not know how many hubs use it.
  • The working tree goes to a runner on the same machine, the commit to a remote one.
  • The dashboard is an addition, not the only way. Everything visible on the page can be obtained with a CLI command as text and in --json; there are no actions on the page that the CLI lacks. Agents and scripts work only through the CLI.
  • Nothing leaves the machine. The dashboard listens only on the loopback; there is no telemetry and there are no downloads. The only exception is the network sink for logs and metrics (OTLP), which the owner enables explicitly and by choice.

2. Architecture: computers and connections

Runners can sit on the same network, on another network or on a VPS: all that is needed is the broker address, which the owner enters by hand. There is no NAT traversal and there are no tunnels.

Blue lines are persistent connections to the broker: orders go down, state and results go up (over IPC on the same computer, over the network via the shared TLS bus). Gray lines are IPC and HTTP on loopback between sessions, the browser and the hub. Dashed frames are computers; the frame inside is an installation with its own ID. Dotted blue frames are pools: each pool has one broker, installations inside the frame share resources, and two pools on one computer are mutually exclusive. Green boxes are runners. The broker does not know about the hub in code: for it, the hub is a client connection, but the broker records in the history which client a run came from; each hub has its own list of brokers given to it by the owner: different hubs can know different brokers or the same ones (in the diagram, the hub of computer 1 has no mac-mini, while the laptop has all three). The hub decides by its own policy (platform, availability) which of the known brokers to send an order to.

What runs where

  • Running jobs from any computer. Each client computer has its own hub. Agent sessions talk to it over IPC, and it sends orders to the right brokers. The order queue lives on the pool broker, and its policy decides the assignment order.
  • Dashboard from any computer. The dashboard listens on the loopback of its hub and builds the view itself: runners, load, queue and run history come from the broker APIs; orders the broker has not yet accepted are held by the hub in its outbox. If a broker is unavailable, the dashboard shows that its data is stale.
  • Switching between Windows and Mac. Each client computer has its own hub, and brokers sit on the pool computers. If the laptop is turned off, only its orders disappear; the other clients and the pool keep working.
  • Several runners on one OS. On Windows and on Linux, two separate processes run, for example runners named light and heavy (the names mean nothing to the core). Each has its own name, admission rules and registration on the broker; a runner executes one job at a time, parallelism comes from several runners; the pool is shared, and memory and CPU are counted together.
  • One computer, several installations. Windows, Docker and a virtual machine on computer 1 are three installations with three IDs, one pool and one broker.
  • Different OSes. The runner platform is an owner label (windows, linux, macos, ios, android); the core compares labels for equality.

Key decisions

  • The user installs a hub on each client computer. Brokers sit on the pool computers; the hub sees the brokers whose keys it has received. On a single computer, up starts the hub, the broker and the runner.
  • Hubs and brokers are connected many-to-many: each hub has its own list of brokers (a key and an address for each), and a broker does not know how many hubs use it. A shared pool is divided among all hubs that know its broker; one broker counts the budget, so a runner is not overloaded however many hubs send orders.
  • The broker assigns an order to a suitable runner: by platform, programs, resources, tags and the timeout ceiling; among the suitable ones, by default to the nearest by zone (local, lan, remote). All of this is policy rules.
  • Priority is decided by policy. By default ci goes first without preempting running jobs, and an order without ci that has waited more than 30 minutes is ordered like ci.
  • An order belongs to the hub key, not to the connection: after a disconnect it remains. The broker cancels waiting orders only if the hub has not appeared for longer than absent_after_min (6 hours by default, policy); a job that is already running finishes, and the result waits for the hub to return.
  • If the broker disappears for 3 minutes, the runner kills its running jobs; it keeps the results of finished ones and hands them over later. The period and the action are policy.

3. Roles and interaction

Three roles — hub, pool broker, runner — and two interfaces between them. Whatever can be decided by policy is decided by policy.

3.1 Hub

  • Lives on a client computer, one per OS user (each user has their own state directory). Accepts CLI commands over IPC, reads the profile, turns it into an order and sends it to the broker. Keeps an outbox: outgoing orders and cancellations are written to disk until the broker confirms them and are repeated after a disconnect; while a run is active, it remembers its sender process. Maintains the log copy in the sender directory, the dashboard, the sender check and the right to cancel.
  • Does not execute jobs, does not hold the resource queue, does not keep the runner registry and does not assign orders to runners. It reads the runner summary, load, queue and history from the broker APIs.
  • Broker choice. The hub learns the zone of each broker relative to itself from the broker: in reply to a connection, the broker reports which network it considers the hub address to be in (a laptop moved from home to the office or to a mobile network — the zone is recomputed at the next connection). The hub enters and stores nothing except the last known zone. The zones are: local (the broker is on the same computer: it is reached over local IPC, not over the network), lan (the hub address and the broker address belong to one network from [networks]) or remote. For each order the hub acts as follows:
    1. Keeps only the brokers whose zone is allowed for the order. An order with the “same computer” requirement (working tree) considers only local and never goes to the network: step 3 does not apply to it, and policy cannot turn this off. If there is no local broker in the hub list or the user is not in [[local_user]], the order is rejected with a reason; if the broker is temporarily unavailable, the order waits in the outbox and is neither moved to another computer nor replaced by a commit; an order with the restriction zone = "lan" gets local and lan and never goes to remote. The order boundary is a hard invariant, not a preference: moving on to the next zone (step 3) is allowed only within the allowed zones, and policy cannot widen the boundary. The hub does not query brokers of disallowed zones at all.
    2. Queries the brokers of the first zone in order (in parallel, with a short timeout from hub-policy.toml): runners, platforms, programs, resources, tags, timeout ceilings, online/offline. The data is not cached; the decision is made on fresh information. The local broker (over IPC) is included in the hub list automatically under the name local if it is configured on this computer: the broker role is recorded by init, its broker.db exists or the broker service is installed. A hub started before the first start of the broker will see it after a restart (up, which brings up both roles, starts the hub only after the broker has answered; if the broker has not answered within the start timeout, up reports it, exits with code 1 and does not start the hub); on a computer without a broker, local is not in the list. If there are no allowed brokers at all (the order zone admits nobody), the order is rejected with a reason and does not wait in the outbox. The hub has a single address for a broker: from another network it must be reachable at the same address (public name, VPN).
    3. If any of them is suitable (a runner is online and meets the requirements; being busy does not exclude it: the order joins the broker queue), the hub chooses by policy and goes no further. If none is, it moves to the next allowed zone. The zone order is set by hub-policy.toml (broker_zone_order): by default from nearest to farthest (["local", "lan", "remote"]), but it can also be the reverse (["remote", "lan", "local"], for example to offload the own computer), or any other. The policy can also require querying all allowed zones at once. The order changes only the sequence within the allowed zones; it does not widen the order boundary.
    A broker that does not answer within the timeout is treated as unavailable for this choice, but it does not give a refusal: if some of the allowed brokers are unavailable and the others answered “no suitable runner”, the hub repeats the query (the total number of attempts query_attempts, including the first, and the pause query_retry_s in hub-policy.toml), and the order waits with the reason “broker X is unavailable”. An unavailable broker of a zone counts as “no suitable runner” for the step of moving to the next zone, while the query retry applies to the whole choice. If the attempts are exhausted and the unavailable broker still has not answered, the order is rejected with a reason in which the unavailable brokers are named; a refusal with figures about the mismatch is given only when all allowed brokers have answered. The data may become stale between the query and the acceptance of the order, so the broker has the final say on admissibility, including the zone boundary (it will not assign the order to a runner outside the allowed zone relative to the client): if it rejected the order, the hub tries the next one by policy. The same applies after acceptance: if the broker returns a not yet started order with a reason (for example, “the installation runner disappeared”, the runner was removed by the runner remove command), the hub goes through the broker choice by the steps above again, excluding the broker that returned it, and immediately places a replacement order without waiting for the user; the zone boundary stays the same. For a “same computer” order there is no replacement (it does not leave the computer), so it ends with a refusal with a reason. If no allowed broker answered, the order waits in the outbox with the reason “brokers unavailable”, and the choice is repeated when connectivity appears. (User decision.)
  • The hub has its own list of brokers: an address and a key for each, issued by the owner at joining. Different hubs can know different brokers or the same ones. If several brokers are suitable, the choice is made by the hub policy: the hub-policy.toml file in the state directory (the list and order of brokers, the selection strategy). By default “the first in the list, the rest are spares”. (User decision.)
  • Outbox. Canceling an order that is still in the outbox without Accepted removes the record locally and still goes to the broker with a “canceled” mark: if the order managed to arrive earlier, the broker discards it on acceptance. An order and a cancellation are first written to the hub persistent queue and delivered to the broker with retries until a confirmation arrives; the broker discards a repeat of the same pair “client key + JobId” (the identifier is assigned by the hub) and answers Accepted only after the order is committed in broker.db; on Accepted the hub deletes the record from the outbox. The result and output go in a separate broker → hub stream with its own confirmation (seq). This way an order survives broker unavailability and a hub restart and is not executed twice. The wait limit in the outbox is both conditions at once, whichever comes first: the order waits while the sender process is alive (unless --detach), and no longer than [outbox] ttl_hours (24 by default); on expiry on_expire decides: fail — the order is rejected with the reason “the broker did not appear in time”, keep — it keeps waiting. The death of the sender also removes an order without Accepted (reaper, 7.3).
  • Return after a disconnect. An order belongs to the hub key, not to the TCP connection. After reconnecting (sleep, network change, hub restart) the hub reconciles its active orders with the broker: what is running, what finished, what was canceled during the absence. If the broker canceled orders because of the absence limit, the hub shows them as cancelled with a reason and does not resubmit them itself. At startup the hub also checks the sender processes: orders of dead senders are canceled under the rule from section 7.
  • Resources per run. The --mem and --cpu flags of submit and run (next to --timeout) replace the profile memory and CPU for this order, upward or downward: the hub puts them into the order requirements instead of the profile values (and instead of the maximum over the steps) and marks them in the order as overridden. Without a flag the profile value applies. The values are chosen by the user; there is no selection from run history. Zero is a flag error (error malformed). The broker checks the ceiling at acceptance: a flag value larger than the pool ([pool]) is rejected with rejected_override_above_pool and figures (“--mem 20000 MB is larger than the pool: the maximum in the pool is 16384 MB”); if the pool exceeds the value of the profile itself, rejected_pool_memory or rejected_pool_cpu remains. A runner with less memory or CPU than the flag specifies does not fit the order, just as with profile values (rejected_no_matching_runner with figures). If both flags are larger than the pool, the refusal names both. Policy rules see the overridden value: the min_mem_mb condition, reserves and quotas are compared against it, and their refusals come with their own codes (rejected_reserved, rejected_quota). The order steps (steps) store mem_mb and cpu from the profile as reference: the pool budget is counted only from the order requirements. (User decision.)

3.2 Pool broker

  • One per pool. Knows only the runners of its pool: name, platforms, programs, tags, resources, load, state. Accepts orders, holds the order queue, assigns them to runners by policy and watches the pool budget. Keeps an outbox for each client: output chunks, results, cancellation confirmations — until the sink confirms them. Keeps the run history on its runners: a record per job and step, full logs, and for each run the client (key, MachineId, label). (User decision.)
  • In code it knows nothing about the hub: the logic does not distinguish consumers, does not branch on them and requires nothing from a client except a key. In the data the client is recorded as a field. For the broker a client is an authenticated connection with a key and a label that the owner set when issuing the key. The broker takes the label and MachineId from the key record, not from the order, so it is impossible to sign as another computer or with another label.
  • Serves an API of two kinds: order intake (create, cancel, receive output and result) and reading state and history (runners with capabilities, pool load, queue, running orders, run history, logs, statistics). Visibility of other clients’ orders is set by policy ([visibility] others_orders): none — other orders are not visible, only pool occupancy; summary (the default) — identifier, state, platform, runner, times and client label, while project, branch, directory, command, note, the --as label, OS user, host and log are hidden; full — all order fields, but not the job output: the full log is given only to the client that owns the run, at any level. The “broker owner” is the OS user with rights to the broker state directory (the computer administrator or the service owner, 3.9); they see everything, including logs, and only they may cancel other clients’ orders under [cancel] others = "owner". The other local users from [[local_user]] see and cancel their own. (User decision.)
  • By default, on a single computer up starts the hub, the broker and the runner as separate processes of one binary, connected over a local channel.
  • One broker per pool; a pool served by one broker is the unit of budget. If the broker stops, the pool idles; orders without Accepted wait in the hub outbox in the “broker unavailable” state, accepted ones are kept on the broker and continue after it returns; runners finish their current jobs and hand over the results after reconnecting.

3.3 Runner

  • A separate process. Connects to the broker itself (there are no incoming ports), registers, executes the assigned jobs, streams the output and returns the result. It does not decide what to run.
  • Settings of the runner owner: the job timeout ceiling, the size and retention of the cache and working copies (section 3.10).
  • Runner capabilities: platforms (opaque owner labels), programs (which programs were found and verified), free disk, tags, the name (unique on the broker). The optional admission rule [accept] reserves the runner for the needed orders (section 4).
  • Several runners can work on one installation (for example, light and heavy); each has its own name, admission rules, platforms and tags; each executes one job at a time. They share the installation pool.
  • If the broker is unavailable for longer than the grace period (3 minutes by default, policy), the runner kills its running jobs; it keeps the results of finished ones and hands them over after reconnecting.
  • The runner accepts jobs only from the broker it joined and executes the commands from the assigned order.

3.4 Order

An order is data, not code: the JobId identifier from the hub, descriptive fields (project, branch, directory, label, note, source) that the broker writes into the run history together with the client, requirements for the runner (a platform or “the same computer as the client”, programs, tags, memory, CPU, disk, exclusive, the farthest zone), the code source (working tree or commit), commands and steps with timeouts, the desired priority. The priority in the order is only a wish; the order is decided by policy.

  • Working tree. A job that needs local files carries the requirement “execute on the same computer”. The broker considers a runner “the same computer” only if the client and the runner are connected to it over local IPC from the same OS user (the OS kernel checks the user); the MachineId values declared at joining do not replace this. Therefore the working tree is available only to a runner of the same user on the computer where the broker is installed. Waiting makes sense only while a live runner of the installation exists: if a suitable runner is online but busy, the order waits and the reason says so (“runner busy”). If there are no runners of the installation or all of them are offline (turned off), the order is rejected immediately at acceptance; the same applies if the runner disappeared after Accepted but before the order started: the broker returns it with a reason, and the hub ends it with a refusal and a hint (“no runner on your installation, start it: up”): there is nothing to wait for, and the agent will not hang. If runners are online but none fits by capabilities, the refusal comes with figures. There is no substitution by a commit. (User decision.)
  • Commit. A job on a runner of another installation checks out the pushed commit (details in 3.7).
  • Who chooses the code source. The source is an order field, and the hub chooses it before routing: an order without a platform uses the working tree, an order with a platform uses the pushed commit, even if a runner of the same computer executes it. The hub checks that the commit is pushed; the CLI only collects the data. A working-tree order has no snapshot: the job reads the live directory of the client, so edits made while it runs reach it; only a commit order is isolated from them.

The semantics of the keys are defined in the subsection “Policy semantics” below; the list of strategies is closed. Fixed rules stay in the code.

  • What stays in the code and is not set by policy: the protocol and versions, authentication and key verification, process isolation and kill of the tree, storage integrity. The policy chooses what is allowed, not how the check works.
  • Only the person at the broker computer edits the policy. The file is edited locally, and policy reload is accepted only over the local channel; it cannot be changed remotely, and a compromised hub changes nothing. A special remote owner key is a possible extension. (User decision.)
  • Protection from the policies themselves. Every rule is checked on load; a broken file is rejected and the previous policy stays. An unknown strategy name is rejected. Any delay or rejection names the rule that fired (for example, “rule ci-reserve: 2 of 8 cores are reserved”). An empty file does not break the system: the default values apply.
  • Trusted and claimed attributes. Trusted ones come from the key record (key, label, MachineId); claimed ones arrive in the order (source, project, tags, size, --as) and the client can name them anything. Rules for priority, reserve, quotas and grouping by claimed attributes are allowed only together with a condition on the trusted label; otherwise the file is rejected on load. The order submission time (FIFO and aging are counted from it) is assigned by the broker itself, by its own clock at the moment of acceptance; the time sent by the hub is not used, so a client cannot “age” an order and bypass the rules.
  • Reload without stopping: policy reload checks and applies the file; warnings (for example, an overlapped rule) are printed but do not prevent applying, and changes to [listen] and [networks] take effect only when the service restarts, which the command reports. The new policy applies to new orders and scheduler decisions; orders already accepted are not reconsidered, running jobs are not affected, and a changed [grace] is sent by the broker to connected runners. A call without rights to the state directory is rejected.
  • Commands in an order. By default a client with a key is trusted (like a GitHub self-hosted runner); for individual keys the policy can restrict orders to names from the runner list. (User decision.)

Policy semantics

  • Rule order. The [[rule]] rules are checked from top to bottom. For each decision field (priority, reserve, quota, weight) the first matching rule that sets this field applies; rules with different fields complement each other. So the answer to the question “why this priority” is one line: “rule number N”. On load, a rule that can never fire (an earlier one fully overlaps it) produces a warning.
  • priority is a number, larger means earlier; 0 without a rule. reserve = { cpu, mem_mb } is the share of pool resources that only orders matching the rule receive: other orders do not take it, even when it is free. quota = { max_running, max_mem_mb } is the ceiling of simultaneously running jobs and memory for a group (by group_by). weight is the group weight for the weighted strategy.
  • Strategies. priority-fifo: by descending priority, within a priority by submission time. fair-share: within a priority, groups take turns, and the one that has gone longest without receiving resources goes first. weighted: like fair-share, but the group share is proportional to weight. Aging (age_after_min) applies on top of any strategy.
  • The when conditions. A rule matches when all specified fields match; an empty or missing when matches everyone. Trusted fields: client_key, client_label, machine_id (from the key record). Claimed: source, project, submitter_label (the --as label), tag (the order asks for this tag) and min_mem_mb (the order asks for at least this many MB). A rule with a claimed field and any of priority, reserve, quota, weight without client_label causes the file to be rejected. Rule names are unique; weight is at least 1.
  • Default values. Without [[rule]] a single rule ci-first applies (client_label = "ci", priority = 100); rule = [] sets a policy without rules. 3.6 Pools and resources

  • A pool is a set of installations that work simultaneously and share one budget: memory, CPU and a set of exclusive tags. The limits belong to the computer owner and are described in the broker policy, not in the project. Profiles only say what a job needs.
  • Runners of one pool share limits and occupied tags. A Windows host and a runner in Docker on it are one pool, so the scheduler sees their load together. Shared use cannot be reliably detected, so the owner declares it.
  • Several users on one computer. There is one pool, so there is one broker. It runs as an OS service (3.12), so it does not depend on who is logged in: a user logging out does not stop the pool. Users' hubs and runners connect to the service over local IPC; the list of allowed users and their labels is [[local_user]] in policy.toml; it is also possible to connect over the network (127.0.0.1) as an ordinary client. “The same computer” requires the hub and the runner to connect over IPC as the same OS user: for each user the working tree works with that user's own runner and is not accessible to another user.
  • A runner belongs to the pool of the broker it joined. A runner that shares nothing with anyone is a pool of one runner with its own broker.
  • A pool is the shared limit of a computer, and pools do not nest. Two pools on one computer are two independent budgets: this is right for mutually exclusive installations (dual boot), while for simultaneously running ones the owner declares one pool.
  • A runner executes one job at a time; parallelism is the number of working runners, and it is bounded by the pool limits. The limits are static numbers from the owner; the broker keeps accounting against the declared numbers. By default it does not measure the real load, so outside work that is not in the queue is not counted; the owner can enable admission by the real load of the runner machine with [admission] foreign_load = "wait" (3.14).
  • A ci runner is an ordinary client: its jobs place orders through the hub of its computer, and pool resources are counted once, per order. The ci label is assigned to the key of the hub of that computer, so the owner keeps a computer with a GitHub runner separate from agent sessions, otherwise their orders would get the same priority.

3.7 Routing and code delivery

  • An order fits a runner if one of the requested platforms, all tags, programs and disk match, the timeout is not above the runner ceiling, and the pool can provide the resources. Without a platform the order goes to a runner of the same installation as the client: both are connected to the broker over local IPC as one OS user (this is how “the same computer” is defined everywhere).
  • A profile may have several platforms and a command for each ([profile.X.platform.ios]). run --platform name accepts exactly one platform and creates one job; for a second platform the user or agent runs the command again (that is a second independent job, there is no group of runs). Without --platform the platform is taken from the profile, and if there are several there too, the command asks to specify one.
  • Choice among fitting ones by default: a runner on the client computer, then on the local network, then remote ones; among those equal by zone, the one with the most free capacity. This is a broker policy rule (runner_zone_order), the order can be reversed or set to any; it does not affect the order boundary (3.1). Eligibility always comes first: a near runner that does not fit is not chosen instead of a far one that fits. A preference is not a reservation: if the near one is busy and the far one is free, the order goes to the far one at once.
  • Zone is the distance of a runner from the client: local (the client and the runner are connected to the broker over IPC as one OS user; the IPC of another user of the same computer counts as the broker host address, that is, the zone of the network from [networks] where the host sits, usually lan), lan (the client and runner addresses belong to one network from [networks]), remote (everything else, including a mobile network and an address outside the list). The client address is the one from which the broker sees the connection (the source address). The owner describes the networks once in the broker configuration: [networks] home = ["192.168.1.0/24", "127.0.0.1/32", "172.17.0.0/16"]; the broker host, its loopback and the Docker bridge belong to the network where the host sits. The broker reports the zone to both hubs and runners relative to the client, so the order restriction is checked against the runner zone, not only the broker zone. A project can narrow the zone with the zone field. Order priority and the preference among runners are independent: the first orders the queue, the second chooses the runner for the head order.
  • An order for which no registered runner fits by characteristics (for “the same computer”, no runner of this installation) is rejected on acceptance with a reason; for “the same computer” the same happens if the installation has no runners or all of them are offline; if all fitting runners are offline, the order waits and shows the reason.
  • Code delivery. A runner of another installation checks out the pushed commit. The hub refuses a remote order if HEAD is not reachable from a remote branch, and asks to commit and push (no MR is needed); uncommitted changes (modified, staged and new files, as git status shows them) are ignored with a warning and do not block the order: the hub returns it to the sender together with the JobId (submit and run print it to stderr) and writes the line “warning: uncommitted changes are ignored: the runner checks out the pushed commit <commit>” to the log copy. The runner keeps one shared bare mirror per project, runs git fetch in it and creates a separate working copy (git worktree) for each job with a clean detached checkout, so jobs of one project do not interfere with each other; access to the repository uses the runner's own git credentials, and the core does not store them. Preparing the working folder is not built-in magic of the core but an ordinary sequence of commands in the order (the source step, run before the profile steps). For a “same computer” order this is simply cd to the sender working directory, nothing is cloned. For a remote one: cd to the project mirror on the runner (the path from [workspace]), git fetch and git worktree add at the needed commit; if the mirror does not yet exist on the runner, first mkdir and git clone --mirror <address>. The hub builds this sequence by default for git; the parameters are the placeholders {repo_url} (from git remote get-url origin), {commit}, {branch} and {workspace}, the last one substituted by the runner itself (the mirror lies inside its state directory, so runners do not share it and do not race on git fetch); the job working directory is set by the source steps themselves, and the profile steps start in it; a profile may replace it with any commands of its own (another mirror, sparse checkout, monorepo). Credentials for these commands stay on the runner. The profile for a remote order is read from the commit (git show <commit>:...). Delivery goes through origin by default; packing the commit into a file through the broker is a possible extension through policy. (User decision.)
  • A runner accepts orders of any project; the restriction is its own git credentials. There is no project list.

3.8 Joining a pool

As with GitHub self-hosted runners: the joining party connects to the broker itself and needs no incoming port.

  • On the broker: localrunner broker add [--name client-name] [--label label] (the client name is unique on the broker, client list and client remove work by it; the label is shared by a group of clients) prints the address and a one-time code (lives 1 hour by default, [join] code_ttl_min in the policy) with the broker certificate fingerprint: the code is a composite token, the fingerprint is embedded in it, so join accepts only the address and the code. If the broker has several addresses in [listen], the first is printed, and another is set with --address. The code is not a key: the key is created on joining, has no expiry and lives until revoked, so after joining the runner works without further actions. For several runners broker add --runners N issues a code for N joins (each still creates its own key). The command uses the admin channel of the broker: for a broker installed as an OS service it needs an administrator (Windows) or the OS user of the broker (Unix), and a refused access is reported with that action. Because join refuses to run as an administrator, broker add --code-file file hands the code over: the administrator writes it to a new file, the ordinary user passes the file to join --code-file.
  • On a new computer: runner join <host:port> <code> [--name name] [--count N] [--config file] for runners (platforms, tags and programs are taken from runner.toml, the flags --platforms and --tags override them; runner name: --name wins over name from runner.toml, with neither the computer name is used, and with --count N the names are name-1 … name-N) or hub join <host:port> <code> [--name broker-name] for a hub (the broker name in the hub list and in hub-policy.toml is set by the hub owner; by default it is the broker address). The joining party (the hub or each runner separately, with its own code) creates its own key pair, the broker stores the public key, the code is redeemed. The code counter (uses_left) decreases only after the join is written to broker.db, so an interrupted join loses only the unredeemed parts. Exhausted and expired codes are deleted when the next code is issued. After that authentication is by key; a runner key registers only the name under which it joined: a hello with another name is rejected (unauthorized), so one key does not multiply runners for itself and does not take over the name of a runner in the removed state.
  • The owner enters the broker address by hand. There is no network autodiscovery (mDNS and the like): the broker announces nothing and listens for no discovery, and address spoofing is ruled out by the one-time code and the certificate fingerprint. (User decision.)
  • The channel is TLS with the broker certificate, pinned by the fingerprint from the code (self-signed, created on first start); an intermediary on the network can neither join nor impersonate the broker.
  • runner list, client list, runner remove, client remove on the broker; removal revokes the key at once. A key belongs to one member, so revoking a runner does not affect the hub and other runners. On revocation the broker breaks the connections of this key, cancels its waiting orders, the action on running ones is determined by the policy ([orphans] running), and deletes its outbox.
  • Local owner. A connection over local IPC needs no key: the OS user is reported to the broker by the kernel, and the user record is taken from the [[local_user]] list in policy.toml (by default it has one user, the one who installed the broker; when installing through sudo or UAC the original user is taken, not root or the administrator account). Each user in the list has their own client record: the client key is the pair “local user + OS user”, and the label is taken from the list. So the idempotency key and the right to cancel do not overlap between two users of one computer, and the ci label is received only by the one to whom the owner assigned it. A user outside the list is rejected. A hub on the broker computer does not need to join by code.
  • The broker listens on the network only on explicit addresses from its configuration (there may be several, for example LAN and the Docker bridge) and only while an unredeemed join code is issued or at least one computer is registered. There are no default addresses, a wildcard address (0.0.0.0, ::) is rejected at start; the only exception is address = "container" inside a container (10.4). The dashboard is always on loopback.
  • When joining over the network the broker rejects a MachineId equal to the MachineId of the broker itself.
  • A runner trusts the broker it joined; do not point a runner at a broker that accepts orders from those you do not trust.

3.9 Failures and protocol

  • Protocol. A persistent connection with a heartbeat every 15 seconds; a runner that misses 3 is considered offline. Messages: join (code, public key, capabilities), capability query, order and the reply to it (Accepted or rejection), assign, Started (the runner reports that the job has started; the broker sets started_at by its own clock, so clock skew does not affect the lost deadline), cancel, log chunk, step and job result, heartbeat, resume (after reconnecting the sink reports the last received seq for each JobId, and the sender resends the rest), drain and Bye (a runner or hub leaves normally), read requests for the CLI and dashboard (state, history, explain, log stream, subscription to queue and runner events), the runner report on service state (which are warm, how much memory) and the broker command “stop service” (eviction, 3.11). Administrative commands (policy reload and the like) do not exist in the protocol over the network: a network connection gets a rejection, and they are accepted only over local IPC from an OS user who has rights to the broker state directory (the computer administrator or the service owner). There is no separate “admin” mark in the configuration: whoever has access to the broker computer manages it (edits policy.toml, calls policy reload, broker add, runner remove, client remove); users from [[local_user]] without these rights only place their own orders and view their own. Every job message is idempotent by the client key, JobId and the seq number (a counter separately for each “job, direction” pair), so a repeat after reconnecting changes nothing. The handshake carries the protocol version; the broker refuses an incompatible major version and says so, so there is no need to update everything at once within a major version.
  • Program update. The owner updates each computer themselves; compatibility is ensured by the protocol version (within a major version roles of different versions work together, with an incompatible version the broker refuses with a clear message). There is no binary distribution and no self-update, so there is no additional outgoing connection either. (User decision; self-update through the broker is a possible extension.)
  • Live log. The runner streams chunks to the broker, the broker saves the log and relays the chunks to the hub; the hub writes temp/runner/<job-id>.log in the sender directory, and agents read a single file. The runner and the broker each keep their own outbox (the broker keeps results for an absent hub for [results] keep_hours and then deletes them, the runner keeps them until delivery and discards them when the broker removes the runner): on a break the runner flushes output and results to the broker in order without duplicates, and the broker delivers chunks, results and cancel confirmations to the hub in the same way.
  • Hub gone. The broker holds the orders of this hub until absent_after_min (counted from the last client heartbeat, and after a broker restart from the moment it started; for a local client the broker maintains last_seen over the IPC connection), then acts by policy; a running job lives out, and the result and output wait in the broker outbox until the hub returns (retention and period are policy).
  • Broker gone. The pool idles, orders without Accepted stay in the hub outbox, accepted ones are kept on the broker; the runner lets jobs finish and kills them when the period expires.

  • Stopping a runner. A runner does not listen on the network, but it has a local control channel in the state directory (IPC, access only for the OS user): down name passes the command through it. With --drain the runner sends drain to the broker, the broker stops assigning it orders, the runner finishes the current job, shuts down services and sends Bye; with --cancel it cancels the job with the reason runner_stopped, then Bye. Without flags down works as --drain. If the broker is unreachable, the runner still stops taking orders and finishes the job, and Bye is sent when the connection appears; after Bye the broker marks the runner offline.
  • Runner revocation. On runner remove the job that was running on it immediately gets lost with the reason “runner removed”, and the resources return to the pool; the result of such a job, if the runner still sends it, is not accepted. The runner understands an authorization failure as a command: it immediately kills the job process tree and does not wait for the grace period.
  • Runner gone. A runner without a heartbeat gets the state offline; the same rule (15 seconds, 3 misses) applies to a client: from the last heartbeat the broker writes machine.last_seen and counts the absent_after_min period. The period passed to the runner by the broker can only be shortened, not increased, by the runner in runner.toml, otherwise it would kill the job later than the broker returns its resources. A job that was running on it and did not report within timeout_s from the moment of Started plus the policy grace period ([grace] lost_min, 3 minutes by default) moves to lost: memory, CPU and tags return to the pool budget, and the hub receives the result lost. The period after which the runner itself kills jobs when the broker is unreachable is passed by the broker at registration, the runner stores it locally and can override it in runner.toml.
  • Dead sender across computers. The hub watches the sender process on its computer and, if it dies, cancels the orders at the broker (submit --detach and handles keep their meaning).
  • ci on another computer. A GitHub job calls run through the hub of the computer with the runner al-ci; the hub is connected to the broker with its own key with the label ci, and there are no special messages for CI in the protocol.

on        = ["passed", "failed", "killed", "cancelled", "timeout"]   # default: all
  • Name. --name wins over name from the file; with neither, the computer name is used. The runner name is also the name of its state directory, so names made only of dots and names with path separators are rejected. --count N (from 1 to 64) starts name-1 … name-N with a shared runner.toml template, each with its own directory.
  • Resources. mem_mb and cpu are what the runner offers to the pool. Without them the runner declares all memory and all cores of the host. The runner executes one job at a time and gives it all the declared resources; to share the computer between jobs, the owner starts several runners (--count) with smaller values. Zero and values larger than the host has are an error at start; if the host memory could not be measured, mem_mb is required.
  • Elevated rights. allow_elevated (default false) is the only way to run a runner as root, administrator or SYSTEM (section 3.12). If the rights of the process could not be determined, it is considered elevated.
  • Broker user. allow_same_user_as_broker (default false) allows the runner to start under the same OS user as a non-service broker that accepts foreign clients; without it such a runner does not start (section 3.12).
  • Timeout ceiling. max_job_timeout_s limits a job on this runner. The profile timeout is an order requirement and is not silently trimmed. A job whose timeout is above the runner ceiling is not suitable for this runner (the runner does not silently take it with a trimmed timeout), and the wait reason says “timeout 7200 s required, runner ceiling 3600 s”. The “trim instead of reject” behavior is enabled by the broker policy: with [limits] timeout_above_max = "trim" (default "reject") an order with a timeout above max_job_timeout_s is accepted with the timeout trimmed to that limit (step timeouts also not above it); the broker reports the new timeout in Accepted (optional field timeout_trimmed_to), and the hub writes the line “=== timeout trimmed by the broker policy: 7200 s -> 3600 s ===” to the log copy and to whoever is waiting. Trimming applies only to the broker limit: a runner whose ceiling is below the timeout is still not suitable. The profile must still set timeout_s. The broker limit (max_job_timeout_s in policy.toml) rejects the order at intake with a reason; the hub does not change the timeout.
  • Limits, environment and cleanup. [limits] enforce, mem_headroom, disk_headroom, [job_env] and [[cleanup]] are described in 3.14 with defaults and validation. An invalid value is a file error and the runner does not start.
  • Cache. A profile can list named caches (cache = ["gradle", "cargo"]). For each client, project and name the runner keeps a persistent directory between runs (the cache key is “client key, project, name”; the owner enables a shared cache for several clients with the rule [cache] share = "project" in policy.toml, default share = "client", so that one client cannot plant an artifact in the build of another; the project is an attribute declared by the client (3.5), so with share = "project" the shared project cache is obtained by any client that names this project, including a client with [commands] mode = "named") and reports its path to the job in an environment variable (LOCALRUNNER_CACHE_<NAME>); what lies in it and how to use it is decided by the job command. The core does not know that this is a Gradle or Cargo cache.
  • Size and retention. Before starting a job and on a timer, the runner deletes entries not used for longer than retention_days and, if the cache exceeds max_size_gb, the oldest ones (lru) down to the required size. A cache used by a running job is never deleted; a job that lacks space even after cleanup waits or fails with a reason.
  • Command names. [commands] maps a name to a command line. The runner reports only the names to the broker; the lines stay on the runner. For a client to which the broker policy assigns [commands] mode = "named" (3.5), only a name is allowed in the command of each step: the runner executes its own line and never the text of the order, and a name without a description in [commands] is a refusal without a run. An empty command line is a file error.
  • Working copies. Checkouts of remote jobs (section 3.7) follow the same rules: retention and size in [workspace].
  • The runner reports to the broker the timeout ceiling, the cache size and its fill level; they are visible on the “Runners” page and in the metrics.

3.11 Runner services: policy with guarantees

A program that a job needs to keep running (a build daemon, an emulator) is described as a runner service. When to start and stop it is decided by the owner policy; the safety guarantees are built into the code and are not disabled by the policy. The core still does not know what program is inside. The format is a draft; by default there are no services, and the job itself starts everything it needs (profile steps).

[service.build-daemon]
start        = "gradle --daemon"
ready_check  = "gradle --status"
stop         = "gradle --stop"
ready_timeout_s = 60
memory_mb    = 2048            # counted in the pool budget while the service is alive
lifetime     = "idle"          # per_job | idle | keep
idle_timeout_s  = 900
max_lifetime_s  = 14400        # always required
reuse        = "same_client"   # same_client | same_project | any
  • Where things are described. The services themselves (start, check and stop commands, memory, lifetime, reuse) are described by the runner owner in runner.toml in the [service.*] sections: the programs and commands are on the runner. The broker rules (who may request a service, eviction of idle ones) are in policy.toml: 
    [services]
evict_idle = true   # the head order lacks resources, and idle services hold them: stop the services
  • Eviction. If the head of the queue lacks memory and part of it is occupied by warm services without work, the broker orders the runner to stop them with the regular stop. A service that is working for a job is not touched; the next job starts the service again. Enabled by default (evict_idle), the owner can disable it.
  • Reservation. A service starts only as part of an order and only after the broker has reserved its memory in the pool budget; the runner never starts anything “just in case” on its own.
  • The policy decides: which services exist, how they start and are checked, the life rule (per_job — stopped after the job; idle — after idling; keep — lives as long as the runner lives), and who may reuse a warm service (reuse). A profile asks for a service by name: services = ["build-daemon"].
  • Guarantees that the policy does not disable:
    1. Bounded life. max_lifetime_s is required for every service, like the job timeout: there are no unlimited services.
    2. Resource accounting. The memory of a live service is part of the pool budget; the broker does not give it to other orders while the service is alive. The CPU of a service is not reserved: [service.*] has no cpu key, the runner processor is already accounted for the job (cpu of the order), and an idle service hardly uses it. A warm service cannot overload the computer unnoticed.
    3. Full cleanup. A service is started in a process container (Job Object, cgroup, process group). Stopping ends the whole tree; if stop hangs, the service is killed forcibly. The full guarantee, including detached descendants (setsid, double fork), exists on Windows (Job Object) and on Linux with cgroup v2. Without cgroup and on macOS the guarantee is best effort: a process group and a walk over descendants by parent, and detached descendants are closed by the regular service stop command and by the check at start.
    4. Does not outlive the runner. When the runner stops, fails or restarts, the services are stopped; orphaned processes of the previous run are found by the record in the state directory and killed at start.
    5. Readiness is required. An order does not get a service until the readiness check has passed; a failure of the start or of the check ends the job with the reason “service did not start” instead of hanging. A failed service is restarted a limited number of times, then marked unavailable, and the runner stops being suitable for orders that need it.
    6. Isolation. A warm service is reused only within reuse: by default the same client. The state of one client does not leak to another.
    7. Visibility. Every start, stop, restart and reason goes to the log and the metrics (service_up, service_starts_total), and the “Runners” page shows live services, their memory and the remaining life.
  • The order requirements for a service are part of runner admissibility (3.7): a runner without the needed service, or with an unavailable service, is not suitable for the order.

3.12 Runner user

  • By default the runner runs under the OS user that started it (up), and all job processes run under the same user. This way it sees the tools, caches, devices and working directories of the user; for “same computer” orders this is necessary. (User decision.)
  • The code does not switch users. If isolation is needed, the owner creates a separate OS user (for example, lr-runner) and starts the runner under it with OS means. A runner that accepts orders from foreign clients or from remote computers is recommended to be kept under a separate restricted user: it executes commands from the order and must not see foreign files.
  • Runner under the broker user. If the broker runs not as a service but under the same OS user as the runner, and the policy allows clients any commands ([commands] not named), a command from the order of any client gets the rights of the pool owner: it opens the admin channel of the broker (issuing codes, deleting runners and clients, editing and reloading the policy), sees the history of all clients and reads the broker key and its databases, that is, it can impersonate the broker. Therefore, when the broker accepts clients other than the owner (there is a [listen] address or a [[local_user]] entry with another OS user; the entry of the owner itself, which init writes, does not count; without policy.toml the default policy applies), the runner of this installation refuses to start: runner run, up (the runner does not start, exit code 1, the other roles start) and autostart on runner end with the error “the runner refuses to start: … or set allow_same_user_as_broker = true in runner.toml to accept the risk”, and doctor marks the runner as an error. An owner who accepts the risk writes allow_same_user_as_broker = true in runner.toml (default false): then the runner starts, and doctor, up and the runner itself warn. A single installation (the broker accepts only the owner) is not affected: neither a refusal nor a warning. The same OS user is determined by installation: the runner and broker of one state directory; a runner of the same user from another state directory is not recognized. To remove the risk: a runner under a separate user, the broker as an OS service, or [commands] default = "named".
  • A guarantee that cannot be disabled: the runner refuses to start as root or administrator (SYSTEM on Windows) until the owner explicitly allows it in runner.toml (allow_elevated = true).
  • The broker is an exception: an OS service. The broker executes nothing, so it can and should run as a service that does not depend on user logins: a Windows service, a systemd system unit, a LaunchDaemon. It runs under a separate unprivileged account (not root, not SYSTEM); the state directory and policy.toml belong to it, and the owner of the computer edits them with administrator rights. Runners and the hub remain user processes. If a user logs out, only their runners and hub disappear, and the pool of other users keeps working.
  • Windows. A runner with an emulator or graphics needs an interactive user session, so such a runner, like ci, is not a system service. A service suits only runners without graphics and runs under a service account, not under SYSTEM.

3.13 Job secrets

A secret is a value that a job needs in its environment (access to a private package registry, a signing key) but that must not be in the order. (User decision: secrets live only on the runner.)

[secret.registry_auth]
from = "env:REGISTRY_AUTH"         # environment variable of the runner process

[secret.signing_key]
from = "keychain:release-signing"  # OS store (Credential Manager, Keychain, libsecret)
  • A profile asks for a secret by name: secrets = ["registry_auth"]. The value is put into the job environment on the runner, and in the order, outbox, history and logs of the system there is only the name.
  • Admission is decided by the policy of the broker: which client (label) may request which secrets. The broker does the check at order intake, like the server at GitHub: a request for a disallowed secret rejects the order at once with a reason (“secret signing_key is not allowed for label agent”), before the queue. The broker puts the allowed names into the task for the runner (Assign); the runner does not know the policy, it only takes the values of these names from its store and puts them into the job environment.
  • Guarantees: the value of a secret is written to no log or metric of the system; the runner masks the exact values of secrets in the job output before sending it to the broker (masking protects against accidental printing, not against a command that deliberately transforms the value); a secret is visible only to the processes of that job and only on the steps that requested it; runner services get a secret only on an explicit request.
  • Clean environment. The job environment is built from scratch: an allowlist (PATH from the runner settings, HOME, TEMP, TMP and TMPDIR (all three point to the job's private temporary directory, see 3.14), the LOCALRUNNER_* variables) plus the requested secrets; the job does not inherit the environment of the runner process, including the env: secret sources. This does not protect against a command that reads the key store or files of the same OS user, so admission of secrets by label is reliable only together with [commands] mode = "named" or with a runner under a separate OS user (3.12).
  • A secret can also be requested on a separate step: { name = "publish", command = "...", secrets = ["signing_key"] }. A service that received a secret cannot be reused more widely than reuse = "same_client".
  • If the source of a secret is unavailable (no variable, store locked), the job ends with the reason “secret not found: name” instead of starting without it.
  • The history and the dashboard show the names of the requested secrets, but not the values.

3.14 Job limits, cleanup after a job and foreign load

The cpu, mem_mb and disk_mb declared by a profile used to serve the scheduler only. This section describes what makes the job itself obey them, how leftovers outside the job are removed, and how the real load of the machine is taken into account. Limits are on by default in the warn mode: without configuration the runner records the peaks of every job, writes a warning to the job log when the declared mem_mb or disk_mb ceiling (times 1.25) is exceeded, caps the CPU share to the declared cpu and limits the process count; nothing is killed unless the owner chooses kill. To turn everything off, set mode = "off" in the broker [resources] or enforce = "off" in the runner [limits]. Foreign-load admission stays off by default. The core stays generic: it knows no container, build daemon or toolchain; everything specific is a command or a number written by the owner.

# policy.toml of the broker (all tables are optional)
[resources]
mode          = "warn"       # off | warn | kill; warn is the default; "off" turns the limits off
mem_headroom  = 1.25         # ceiling = declared mem_mb x factor
disk_headroom = 1.25         # ceiling = declared disk_mb x factor

[admission]
foreign_load    = "off"      # off | wait
mem_headroom_mb = 256        # memory that must stay free on top of the order's mem_mb

# runner.toml: [limits] enforce / mem_headroom / disk_headroom, [job_env], [[cleanup]] (see 3.10)
  • Who decides. The broker [resources] is sent to the runner with every assignment. The runner owner overrides it in runner.toml: [limits] enforce replaces mode, mem_headroom and disk_headroom replace the factors; the machine owner's value wins over the broker's. mode is off, warn or kill (default warn, also when [resources] is present without mode or absent altogether); a factor is a number from 1.0 to 100.0 (default 1.25); anything else is a file error (the broker rejects the policy, the runner does not start). policy check warns about a factor that has no effect with mode = "off".
  • Ceilings. They are applied only when the mode is not off and only to a resource the job declares (a declared 0 means no limit). Memory: mem_mb times mem_headroom. Disk: disk_mb times disk_headroom. CPU: the declared cpu cores of CPU time; this is a share, not pinning to cores: a job may start any number of threads but in total gets no more than this, and it is a hard cap. CPU never causes a kill, the job only runs slower. Process count: max(512, cpu x 256).
  • Modes. off (chosen explicitly) limits nothing and only records the peaks. warn (the default) writes a warning line to the job log once the ceiling is exceeded and lets the job go on. kill ends the whole process tree; the job becomes failed with the reason resource_exceeded and the text declared mem_mb exceeded: declared X MB, peak Y MB (or disk_mb). Turn kill on after a history of peaks has accumulated (section 8): the owner should move from the default warn to kill once the peaks in the history show that the declared values are right. Note: this default changes the behaviour of existing installations; the CPU cap and the process limit apply from now on, even though nothing is killed. A job that exits with code 0 while its peak exceeded the ceiling stays passed.
  • Mechanisms of memory, CPU and processes (lr-exec):
HostenforcementHow
Windowsosthe job process tree is in a Job Object: JOB_MEMORY memory limit, hard CPU rate cap, ActiveProcessLimit
Linux, cgroup v2 controllers delegated to the userosa scope created by systemd-run with the properties MemoryMax, CPUQuota, TasksMax

  • The watcher. It samples the job process tree about every 250 ms: resident memory (RSS) on Unix, so the value is approximate, committed memory on Windows. In the watcher mode the CPU is lowered by the process priority (nice) and the process count limit does not apply. The watcher is the arbiter of memory kills in every mode; where the OS limit exists, it is only a backstop 10 % above the ceiling, so that the job ends with a proper reason before the OS refuses an allocation. The runner reports the mechanism in its capabilities (enforcement: os or watcher); it is shown in runners and on the dashboard. On macOS all memory figures are approximate.
  • Disk. A watcher sums the sizes of the files in the job's working directory and in its private temporary directory <runner state dir>/tmp/lr-<job-id> about every 2 seconds (the shared system temp is not measured; symbolic links are not followed); the ceiling is disk_mb times the factor, with the same modes. Admission also uses the factor: the runner checks the free space of the working volume against disk_mb times the factor (a configured factor applies even with mode = "off"). OS quotas are not used.
  • Private temporary directory. Every job gets the directory <runner state dir>/tmp/lr-<job-id> (not inside the system temp; it is always used and does not depend on a configured temp); the job's TEMP, TMP and TMPDIR point to it. It is created before the first step, counted as the job's disk usage together with the working directory, and removed after the job, also after kill and cancel: up to 8 attempts 250 ms apart (on Windows the files of a just-killed process are briefly locked). After a runner crash, everything under <state dir>/tmp is removed when the runner starts (recovery). Previously a job wrote to the system temporary directory; now temporary files go to this directory, and commands that relied on a shared temp will not see it.
  • Peaks. The peak memory and peak disk of every finished job are written to the history in any mode (section 8).
  • Cleanup after a job. A job and its tree are limited, but containers started through a daemon, build daemons and similar leftovers live outside the job. [[cleanup]] in runner.toml lists commands that run after every job outcome: name (unique, required), command (required, not interpreted by the runner), timeout_s (1 to 3600, default 60), on (a non-empty list of passed, failed, killed, cancelled, timeout; default all five; killed means resource_exceeded or the lost broker). The hooks run one after another in the order of the file, with the job environment plus LOCALRUNNER_JOB_ID and LOCALRUNNER_JOB_LABEL (lr-<job-id>, unique per job). A hook failure never changes the job result: a warning line goes to the job log and an entry to the runner diagnostics. A job cut short by a runner crash or restart gets its hooks once, at the next start, as killed (before its result runner_restarted is sent; the job id comes from the active-job marker), so a hook must be idempotent. Hooks do not run for an order rejected at intake. Examples (removing the containers labeled with the job, stopping a build daemon) are commands of the owner, not behavior of the core.
  • Job environment. [job_env] adds variables to every job and every hook (for example, to disable daemon reuse). The names are checked (letters, digits, _, no leading digit); PATH, TEMP, TMP, TMPDIR and LOCALRUNNER_* are forbidden; HOME is allowed. The owner's value replaces a variable of the same name already in the environment. LOCALRUNNER_JOB_LABEL is added to a job only if at least one [[cleanup]] exists.
  • Foreign load. The runners send the real load of their machine with the heartbeat: free memory (MB), the CPU busy share (%) and the number of cores. With [admission] foreign_load = "wait" (default off) an order waits while the machine of the chosen runner has less free memory than mem_mb plus mem_headroom_mb (default 256), or fewer free cores than the order's cpu. The reason is shown in status and explain: busy with foreign processes: 800 MB free, 2000 MB needed or busy with foreign processes: CPU 95%, 4 cores needed. The declared cpu of the broker's own running jobs on the same machine is subtracted from the busy share, and the memory declared by jobs assigned after the last sample is subtracted from the free memory, so nothing is counted twice. Running jobs are never paused or throttled. On macOS the reader runs vm_stat (free, inactive and speculative pages) and ps -A -o %cpu (the sum over processes divided by the logical cores). A runner without load information (an older one) is admitted as before. policy check warns when mem_headroom_mb is set with foreign_load = "off" or is not less than the pool memory.
  • Not in this version: limits on disk I/O, pinning to cores, pausing running jobs, a proxy for the Docker socket, OS disk quotas; the process count limit in the watcher mode.

5. Profiles and steps

A profile lives in .localrunner/profiles.toml of the consumer repository. These are the requirements of a job, not settings of a computer.

[profile.rust-unit]
command = "cargo test --workspace"
timeout_s = 900
mem_mb = 4096
cpu = 4
tags = ["cargo"]

[profile.android-tier]
command = "pwsh scripts/android-tier.ps1"
timeout_s = 3600
mem_mb = 12288
cpu = 6
tags = ["gradle", "emulator"]
exclusive = ["gradle", "emulator"]
  • timeout_s is required; there is no default value and no unlimited run. The upper limit is set by the broker policy (rejection at intake) and by the runner ceiling (a runner with a lower ceiling is not suitable, section 3.10); the timeout is not silently trimmed.
  • mem_mb and cpu of a profile can be replaced for one run with the flags submit --mem 6g --cpu 4 (memory in MB — 6144 — or with a unit: 512m, 6g; CPU — an integer number of cores, at least 1). The profile does not change; a flag value larger than the pool is rejected by the broker with the code rejected_override_above_pool (3.1).
  • cache — named caches kept on the runner between runs of this project (section 3.10); the core does not know their contents.
  • tags — resources that a job holds for the duration of the run; exclusive — tags that no other running job can hold.
  • The core does not interpret command, it only starts a process. Several commands — steps. The requirements for the runner (memory, CPU, disk, programs, platforms, tags) are listed by the profile itself (section 4).

5.1 Steps

A profile has either command (one step) or steps (an ordered sequence), but not both.

[profile.rust-gate]
timeout_s = 1800
tags = ["cargo"]
steps = [
  { name = "fmt",    command = "cargo fmt --all --check", timeout_s = 120 },
  { name = "clippy", command = "cargo clippy --workspace --all-targets -- -D warnings", timeout_s = 600 },
  { name = "test",   command = "cargo test --workspace", timeout_s = 900, mem_mb = 8192 },
]
  • One job is one place in the queue: the steps go one after another, and other jobs do not start on the same runner between them.
  • Resources are taken once: the maximum over the steps (memory, CPU) and the union of tags and exclusive; a step can override mem_mb and cpu, and only adds its own tags to the tags of the profile. There is no per-step acquisition, so there is no partial holding and no deadlock.
  • Each step has its own required timeout_s, which runs inside the remaining job timeout (also required); a step is killed at the earlier of the two.
  • A failed step stops the job, the remaining steps are skipped. continue_on_failure = true allows continuing, and the job result stays failed.
  • Branching, conditions and dependencies between steps are not part of the core — use a script inside command.
  • Several independent jobs from one session — several submit calls: each is queued separately, and jobs of other sessions can run between them.

6. Queue and scheduling

  • The order queue lives on the broker. The policy determines the assignment order; by default it is strict priority (orders from the ci client go before the others), and within a priority the order of submission (FIFO). A job starts when a runner that satisfies the order requirements is free, and the scheduler allocates memory, CPU and tags.
  • Backfilling with prediction. Every job must have timeout_s, so the time at which a running job will certainly release the runner, memory, CPU and tags is known in advance: start plus timeout_s (an upper bound; in practice a job often finishes earlier). From these times the broker computes the earliest possible start for the head order and treats it as reserved. The next order may bypass the head order only if it does not delay this start: it fits into the free resources now and either certainly finishes before the reservation (its timeout_s is not greater than the time until the reservation), or does not occupy anything the head order will need (another runner, the remaining memory). If there is no such order, the pool waits for the head order. If the head order has no predictable start (all suitable runners are offline), it creates no reservation, and the first of the following orders whose start is predictable receives it: this way an unavailable runner does not stop the queue. The reservation is recomputed on every event: if a running job finished earlier than its deadline, the head order starts earlier. This way a heavy order does not starve without a separate threshold, and the pool does not sit idle without a reason. Idle warm services are counted as free in the computation if preemption is allowed. The reservation takes into account [reserve], [quota] and [accept] of the runners. The policy decides the order, and aging (age_after_min) moves an order that has waited a long time to the head. Because the forecast is based on timeouts, small orders with a long timeout_s are bypassed less often, so profiles should set realistic timeouts.
  • No preemption: a high-priority order never stops a running job; it goes first and waits for resources.
  • Waiting for foreign load. With [admission] foreign_load = "wait" the order also waits while the real load of the runner machine leaves too little room. The reason (in Russian, like all wait reasons in status and explain) is busy with foreign processes: 800 MB free, 2000 MB needed or busy with foreign processes: CPU 95%, 4 cores needed. Running jobs are never paused (3.14).
  • Aging (30 minutes by default, a policy rule): a job that has waited longer than the threshold is ordered as the highest defined priority. The age is counted from submission to the hub (passed in the order) and is not reset when the broker is re-elected.
  • A job that will never fit into the pool limits is rejected on intake with a reason.
  • States: queued → running → passed | failed | timeout | cancelled | lost; when a running job is cancelled, there is an intermediate cancelling; a step is passed | failed | timeout | skipped | cancelled.
  • Each job writes stdout and stderr to temp/runner/<job-id>.log in the sender directory, with a header per step; submit returns the identifier, and waiting streams the progress and returns the exit code.
  • Cancellation and timeout kill the process tree: Windows Job Object and Linux cgroup v2 do so completely; otherwise a process group and a walk over descendants (best effort, section 10). Orphaned processes after a crash are found by the pair “pid plus start time”, so as not to kill an unrelated process that reuses the number.
  • Resilience: the dead sender rule is described in section 7; a dead job is removed.

7. Sender and cancellation

Every job says who sent it, so that the queue, the page and the log answer the question “whose is this”.

7.1 Identity

  • --as <name> is required for submit and run from a session or terminal (inside GitHub Actions it gets a default value). It is a free label of the caller (claude:session-3, alex); the core neither enumerates nor interprets agents. An optional --note <text> (up to 200 characters) says why the run is made.
  • The CLI collects by itself, without the possibility of override: the OS user, the host, the identifier and start time of the sender process, the working directory, and for a git worktree also the branch and the root. This is common git and OS data, with no knowledge of agents.
  • It is shown in status, the HTML snapshot, the dashboard and the log header: project, source, label, note, branch, directory, job age.
  • Identity is a hint, not authentication: any local process of the same OS user can submit under any label. The boundary is the IPC, accessible only to the OS user. For the broker, the boundary is the client key.
  • Cancellation: by default only jobs with the same --as label and the same OS user; a foreign label requires --force, which is recorded in the log of the cancelled job together with the label of the canceller. This check is local, in the hub. The broker itself allows cancelling only orders of the same client key; cancelling other clients’ orders is a right granted by the policy ([cancel] others), and by default only the broker owner has it, through the local channel.

7.2 Project and source

  • project: the normalized origin (owner/repo) of the sender directory; without a remote, the name of the repository root; outside git, the directory name. The repository root and the worktree are also recorded, to distinguish two worktrees of one project.
  • source: session (a terminal or an agent session: label, process, directory) or github (a GitHub Actions job, detected by GITHUB_ACTIONS=true: repository, workflow, job, run id and attempt, ref, actor, run URL; --as defaults to github:<workflow>/<job>).
  • Reading the CI environment lives in the github source adapter; the core sees only normalized fields. Another CI system means another adapter, not a change to the core.
  • For a github job, the sender process is the run that the GitHub ci runner invoked on the hub computer: the reaper watches it like any other. A cancelled workflow terminates the step process, and therefore run, after which the reaper cancels the order (unless --detach).
  • Everywhere project, source and the label are shown together (for example, Al.Browser · session · claude:fix-12); github links to the run URL. Filters: status --project, --source session|github, --as; the same fields are in --json.

7.3 Own jobs and early cancellation

  • submit prints the identifier and writes the handle temp/runner/<job-id>.json in the sender directory (label, identifier, profile, time). After a loss of context or a restart, the agent finds its jobs by the handles and by the hub.
  • localrunner jobs --mine lists the caller’s jobs (the same OS user and --as label; the label is given or read from the latest handle in the directory); --active keeps only queued and running; --json is available.
  • localrunner cancel <job-id> cancels one job, cancel --mine cancels all active jobs of the caller; the owner is checked as in 7.1, a foreign label needs --force. cancel --mine, down --cancel, runner remove and client remove destroy work, so they ask for confirmation before acting: --yes or yes typed at a terminal; without a terminal and without --yes the command does nothing, prints “…; confirm with --yes” and returns 1. Cancelling one job and down without --cancel do not ask.
  • Timeout. When timeout_s expires, the runner immediately kills the job process tree, with no soft signal and no grace period (those are only for cancellation), and sends the result timeout. The broker waits for nothing in this case: its reserve [grace] lost_min is needed only for the case when the runner could not report.
  • The effect of cancellation: queued is removed from the queue at once; an assigned but not yet started order (including at the source step) is cancelled as running; running receives a soft signal (Ctrl+Break on Windows, SIGTERM on other OSes), after the grace period (10 seconds by default) the tree is killed, the running step becomes cancelled, the others skipped, the job cancelled, and resources are released only when the tree is dead; for an already finished job the command reports the final state without any action.
  • The reason for cancellation is written to the log header: who, when, and --reason if given.
  • wait is only an observer: interrupting wait (Ctrl+C, an agent tool timeout) cancels nothing. Only cancel, a timeout or the dead sender rule cancels.
  • The sender process is the one that invoked the CLI (the parent of the short-lived localrunner, recorded with its start time), not the CLI itself, otherwise every job would die after submit returns. submit reports its completion to the hub with the message Done (CLI → hub; not to be confused with the network Bye of the runner and the hub) right after receiving the identifier, and wait works on its own connection. (The author’s decision.)
  • Dead sender: when the sender process has disappeared, its waiting orders are removed and the running ones are killed, to free the computer. submit --detach lets an order, both waiting and running, outlive the caller (the reaper does not touch it; a waiting detached order is removed only by an explicit cancellation or a long absence of the hub per [orphans]); it stays visible and cancellable by label. A github job is cancelled by cancelling the workflow run or by the operator through cancel --force.
  • Liveness detection: the CLI parent, the pair of pid and start time (on Linux relative to boot, from /proc starttime); the sender is considered dead if, on two checks in a row with an interval of 2 seconds, there is no process with that pid or its start time does not match the recorded one (so a reused pid will not kill someone else’s job). The liveness check runs every 5 seconds and is confirmed by a second pass after 2 seconds. The start time is taken on Linux from /proc/<pid>/stat (starttime, converted to absolute), on macOS from proc_pidinfo (PROC_PIDTBSDINFO), on Windows from GetProcessTimes; if the start time cannot be obtained, the job is not killed and a warning is written to the log. A short-lived agent shell will kill its jobs, so skills prescribe submit --wait or --detach.

8. History

Finished jobs are stored and are available later from any session and for any project.

  • Storage. SQLite broker.db in the broker state directory (one database: run history, computer registry, order queue) (SQLite is in the public domain, which the project license rule allows; the wrapper is the rusqlite crate, MIT). A row per job with everything known: identifier, client (key, MachineId, label), project, source, label, note, branch, directories, profile, times of submission, start and finish, result, exit code, who cancelled and why, runner; a row per step: state, times, code, timeout. The record is created on submission and updated on every state change, so a crash loses at most the last update.
  • Whose history. The broker is the source of truth for runs on its runners, including which client a run came from. The hub stores only the outbox of undelivered orders and a copy of the log in the sender directory; it requests the history and details from the brokers. If a laptop is switched off, the history of its runs stays on the broker and is available to other hubs within the visibility policy. (The user’s decision; “the broker knows nothing about the hub” applies to the code, not to the data.)
  • Logs. The full log is stored at the broker in logs/, the copy is temp/runner/<job-id>.log in the sender directory; for github the run URL is stored as well.
  • Peaks. Every finished job gets its peak memory and peak disk usage in MB (peak_mem_mb, peak_disk_mb), whatever the enforcement mode; the disk peak is measured only for a job that declares disk_mb. They are shown in history (columns PEAK_MEM_MB and PEAK_DISK_MB before BROKER, - when unknown), history show, jobs, explain, status --json and on the dashboard card. Use them to pick honest mem_mb and disk_mb before turning kill on (3.14).
  • Retention. By age and total size, whichever comes first: by default 30 days and 2 GB of logs, 365 days of rows (broker policy). Cleanup goes from the oldest and does not touch active jobs. A broker on a shared computer limits the volume by policy, so that one client does not fill the pool disk. The limits are in the code, the values are changed by the policy: the log of one job 256 MB (beyond that, truncation with a mark), the broker outbox per sink 512 MB (beyond that, output chunks are dropped, the result is kept), 100 active orders per client key, and an API request rate limit: no more than 1200 orders and read requests per client key in any 60 seconds ([limits] api_requests_per_min); above it an order is rejected with the code rejected_rate_limited, and a read request is refused with the same code; cancellation, unsubscription, stopping a log follow, acknowledgements and heartbeat are not limited, and a rejected request and a re-sent already accepted order (the hub outbox after a reconnect) do not count: a repeat gets the previous reply.
  • CLI. history [--project P] [--source session|github] [--as L] [--profile N] [--result R] [--since D] [--limit N] [--platform] [--runner] [--client C], newest first, --json; history show <job-id> is the full record; log <job-id> [--step NAME] [--tail N] [-f] reads the stored log, and with -f for an unfinished job follows it to the end. The commands go through the hub to the brokers it knows, and by default show the runs of this client; history --all shows everything the broker visibility policy allows, --client C shows the runs of the named client. Time is printed in UTC; --since accepts an age (30m, 2h, 7d) or a date (2026-11-01). Before output the log passes the CLI secret masking by whole lines (built-in names and [redact] fields from logging.toml of the configuration directory the CLI is run with; fields from the broker service configuration do not apply here), so a secret split between portions is hidden too. The output of run and wait and the last lines of running jobs in status and status --json are masked in the same way. A refused order is recorded as well: it appears in history as rejected (filter --result rejected) with the reason code and text, and the dashboard shows the same state; sending the same order again is refused again with the same reason.
  • Views. status --html --history adds a history table to the snapshot; the dashboard has a “History” tab with the same filters; every row leads to the log.
  • Statistics. localrunner stats [--project P] [--profile N] [--client C] and the “Statistics” page: runs, success rate, wait time and duration (median and 95th percentile) by profile and step, the share of timeouts and cancellations, pool saturation by client. It is computed by the broker from its history; the broker owner sees the whole pool, a client sees its own data. The goal is to set honest timeout_s values and to see where the queue waits.
  • History is read by the views and does not leave the network: the broker gives it only to authenticated clients according to the visibility policy.

9. Queue view and dashboard

9.1 Three forms of the same data

  • localrunner status is text, --json for agents and scripts.
  • status --html [path] is the dashboard as one self-contained HTML file with embedded data (by default temp/runner/queue.html). A snapshot: no listener is needed, it opens from disk. Finished jobs (up to 100 per broker) get into it only with --history, the logs of running and finished jobs (the last 500 lines) only with --with-logs: the CLI reads them through the hub, the broker gives only those its visibility policy allows, and the text passes secret masking; an unavailable log is simply not embedded. The last lines of running jobs in the snapshot and in the live dashboard pass the same masking, as does the tail of the log copy that the live dashboard reads from disk (a line cut by the start of the tail is discarded). The snapshot file is accessible only to its owner (0600 on Unix, the owner DACL on Windows).

One interactive page serves both the live dashboard and the static snapshot: the snapshot embeds the JSON data and runs the same code with updates and actions switched off. Delivery: one self-contained page embedded in the hub, with no external scripts, fonts or network requests (it works offline). The light and dark themes follow the system; the layout works at phone width; keyboard control with a visible focus.

A row expands into a card: project, source, label, note, branch, directory, profile, runner, the reason for waiting and the step ribbon (one bar per step relative to the timeout, the current step animated, skipped gray). Live updates over one SSE stream with automatic reconnection and a visible connection state; the “Pause” button freezes the view, and new events during the pause are counted by a counter. 9.3 Data sources

  • The page and the server read through one DataSource interface. The hub dashboard takes everything from the broker APIs: runners, pool load, the queue, running orders, run history and logs. When a broker is unavailable, the dashboard shows the log copies and the orders waiting in the outbox. The dashboard is not configured with a list of runners, and runners do not know the dashboard address.
  • One data model for all three forms: the view types DashboardSnapshot, DashboardJob and DashboardEvent in lr-proto (dashboard.rs): the hub builds them, and the live page, the snapshot and the JSON export only read them.
  • If a broker is unavailable, its data is marked as stale; the orders in the outbox of this hub and the log copies remain. A dashboard on another computer is the same dashboard of its own hub: it reads the brokers that this hub knows.

9.4 Dashboard actions and security

  • Cancellation of a waiting or running job after a confirmation naming the job. Cancellation from the page counts as --force: it is recorded in the log and history as a cancellation by dashboard:<OS user> with the reason from the dialog; on the broker the same key rule applies: the hub dashboard cancels only the orders of its own key. Cancelling all jobs of a project or label is a separate explicit action with a list in the dialog. There is no submission, editing of profiles and configuration, or starting and stopping of runners from the page.
  • A random port, a token per launch; the token is exchanged for a session cookie (HttpOnly, SameSite=Strict) on the first request and is removed from the address bar.
  • Localhost only, with no way to change it: the socket is on 127.0.0.1 (and ::1), never 0.0.0.0, :: or a LAN address; there is no option, configuration key or environment variable that would widen this. The dashboard is not published or tunneled by a plugin.
  • Protection against DNS rebinding: a request with a Host not equal to localhost, 127.0.0.1 or [::1] with the dashboard port is rejected, as is a request with a foreign Origin. At startup the hub checks the actual address and exits with an error if it is not loopback.
  • Nothing leaves the computer: the hub, the CLI and the page make no outgoing requests, send no telemetry, and upload no logs, history or snapshots. The only outgoing connections of the system roles (the installer is a separate program that the owner runs by hand, see 10.1) are: the GitHub Actions ci runner to GitHub (its own protocol, without system data), the connections of the hub and the runners to the brokers, the runner’s git fetch from the job repository, and the optional sink for logs and metrics (OTLP) that the owner enabled in logging.toml.
  • Any request that changes state is a POST with an anti-forgery header and an Origin/Host check; reads and the stream require the session cookie. The text of logs and fields is output as text, not as markup; a strict CSP without execution of inline scripts; logs are not indexed and not cached. The snapshot contains logs only with --with-logs, because logs may contain secrets from profile commands.

broker install-service copies the binary to the service directory (the service does not depend on the user directory) and creates the service account. It first checks the service state directory: if the directory already exists and is a link or junction, belongs to someone other than administrators, SYSTEM (root), and the service, or its ACL explicitly lets anyone else in (on Unix, write access for the group or everyone), the installation refuses, copying nothing there. If any step failed, the service registered by this run is deleted; a service that existed earlier remains and, after a failed reinstallation, stays on manual start. The service state is not deleted by autostart off broker or uninstall.

Hub and runner autostart starts them with --background. On Windows this is a scheduler task under the user themselves: the trigger is their login, it runs in their session without elevation, restarts a minute after a failure (up to 999 times), with no time limit and running on battery. The task runs localrunnerw.exe, a launcher without a console, which starts localrunner.exe next to itself with a hidden console and returns its exit code, so a window does not appear even for a moment. The task is created without administrator rights; if the machine policy forbids this, the command ends with a clear error and a hint, and does not silently switch to another method. The task name is Al.LocalRunner <role> <user SID>: the scheduler folder is shared by all users of the machine, and the SID prevents them from replacing or deleting each other's tasks; a repeated autostart on replaces only the task of this user, and autostart off and uninstall delete only their tasks. The restart on failure of the scheduler task still has to be verified on a clean VM.

The hub has one state directory, and each runner has its own: runner/<name> inside the installation directory with its own runner.toml, runner.db, and key; up starts the runners by the names from this directory, and machine-id is shared among them (it belongs to the installation). In the state directory: machine-id, configurations, databases (broker.db, hub.db, runner.db), logs/, the broker certificate, and the secret member keys. Secret keys and databases are accessible only to the owner of the directory (rights 0600 and the Windows ACL equivalent).

10.4 Docker and Compose

The image contains only the binary and does not run as root. It has no consumer tools (gradle, adb, emulator): the owner builds their own image on top of ours (FROM) and adds what is needed. An example for the broker and one runner:

services:
  broker:
    image: al-localrunner:version
    command: ["localrunner", "broker", "run"]
    ports: ["7443:7443"]
    volumes:
      - broker-state:/var/lib/al-localrunner
      - ./policy.toml:/etc/al-localrunner/policy.toml:ro
    restart: unless-stopped
  runner:
    image: al-localrunner:version
    command: ["localrunner", "runner", "run"]
    volumes:
      - runner-state:/var/lib/al-localrunner
      - ./runner.toml:/etc/al-localrunner/runner.toml:ro
    depends_on: [broker]
    restart: unless-stopped
volumes:
  broker-state: {}
  runner-state: {}
  • Join. The code is issued by docker compose exec broker localrunner broker add, and the runner joins with the command runner join broker:7443 code; the keys and certificate are in the volumes and survive recreation of the containers.
  • Policy. The owner edits the mounted policy.toml and calls docker compose exec broker localrunner policy reload: access inside the container counts as the local channel.
  • Configuration in the container. The configuration directory is set by --config-dir or LOCALRUNNER_CONFIG_DIR (/etc/al-localrunner in the example); the owner adds the Compose network (for example 172.18.0.0/16) to [networks]. The runner service in compose.yaml is brought up after runner join, otherwise the container restarts in a loop.
  • Boundaries. A container runner does not see host files, so it takes only orders with a commit. The owner assigns its networks in the [networks] list to the host network. In a container the broker listens on [listen] address = "container" (all container interfaces: the address in the Compose network is not known in advance), and the boundary outward is set by ports: in compose.yaml: port 7443 is published explicitly, preferably on a specific host interface ("192.168.1.10:7443:7443"). Outside a container the value container is rejected, and wildcard addresses are still not allowed.
  • Version. The image tag is always explicit; an update is a tag change and docker compose up -d.

Implementation details (installation):

  • Files. The scripts install/install.sh (POSIX sh) and install/install.ps1 (PowerShell 5.1 and newer), the image install/Dockerfile (the build context is the repository root, .dockerignore lets through only Cargo.toml, Cargo.lock, and crates), install/compose.yaml with the examples install/policy.toml and install/runner.toml.
  • Release files. The archives al-localrunner-<os>-<arch>.tar.gz (linux-x64 and linux-arm64 (static musl builds that do not depend on the glibc version), macos-x64, macos-arm64; localrunner at the archive root) and al-localrunner-windows-x64.zip (localrunner.exe, localrunnerw.exe), with SHA256SUMS and SHA256SUMS.sig next to them. The release tag is v<version>; without --version the latest release is taken (releases/latest/download). --offline file looks for SHA256SUMS and SHA256SUMS.sig next to the archive, first copies all three files to a temporary directory of the installer (owner-only rights) and then verifies and unpacks only the copies, so replacing the source files after copying changes nothing; it does not go to the network. curl accepts only https, including on redirects.
  • Signature. SHA256SUMS.sig is an SSH signature (ssh-keygen -Y sign, namespace al-localrunner-release, ed25519 key); the script verifies it via ssh-keygen -Y verify (OpenSSH 8.1 and newer is needed: modern Linux and macOS; on Windows, the built-in System32\OpenSSH of version 8.1 and newer, while Windows 10 1809–20H2 has the built-in OpenSSH 7.7 without -Y — there a newer OpenSSH or manual verification of the prebuilt file is needed; an old ssh-keygen gives a clear refusal) against the public key embedded in the script itself. In the repository a placeholder @RELEASE_PUBKEY@ stands in place of the key, and the release build substitutes it; a script with the placeholder, without ssh-keygen, without a signature, or with a mismatched signature installs nothing. The order: refusal of root or administrator (flag --allow-elevated), download, the signature of SHA256SUMS, SHA-256 of the archive, unpacking to a temporary directory, then localrunner install --role … [--dir=…] from the verified binary (it does the copying, the idempotent PATH extension, and init) and, as in diagram 10.1, localrunner doctor. A doctor failure does not roll the installation back: the installer prints a warning and exits with code 0. The variable LOCALRUNNER_INSTALL_SOURCED=1 is needed only by tests (the script loads the functions and installs nothing) and always produces a warning.
  • Image. The build uses rust:1.99.1-alpine (a static musl binary), the base is gcr.io/distroless/static-debian12:nonroot: no shell, only /usr/local/bin/localrunner, user 65532:65532. LOCALRUNNER_STATE_DIR=/var/lib/al-localrunner, LOCALRUNNER_CONFIG_DIR=/etc/al-localrunner; the state, configuration, and IPC directories (/run/al-localrunner: the state directory matches the Linux service directory) belong to this user. Every release publishes the multi-arch image ghcr.io/alexpantiukhin/al-localrunner:version (linux amd64 and arm64) and attaches compose.yaml that points to it; the version of the image, the tag, and the crates is the same. ENTRYPOINT is empty because command in compose.yaml starts with localrunner.
  • Compose. The network pool with the subnet 172.30.57.0/24 (the same as in [networks] of the policy.toml example), the broker port is published on 127.0.0.1:7443 — for other machines the owner changes the address to a host interface; the runner has hostname: runner. Both services take the image al-localrunner:version with an explicit tag; build on the broker builds it from the repository, and the build context is the repository root (.. from install/); without the repository, build is removed and the published image is used. 10.5 Update, removal, migration

  • Update. On a machine with localrunner the way is install.sh --upgrade or install.ps1 --upgrade (the signature is checked as for installation): the downloaded binary runs localrunner upgrade, which compares the installed and the new version, lists the running jobs and the waiting orders and asks (with running jobs: wait for them, cancel them with --cancel, or abort; --yes alone waits), stops the runners first (drain or cancel), waits for them, only then stops the hub and a broker started by hand (Ctrl+C while waiting replaces nothing and leaves both running), copies itself over the installed binary and starts the same roles from it; an older binary is refused, the same version changes nothing, and if the copy fails the stopped roles are started from the old binary. The broker OS service keeps its own copy of the binary and is updated by hand with administrator rights (stop the service, replace the copy, start it). Otherwise: replace the binary or image by any method from 10.1 and restart the role (down and up, restart of the service or container). Before replacing, it is better to stop the runners gracefully (down works as --drain): running jobs finish. A broker restart shorter than [grace] lost_min is safe: runner jobs survive, and the timers are counted anew from the first heartbeat after the start. Compatibility by protocol version (3.9). Database schemas are updated automatically at startup with a backup; rollback to an older version with a newer schema is not supported and ends with a clear refusal.
  • Removal. localrunner uninstall stops the roles of the installation like down --cancel: running runner jobs are canceled (whoever needs their result calls down first), it waits for the runners to exit after cancellation for no more than 30 s, then the manually started hub and broker are stopped; the broker service is removed together with the service. If any role did not stop, uninstall deletes nothing, names the reason, and returns 1. Then uninstall turns off autostart and deletes the service, the binary, and its directory from the user PATH; keys and history remain. uninstall --purge, after confirmation, deletes the state directory as well; it does not revoke the runner key at the broker, and the runner stays offline until runner remove. The schema backup made during migration lies next to the database (broker.db.bak-<version>); only the latest one is kept.
  • Broker migration. Stop the service, copy the state directory (broker.db, logs/, the certificate, policy.toml; machine-id is not copied: the new computer has its own installation and its own identifier) and fix [listen] in policy.toml for the address of the new computer (the address stays the same only if the IP moved together with the broker) to the new computer and start with the same address: the hub and runners connected over the network connect without joining again while the certificate is the same; the hub and runners of the old computer that used IPC are now remote and join again by code. When the address changes, it must be updated in the hub list and in the runner settings.

12. Logging and metrics

The diagnostics of the system itself go through a logging facade, and the owner decides by configuration where they end up. By default this is a file on disk; Grafana is attached as an optional sink.

  • The facade in code. The roles write structured events to the LogSink trait and metrics to the Meter trait (both in lr-abstractions), and know nothing about the sinks. This is the analog of ILogger. Sinks, levels and field redaction are attached by one common crate (lr-obs), not by the role code; the roles do not depend on lr-obs, and lr-cli passes the implementations to them. (Implementation note: instead of the tracing crate, the facade is made of our own traits: this way the roles depend only on contracts, and stubs for tests already exist.)
  • What is logged. The diagnostics of the hub, the broker and the runner: connections and drops, receiving and assigning orders, policy rules that applied, policy reloads, refusals, outbox work, storage cleanup. Job output is not included: it is stored as run data (section 8) and does not go to the sinks. (User decision: Grafana receives diagnostic logs and metrics.)
  • Event fields: time, level, role (hub, broker, runner), component, MachineId, message and, where applicable, job_id, runner, client label, the name of the rule that applied. Not written: job commands and environment variables, job output, keys, join codes and tokens. The list of redacted fields is set by configuration.

Implementation notes (lr-obs):

  • Keys. Unknown keys, sink kinds, levels and signals are rejected. A file without [[sink]] means the default file. [redact] fields only extends the built-in list and cannot weaken it. A reload with an error keeps the previous configuration; after shutdown a reload is rejected. A journal that the OS does not have is a configuration error.
  • Redaction is performed before any sink (the sinks accept only the redacted record). Masked (***) are: secret values obtained by the runner through SecretSource (the RedactingSecrets wrapper), wherever they appear; PEM blocks with PRIVATE KEY; join codes lrj1.…; credentials in URLs; Bearer/Basic; the value after a sensitive name and = or : in text, including in escaped JSON of any depth ({\"token\":\"…\"}, {\\\"token\\\":…}): a quoted value up to the same closing quote, nested {…}/[…] entirely, an unquoted value after = up to a space or , ; & ) } ] " ', and after : and for the names Authorization/auth up to the end of the line (password: my pass phrase and password: ab,cd are masked entirely) (token …, Digest …, Basic …); the entire value of a field with a sensitive name. The built-in names are: token, key, password, passwd, secret, authorization, auth, cookie, credential, credentials, command, env, environment, join_code; the match is by name parts, which are split on _ - ., camelCase, acronyms and a change from letter to digit (api_token, X-Api-Key, privateKey, APIKey, token2 match; exit_code, keyboard do not). In addition, a name is sensitive if, without separators, it contains one of the parts token, secret, passw, apikey, passphrase, pwd, credential, bearer, auth (PGPASSWORD, accesstoken, dbPwd, OAuthHeader). Ruling: from this rule (and only from it) the false positives tokens_used, author, authority, unauthorized, authenticated are excluded (the NOT_SENSITIVE list, verified by tests); the built-in names and [redact] fields do not weaken the exceptions (token_count is masked by the part token, a configured authority is masked); other words with these parts are masked: an extra mask is cheaper than a leak. The registered values are searched by a single Aho-Corasick automaton: protect only marks it stale, the next redaction rebuilds it outside the lock, and a redaction started after protect returns always sees the new value. Overlapping matches are merged during the search, without tails; more than 65 536 matches in one text (a degenerate set) mean the rest of the text is masked. Limits: a message of 16 KiB, a field value of 4 KiB, a field name of 128 bytes (the #number of the field is appended to a truncated name so that long names do not merge), 64 fields; of repeated names in a record the last value remains; dropped fields (beyond 64 and repeats) are counted (Redactor::dropped_fields). Before redaction the input is cut to the limit plus the length of the longest registered value, and the cut point is moved back until it settles, to the start of a split registered value and to the start of a split token (a token ends only at a whitespace character: , and ; are valid in a URL userinfo): each pattern is judged on a whole token, so URL credentials, Basic or a “name=value” pair on the boundary are dropped entirely rather than output as a prefix. A text whose first token is longer than the limit becomes a single ...[truncated] mark. After redaction the text is cut to the limit with the ...[truncated] mark. Limitations: an unregistered secret with no sensitive name next to it is not recognized; an unquoted value after = ends at the first delimiter, so token=ab&cd leaves &cd; a value in an unclosed quote is masked to the end of the text; values shorter than 4 characters are not registered; encoded forms (base64, URL) are not searched; up to 4096 values are kept, older ones are forgotten.
  • Lines. A JSON line: time (RFC 3339 UTC, ms), level, role, component, machine_id, message, fields. Control characters (C0, DEL, C1), bidi characters and the separators U+2028/2029 are escaped in both formats, so a field cannot forge a second record or color a terminal. In text, the message is always quoted, and a value is quoted when it contains a space, ", =, \ or an escapable character; inside quotes \ and " are escaped, so a message such as job_id=evil cannot forge a field. format = "text" writes the same line as the console.
  • File rotation: before the line with which the file would exceed rotate_mb MiB, and one day after opening, the active file is renamed to daemon-YYYYMMDD-HHMMSS-mmm[-n].log (UTC). Rotated files older than keep_days by the time in the name are deleted, then those beyond keep_files (default 10); other files in the directory are not touched. The path is only relative inside the state directory, without .., a drive or Windows device names. On Unix the directories are created with mode 0700 and the files 0600; on Windows the ACL of the state directory is inherited. An I/O error does not crash the process: it is counted, the event is lost and counted in log_dropped_total together with the lines that remained in the buffer since the last successful flush, and the file is reopened; a failed rename is retried after a minute. On reload the previous file is closed before the new one is opened, so there are never two writers on one path: the replacement, the closing of the old sinks and the start of the new threads happen under one lock, which both flush and shutdown take, and a closed sink no longer touches its writer. Events written during a reload are put in the queue of the set of sinks that is current at the moment of enqueueing, so they do not land in a closed queue; late events in a closed queue are counted in log_dropped_total.
  • Buffer: each sink has its own queue of up to 10 000 events and 8 MiB; on overflow the oldest are dropped. Writing happens in the worker thread of the sink, and the file is flushed to disk once a second and at shutdown. While a sink is not ready (an OTLP pause), the thread sleeps for a second at a time and is not woken by new events, so the pause does not load the CPU. If the sink thread could not be started, this is written as an error event to the other sinks and counted in the errors; such a sink delivers only on an explicit flush.
  • OTLP: OTLP/HTTP JSON to <endpoint>/v1/logs and /v1/metrics, https only, TLS 1.3, the receiver certificate is verified against ca_file; credentials, a query and a fragment in endpoint are forbidden, and the error text does not repeat the address. There is no separate authentication: a receiver with authentication is placed behind a local Alloy. Batches of up to 512 events; a failed send loses the batch (counted) and starts a 5 s pause doubling up to 300 s. Metrics are sent every 60 s, cumulatively. timeout_s limits the connection and each read and write operation.
  • OS journal: syslog (collected by journald) on Unix, Windows Event Log (the Application log, the source Al.LocalRunner) on Windows; a line without time. On Windows the line is cut to 31 839 UTF-16 units (the limit of the ReportEventW insertion string) with the ...[truncated] mark.

Implementation notes (lr-obs):

  • The labels are in English: platform, pool, runner, reason, result, service, role, sink. cache_used_mb has only runner, cache_evicted_total has runner and reason. saturation_wait_seconds is a gauge; metrics without _total and without the “histogram” mark are gauges.
  • Permitted values: the saturation reason is runner_busy, memory, cpu, tag, rule; the eviction reason is size, age; the result of orders and duration is passed, failed, timeout, cancelled, lost, rejected; the reload result is ok, error; role is hub, broker, runner; sink is file, console, journal, otlp.
  • Only the names from the catalog and exactly their label sets are accepted; a label value is up to 128 bytes without control characters; no more than 256 series per metric; rejected updates are counted. The series of a vanished runner, service or pool are deleted by the call Meter::forget(label, value), which frees space under the series limit. Counters saturate rather than overflow; a gauge does not accept NaN and infinity, a histogram does not accept negative values.
  • Histogram boundaries, s: 1, 5, 15, 30, 60, 120, 300, 600, 1800, 3600, 7200, 14400. The units are UCUM: s, MBy, {order} and so on.
  • The client label is allowed only with [metrics] client_label = true in logging.toml and only on queue_wait_seconds, orders_total, job_duration_seconds; when the setting is off it is dropped.

Implementation notes (roles):

  • The roles receive the Meter through BrokerDeps, HubDeps, RunnerDeps; lr-cli passes the registry of the same logger whose otlp sink publishes it. The names and label keys are constants of lr_abstractions::metric; a test in lr-obs checks them against the catalog.
  • Broker. orders_total grows at every final state (passed, failed, timeout, cancelled, lost), including when the broker returns a “same machine” order without a live runner (cancelled, code rejected_no_runner_on_machine), and at a refusal on receipt (rejected); job_duration_seconds runs from start to the final state, only for jobs that started. The wait is measured by the broker clock, not the hub clock: queue_wait_seconds runs from the last placement in the queue (receipt of the order, recovery after a restart or a return to the queue from a lost runner) to the assignment to a runner; an order returned to the queue yields a second observation. platform is the platform of the order, same_machine for an order without a platform, other if no known runner declares the platform (so the text of a rejected order does not become a series); the label is fixed at assignment to a runner, and the job result goes with the same label. The gauges (queue_length, running_jobs, pool_memory_used_mb, pool_cpu_used, runner_online, saturation_wait_seconds) are recomputed after every scheduling pass and once a second; pool is always default (the broker has one pool); runner_online = 1 while the runner has a connection. saturation_wait_seconds{reason} is how long, since its last placement in the queue, the oldest order currently waiting for this reason has waited, 0 without such orders; runner_busy ← the runner is busy, memory/cpu ← the pool lacks resources, tag ← an exclusive tag is busy, rule ← a reserve or a rule quota; waiting for an offline runner, the absence of a runner and the start reserve of the head of the queue do not count as saturation. policy_reload_total also counts a failure to read policy.toml. A removed runner is forgotten (Meter::forget("runner", name)).
  • Outbox. Every 15 s and at start, each role takes from the storage the number of unacknowledged records and the time of the oldest one (outbox_backlog, results_backlog for the broker, across all clients, without reading the content); the age is 0 when there are no records.
  • Runner. cache_used_mb is the size of the named caches (without the worktree mirrors) at every capacity count and after cleanup; cache_evicted_total counts the named caches removed by cleanup: age means older than retention_days, size means evicted by max_size_gb; the removal of worktree mirrors is not included. The runner label is the runner name.
  • Runner services (3.11). The [service.*] keys: start and ready_check are required, stop is optional (without it the tree is killed at once); ready_timeout_s defaults to 60, stop_timeout_s (the grace period after stop) to 10, restart (how many times the service is brought up again after failures) to 3, memory_mb to 0, lifetime to per_job, reuse to same_client; max_lifetime_s is required for any lifetime, idle_timeout_s for idle; an unknown key is an error. A service with secrets (secrets = [...], values from the runner storage) is reused only by the same client, whatever reuse is set; same_project means the same project with any client. start runs in the foreground while the service is alive: the life of the service is the life of its root process, so a command that launches a daemon and exits is not supported (such a service is considered crashed at the next assignment). The environment of start, ready_check and stop is only the runner PATH, HOME, TEMP, and the working directory is services/<name> in the state directory; before each new instance it is cleaned so that the next client does not see the files of the previous one. The service starts before the job steps and is recorded in the registry before the readiness check; ready_check is repeated once a second until code 0 or until ready_timeout_s. A failure of start or readiness ends the job as failed with service_failed and counts as a failure; a crashed warm service is detected at the next assignment and also counts as a failure. Failure number restart + 1 makes the service unavailable until the runner restarts (capabilities: unavailable). After the job, a per_job service and a service that has outlived max_lifetime_s are stopped before the result is sent; the others stay warm and are shut down on idle or max_lifetime_s. Stopping: stop, waiting for the process to end up to stop_timeout_s, then killing the whole tree in any case. The broker command “stop the service” does not touch a service that is busy with a job. On drain and on an authorization refusal the runner shuts down all services, including those already being stopped by a timer or the broker, and waits for them to exit (no longer than the longest stop_timeout_s plus 30 s) before Bye; the heartbeat continues meanwhile. The service report is sent after welcome and at every change. The runner declares the memory_mb of each service in the capabilities (the optional field service_mem_mb). The broker subtracts from [pool] mem_mb (and in the reserve rule checks) the memory of the services that the runners reported as starting, idle, busy or stopping, and schedules an order with services with an addition of their declared memory: the smallest over the runners that take work and offer all these services, without the services already alive on the runner (their reuse); if a scheduling pass puts an order on a runner where its services cost more and do not fit in the remainder of the pool or the runner, that runner is excluded from the pass and the pass is repeated. The addition of an assigned job is held until the runner reports the service. This way the memory is reserved before the service starts and is not doubled on reuse. On receipt, an order with services is checked with the same addition without counting live instances (the smallest over all registered runners that offer the services): the pool, reserves and quotas see the job plus the services, each runner sees the job plus its own services; an order that never fits this way gets rejected_pool_memory, rejected_quota or rejected_no_matching_runner with the numbers “job + services” rather than waiting forever. The max_mem_mb quota counts the memory of the services that the order will start, both on receipt and in the queue; the memory of already live services is not part of the quota. The pool_memory_used_mb of a runner includes its live services. Metrics: service_starts_total is every start attempt, service_failures_total every failure, service_up is 1 after readiness and 0 after stopping; the service label holds only names from runner.toml, the series of a service that is no longer in runner.toml are forgotten at runner start only for that runner (Meter::forget_series by the pair runner, service), and a same-named service of another runner of the same process keeps its series.
  • No role puts into labels a JobId, a project, a branch, a job label, a client key or user name, paths, commands or secrets.
  • Key revocation. runner remove and client remove first revoke the key in the registry, then the engine drops the connections of the key. The waiting orders of the client get cancelled with the reason client_removed (who cancelled: broker); the running ones, including assigned and not started, get a cancellation sent to the runner with the same reason under [orphans] running = "cancel", and under "finish" run to the outcome; an assigned and not started order that returns to the queue after a runner loss or a broker restart gets cancelled with client_removed instead of the queue and is not assigned to another runner. The hub of a revoked key does not learn of client_removed or of the outcomes of its orders: the outbox of the key is deleted, and no message about runs accepted before the revocation is written to the outbox any more (the outcomes are visible only in the broker history; the hub closes such orders by its outbox time limit). The rule holds also after a repeated join under the same name: the new hub receives only the outcomes of orders accepted after joining, and the runs cancelled and finished at revocation are not replayed to it. At start the broker considers a run to belong to a revoked key if the machine record with the name of its client is revoked or joined later than the run was accepted; such waiting orders are cancelled with client_removed, and running ones follow [orphans] running, so a broker crash between the revocation in the registry and the command to the engine does not return them to the queue. The orders of other clients are not affected.
  • Retention. The engine checks the due time of the retention pass at every command, including the tick; the first pass starts at the first command after start, the next ones no more often than once in 10 minutes. The pass runs outside the engine task, no more than one at a time; a panic in the pass clears the “running” mark, and the next pass runs on schedule: expire_results deletes outbox records older than [results] keep_hours, prune cleans logs and rows of finished runs by [history] (logs_max_gb in GiB); active runs are not touched. The values are taken from the policy in effect at the moment of the pass, a storage error is written to the log as a warning and is retried by the next pass.
  • Schema migration. Before migrating any database (broker.db, hub.db, runner.db) to a new schema version, the file is copied (VACUUM INTO) to <name>.bak-<old version> next to it, on Unix with mode 0600; a copy of the same version from a previous attempt is replaced, and after a successful copy the copies of other versions are deleted: one, the latest, is kept (10.5). The copy is made only when the migration will actually run; if it could not be made, the migration does not start and the opening of the database ends with an error with the path of the copy.

13.2 Inside the broker

Engine clarifications where the sections above do not define the behavior:

  • A local IPC client receives the key local:<OS user>; the same key serves as the identifier of its computer and as the “same computer” reference for its runners. A network runner does not receive the “same computer” reference, whatever it reports about itself.
  • The broker closes a connection that is silent for 45 seconds (three missed heartbeats of 15 seconds each); a runner on such a connection becomes offline, and orders not yet assigned to it return to the queue.
  • A local runner lives only in the memory of the broker session: only a runner with a computer key has its runner row written to broker.db.
  • An order rejected on acceptance is not written to the history: the hub receives a refusal with the reason, and nothing more.
  • A refusal to cancel (a foreign or unknown order) goes to the sender immediately, as cancel_ack without an outbox entry: such a reply is not repeated after reconnection, but a stream of foreign JobIds does not fill the outbox. An applied cancel and a cancel of the sender’s own order go through the outbox.
  • When several clients have the same JobId, a cancel by the broker owner and the requests history show, explain, log accept an optional client key (client); without it the caller’s own run is taken, otherwise the only visible one, and if there are several, the broker refuses and lists the clients.
  • A repeat of an order with an already accepted key and JobId answers with the same Accepted only if seq is not greater than the accepted one (usually 1) and does not advance the counter; an order with a greater seq is rejected as malformed, so that it does not take the number of the next cancel.
  • If storage fails while accepting an order or a cancel, the broker writes to its log and answers with the error unavailable; the hub retries later.
  • The “summary” level for foreign orders shows the state, reason and exit code, but hides the project, label, profile, wait reason and steps; a history filter on a hidden field does not find such orders. At the “hidden” level, the busy tags of a runner are shown without a JobId.
  • The queue position in status is counted over the whole queue in policy order, including orders hidden from the reader.
  • The “same computer” reference of a local runner (local:<OS user>) is visible in the runner list and in the reply to a capabilities poll only to this client itself and to the broker owner.
  • A local runner registers under the name local:<name>. The name of a network runner cannot contain a colon, so a local runner does not take the name of a network one and does not appear in the history under its name.
  • An incoming connection in join mode is rejected as unauthorized until the join code registry is attached to the broker.
  • Queues are bounded: connection commands to the engine wait for room in the shared queue (the connection reader does not read further until the engine frees room), each connection has at most 1024 outgoing frames, and a connection whose queue overflowed is closed by the broker as slow, and the broker writes about it to its log. One connection has at most 16 event subscriptions; an extra one is refused. The outbox resend after resume, log replies and outbox messages that arrived during the resend go to the connection in portions: no more than 256 such frames are in the connection queue at once, the next portion goes when the queue is half empty; the order is preserved, and more than 100 000 waiting frames mean a slow connection.
  • When accepting connections fails repeatedly, after three errors in a row the broker waits before the next attempt: from 100 ms, doubling the pause up to 5 s.
  • log --step selects the output of a step by the heading lines === step <name> ... === that the runner writes at the start of a step, including the line about the cancellation of a step. log -f returns the stored log and then sends new chunks of the job until it finishes (the last portion with end); following takes a subscription slot (no more than 16 per connection together) and goes in portions by the same rules as the outbox resend; for a finished job the reply is the whole stored log. If the log of a running job (or of the chosen step) is still empty, an empty portion without end comes first: following has started.
  • The read request unfollow with the number of a follow request removes this follow on its own connection and frees the subscription slot (the reply is unsubscribed, for a foreign or unknown number — not_found). The hub sends it when the CLI left before the end of the log: one hub connection to the broker serves all its viewers, and an abandoned follow would otherwise hold a slot until the end of the job. A broker of an earlier minor version does not know this request and answers as to an unknown one; the follow then lives until the end of the job.
  • The history filter mine (an optional field, false by default) asks only for the caller’s runs: the broker substitutes the client key of the connection for the client field, so the CLI does not need to know its own key. Visibility does not change: mine only narrows the selection.
  • The CLI channel to the hub: the hub forwards the log (log, log -f) in log_chunk portions (broker name, text, end) in the broker’s order, without a common request timeout for following; a broker refusal arrives as an ordinary read reply, a broken connection to the broker or a lagging stream as the error unavailable. The request shutdown (reply stopping) stops the hub, the administrative command shutdown stops the broker; a broker started by the OS service manager does not stop and answers with a warning. Both exist only on local IPC. The hub does not forward the read requests subscribe, unsubscribe and unfollow from the CLI (refusal malformed): only the hub itself manages the subscriptions and follows on its own connections to brokers, so one process cannot remove another’s follow or take subscription slots. A follow that lagged (the CLI cannot keep up with reading and the hub stream queue overflowed) ends with the error unavailable, and the hub removes it at the broker with the same unfollow.
  • The event stream for the dashboard: on each connection to a broker the hub first subscribes to the queue and runner topics (one of the connection’s subscription slots) and puts their events on its bus. The broker has already masked each event by visibility for this hub’s key. The CLI request events answers watching and then forwards bus events as event replies (broker name and event) while the connection is open. A repeated events on the same connection answers watching again and does not open a second stream. The event unknown means that events may have been lost and the state must be read again. The hub sends it on behalf of a broker when the connection to this broker was lost or restored, and on behalf of hub when the CLI connection fell behind the bus. A hub of an earlier minor version does not know the events request and silently skips it. If watching does not arrive within 5 s, the dashboard switches to refresh ticks every 2 s.
  • The broker checks deadlines on every event and once a second. A running job receives lost (reason runner_lost) exactly at the moment Started + timeout_s + [grace] lost_min by the broker clock, even if the runner connection is alive; a job in cancelling ends the same way. If a write to broker.db on lost, on return to the queue or on the cancel of a waiting order failed, the broker writes an error to its log, keeps the run to itself and repeats the write once a second; the order is not assigned to anyone meanwhile. The write of a job start is repeated in the same way: started is confirmed to the runner at once, the start time is the time of the report, a repeated started of the same job changes nothing. While the start is not written, a cancel is recorded in the run without a state change, and lost and the runner result wait: first the start is written (and cancelling, if the job was cancelled), then the result, exactly once. Only failures of the storage itself are retried; a storage refusal on the run state is written to the log as an error and not retried. A broker restart during the same failure can execute a job twice: an unwritten start is not visible after the restart, and the run returns to the queue. The first failure is written to the log per run, each following failed retry round as one line with the number of waiting writes. A cancel of a run waiting for a repeated return to the queue is accepted (applied), recorded in the run and closes it after a successful return; a run waiting for the write of lost or of a cancel confirms the cancel and ends its own way. A cancel of a waiting, not yet assigned order whose write failed lives only in memory: a broker restart during a storage failure returns such an order to the queue uncancelled.
  • On start the broker reads from broker.db the runners (as offline; the runner memory and CPU are not stored in the row, so until it returns its capacity is counted as the pool budget, and its zone as remote) and the active runs, no more than 100 000: waiting ones join the queue, assigned and not started ones stay with their runner for the grace period [grace] lost_min from the broker start and only then return to the queue (more in the section on completion reasons), started ones wait for the runner report until the lost deadline. A cancel of an assigned but not started order (its own, the owner’s or hub_absent) is recorded in the run at once (who and why, without a state change), so after a restart such an order immediately receives cancelled and is assigned to no one; if the job nevertheless ended as passed, failed or timeout without having been in cancelling, the recorded cancel is removed. The network client address of a recovered order is refined when its hub connects.
  • An order “same computer” whose installation has no runner left online (the last one left, was lost or is in drain) is returned by the broker to the hub with the message returned with the reason rejected_no_runner_on_machine, and in the history the run receives cancelled with the same reason. After a restart the broker waits one grace period [grace] lost_min for the runners to return and only then returns such orders.
  • After drain a runner receives no new orders and on acceptance is considered offline (an ordinary order waits, a “same computer” order is rejected); the runner row is draining until Bye or a new connection.
  • The deadline absent_after_min runs while the client has no connection, from its last message (after a broker restart, from the start). queued = "cancel" cancels waiting orders with the reason hub_absent, running = "cancel" sends runners a cancel with the same reason.
  • Secrets and services are checked on acceptance by client label before the runners are checked: the first disallowed secret gives rejected_secret_not_allowed (“secret X is not allowed for label Y”), a service gives rejected_service_not_allowed. For a client with [commands] mode = "named" the command of each step is a name: an order without steps and an order with a name that none of the runners known to the broker has are rejected with rejected_command_not_allowed (the reason holds the first such name and the runner names). An accepted order carries the names in its requirements (commands), so it fits only a runner that declared all of them, and the decision is not reconsidered on policy reload; such an order gets named_commands in Assign. The broker discards names sent in the order of another client. Names that different runners have separately, but no single runner has all at once, give rejected_no_matching_runner on acceptance with per-runner reasons (“command X is not described”), like other requirements on a single runner. Runner names are not stored in broker.db: after a broker restart they are known when the runner is online again, and until then an order of such a client is rejected with the reason “runners have not returned yet after the broker restart, retry” (if there are no runners with names and the broker has not restarted — “this broker’s runners do not report names”). Accepted orders keep the names in broker.db and remain in named mode after a restart.
  • capabilities_update replaces the runner capabilities entirely (the “same computer” reference is assigned by the broker) and takes effect at once on acceptance and assignment. The service report is visible in the runner list; if the head of the queue waits for memory (a CPU service does not hold the budget, so a CPU shortage does not cause eviction) and evict_idle is enabled, the broker sends stop_service once to each idle service of the online runners, without checking whether the runner fits the head of the queue (the event service_changed is sent only on a change of the service state or memory, not on the remaining_s countdown). The scheduler keeps the memory of live and assigned services in the pool budget (3.11).
  • The broker service at start rejects address = "container" outside a container.
  • A runner message about a job that is not assigned to it or is already finished is confirmed by the broker, not applied, and written to its log.

13.3 Inside the hub

  • The IPC server accepts CLI commands; profile parsing reads the profile from the working tree or a commit and builds the order.
  • The broker client holds connections to the known brokers, chooses a broker by hub-policy.toml, streams output and result back.
  • The Reaper watches the sender process and cancels the orders when it dies.
  • The storage hub.db (outbox, active orders, broker list) and the log copy in the sender directory; the event bus feeds the dashboard SSE and wait; the dashboard HTTP on loopback.

Hub clarifications where the sections above do not define the behavior:

  • An active order keeps the order as it was submitted in active_order.spec_json: after a hub restart a returned (returned) order is offered again to other brokers with seq 1, and a “same computer” order ends with a hint. hub_meta keeps the greatest issued JobId time (job_id_floor): after a restart JobIds are issued above it, even if the clock went back. The hub.db schema is version 2; a version 1 file is upgraded by migration.
  • An order whose record in hub.db cannot be read (corrupt JSON in the outbox, or neither a broker nor a stored order) ends at once with the refusal rejected_order_unreadable, at hub start or on resend. A recovered job with a pending cancel in the outbox is considered cancelled: the reaper and a repeated cancel do not place a second cancel; a repeated cancel of the same job answers with its JobId and places nothing.
  • Broker confirmations (accepted, ack, resume, cancel_ack) are applied no further than the greatest seq actually sent to this broker for this job. A failed write of the broker choice puts the order into waiting with a retry after query_retry_s. If after a broker refusal no brokers remain in the allowed zones of the order, the order receives the reason of the last refusal, not rejected_zone_not_served. The handle file is written after the order is written to the outbox. A cancel_ack denied outside the outbox arrives with seq = 0 and is not part of the seq stream.
  • The CLI channel is accepted only over local IPC (PeerAccess::Local); the OS user is taken from what the OS reports about the peer and replaces os_user in the submitted identity. A network peer receives refused (unauthorized).
  • The handle file temp/runner/<job-id>.json and the log copy are written by the hub (it knows the JobId and the path, active_order.handle_path). The sender directory (cwd, worktree_root) must be absolute (on Windows, with a drive letter) and without . and .., the JobId must consist of letters, digits and hyphen, otherwise the order is rejected with the error malformed. The hub issues the JobId from its own time in milliseconds and a counter.
  • These are rejected at once, without a JobId: a profile or flag error (error malformed, including --timeout greater than the profile timeout and --mem or --cpu equal to zero), an unpushed commit of a platform order (rejected_commit_not_pushed), a “same computer” order without a configured local broker (rejected_no_local_broker). The other refusals arrive after the JobId: to whoever waits (--wait), and into the log copy.
  • done is accepted only on the connection where the JobId of this job was issued, and has no reply; otherwise it is an error. The reaper watches every job without --detach regardless of done. wait on a finished job answers with its result while it is in memory (the last 1024 results), otherwise with an error; closing a wait connection cancels nothing.
  • A broker without a reported zone is considered remote, a local broker is always local. Only online runners are considered matching; least_loaded chooses the broker with the greatest number of matching runners, and on a tie the earlier one by [brokers] order. If no allowed broker answered, the order waits in the outbox and the choice is repeated after query_retry_s and on each broker connection.
  • A rejected (rejected) or returned (returned) ordinary order is offered by the hub to the remaining brokers; both seq streams of the order start again from 1 (HubStore::rebroker); the queueing time at the new broker is the moment of its acceptance by its clock (3.5), the queue position at the former broker is not carried over. If no brokers remain, the order is rejected with the reason of the last refusal. A “same computer” order after a refusal or return ends with a refusal with a hint to run localrunner up. A refusal of the local broker to accept the OS user (unauthorized) rejects waiting “same computer” orders with rejected_local_user_unknown.
  • Messages from a broker that does not hold this order are confirmed by the hub and not applied. A repeat of seq is confirmed again; a skipped seq is the error seq_gap, the connection is closed and established anew. After connecting, the hub sends resume with the last accepted seq for each job of the broker and resends its outbox.
  • A cancel before the broker is chosen ends the order on the spot (cancelled). A cancel of a sent but not accepted order removes the order record from the outbox and places the cancel; a refusal of it (cancel_ack denied without seq) ends the order on the spot. A cancel of an accepted order waits in the outbox for confirmation, the result comes from the broker. A foreign label is cancelled only with --force, who and why go to the log copy.
  • The deadline [outbox] ttl_hours is counted from the write of the order to the outbox; with on_expire = "fail" an order without accepted ends with rejected_outbox_expired without sending a cancel. The reaper checks senders at hub start and every 5 s; an unknown answer (the start time cannot be obtained) is not considered death, one warning is written about it.
  • Queues are bounded: no more than 1024 frames per broker (an overflow of the resend defers the remainder to the next second, an overflow on confirmation closes the connection), 256 replies per CLI connection; a slow wait observer is disconnected (the hub closes its connection, the CLI sees the end of the stream), the full output remains in the log copy; a result pushed out of the last 1024 is forgotten. Each such overflow is written to the hub diagnostic log with a count accumulated by its kind (the field total). Reconnection to a broker is with a pause starting at 1 s, doubling up to 30 s.
  • The CLI command jobs (--mine) answers over the active jobs of the hub of the same OS user and label, without --active also over the results in memory. The real implementation of Repository (git) is in lr-cli.

13.4 Inside the runner

Runner agent clarifications where the sections above do not define the behavior:

  • Each message about a job (started, chunk, step result, result) is first written to the outbox runner.db with the next seq of the job and only then sent; a new connection after hello, welcome, resume and the service report sends all unconfirmed records again in order. The broker ack removes records up to its seq, the broker resume up to the one it names. The broker error seq_gap closes the connection: reconnection resends everything from the first unconfirmed one. Records of started and of the result are retried once a second on a storage failure, a chunk and a step result are written to the log as an error and discarded; the result of an assignment refusal is written in one attempt (on failure, an error in the log), so as not to stop the session. An outbox record that cannot be read is replaced by a chunk without a step with the same seq (“[localrunner: stored message N is unreadable]”) and an error in the log: there is no hole in seq. Each send is limited to three heartbeat intervals: a broker that stopped reading is closed and reconnected to.
  • Incoming assign and cancel pass a strict seq check per job: a repeat is confirmed and discarded, a skip receives the error seq_gap. A job that the runner has already executed, is executing or still holds results for is not started again, even if the broker assigned it again (after a restart): the assignment is confirmed, and the outbox resends the earlier results. An assignment that arrives during another job or after drain ends as failed with a text (“runner is busy with job X”, “runner is draining”), as does a job with a timeout above the runner ceiling (“job timeout 7200 s is above the runner ceiling 3600 s”).
  • Connection: heartbeat with the interval from welcome (15 seconds, clamped to 1–3600 seconds); a broker silent for three intervals is considered lost. Reconnection with a pause starting at 1 second, doubling up to 30. The deadline for killing a job when the broker is unavailable is taken from welcome and settings_update (180 seconds by default, no more than a day) and is counted from the break of a session that passed welcome — regardless of how long the connection attempts and the wait for welcome last; [grace] broker_lost_kill_s in runner.toml only shortens it. A job killed this way receives cancelled with the reason broker_unavailable; an authorization refusal (unauthorized, key_revoked) kills the tree at once, deletes the outbox and stops the agent.
  • The runner marks a running job with the file active-job in the state directory before the assignment is confirmed; if the marker could not be written, the job is not started and ends as failed (“active job marker not written: …”); if at start the marker remained and there is no result in the outbox, it sends failed with the reason runner_restarted and does not restart the job. At start the runner also kills orphaned services from the registry (only when the pid and start time match; without a start time or with an unknown process lifetime — a warning without a kill). A service leaves the registry only when killed or already finished, otherwise the record stays; stop_service behaves the same way., forgets finished jobs older than a day and cleans the cache.
  • The source step. For the working tree — only the working directory of the job, nothing is started; a nonexistent directory gives failed. For a commit the repository address and branch arrive in the order code (code.repo_url, code.branch, optional fields, compatible with the earlier version); without an address the job fails. The project directory {workspace} = <state>/workspace/<project>-<hash of project and address> (a different address has its own mirror), the mirror is {workspace}/mirror.git, the job working copy {job_dir} = {workspace}/jobs/<job>-<hash of client and job>. The runner does mkdir itself, then the steps git clone --mirror -- <address> <mirror> (only without a mirror), git -C <mirror> fetch --prune -- origin, git -C <mirror> worktree prune, git -C <mirror> worktree add --detach -- <job_dir> <commit> in the project directory; then the profile steps in {job_dir}. The default steps are not part of the numbering of the order steps: their output goes as chunks without a step, a failure gives failed with the text “source step failed: <name>”, and the profile steps give skipped. Leading order steps named source replace this sequence: they are ordinary order steps (with their own results), they run in the project directory, and the runner substitutes {repo_url}, {commit}, {branch}, {workspace} and {job_dir} into them. The working copy is deleted when the job ends, the mirror is subject to [workspace] (an entry in the cache index).
  • Security of the source commands. Values are checked before substitution: the address — schemes https, http, ssh, git, file or the form user@host:path, only the characters [A-Za-z0-9._~:/@+=,-], no longer than 2048, without a leading -, without :: (remote repository helpers such as ext::) and without a host starting with -; the commit — 7–64 hexadecimal characters; the branch — git reference rules over [A-Za-z0-9._/-]. The address, branch and paths are put in double quotes; an argument with ", $, `, %, !, ^, control characters or a trailing backslash is rejected, not escaped; -- stands before the positional git arguments.
  • Environment and secrets. The job environment: PATH (only [env] path in runner.toml; the job does not inherit the PATH of the runner process; [env] path is mandatory: without it the runner does not start, as with an error in mem_mb and cpu (“runner.toml has no [env] path: jobs get PATH only from it (spec 13.4); set [env] path”); init and runner join without a template write it with the PATH value of the shell they were started from; the second line of defense — a job assigned to a runner without PATH ends as failed before starting (“runner.toml has no [env] path, so the job would get no PATH; set [env] path (spec 13.4)”); [programs] are searched for in the same [env] path), HOME, TEMP (and TMP and TMPDIR; all three point to the job's private directory <state dir>/tmp/lr-<job-id>), LOCALRUNNER_JOB_ID and LOCALRUNNER_CACHE_<NAME>; on Windows the variables without which the OS itself does not work (Winsock, CryptoAPI, program lookup) are added to them: SystemRoot, windir, ComSpec and PATHEXT with values from the runner environment. Other variables of the jobs are set in [job_env] as NAME = "value" (JAVA_HOME, CARGO_HOME); HOME given there replaces the detected value; PATH (it has [env] path), TEMP, TMP, TMPDIR and names starting with LOCALRUNNER_ are refused when runner.toml is read. There is one mechanism for variables, so the [env] section holds only path; a variable written under [env] is reported as an unknown key. The [programs] checks run in exactly the job environment (with the temp directory of the runner process instead of a private one), each takes up to check_timeout_s seconds (10 by default), and a runner without a needed variable does not offer the program. The profile has no env field and cannot require a variable: the environment of a runner belongs to its owner, who sets it in runner.toml (init and runner join without a template write HOME of their shell into [job_env]; when the file has none, it comes from the OS user of the runner process). The broker chooses a runner only by programs, platforms, tags and resources, so a difference between runners (for example a JAVA_HOME that only some have) is declared by the owner as a program with a check or as a tag. This is a property of the OS, not of the consumer; the job does not inherit the rest of the runner environment. A secret is passed as a variable named after the secret in upper case (non-letters and non-digits become _): registry_auth → REGISTRY_AUTH. A secret named by a step is received only by that step; an allowed secret that no step named is requested by the profile and visible to all steps. A secret whose variable would coincide with PATH, HOME, TEMP, TMP or would start with LOCALRUNNER_ (the name is converted to upper case, so the comparison does not depend on case) ends the job as failed before starting (“secret X would replace the reserved variable Y”). The profile steps after source get the remainder of the job timeout, rounded up to the second.
  • Cache. The cache directory is <state>/cache/<hash of client key>/<project>/<name> (the parts are safe names with a hash). With [cache] share = "project" the broker sends in Assign, instead of the client key, the shared cache_client = "shared:project" (resembling neither ed25519: nor local:), and the directory is the same for all clients that claimed this project (the project is claimed by the client, see 3.5 and the policy check warning); the client key stays in the working directory and in service reuse. The policy is taken at the moment of assignment; without the field the runner keeps the cache per client. Without max_size_gb and retention_days there are no limits; evict knows only lru. Cleanup runs at start, before each job and once an hour, including during a job; the caches and mirror of the current job are not deleted (the job occupies them until cleanup, cleanups and occupation go in turn). After a job the runner updates the size and time of use and sends capabilities_update with the cache fill.
  • Disk. After the cache cleanup before a job the runner compares the order’s disk_mb with the free space of the volume (of the working tree — for the working tree, of the state directory — for a commit) minus the reservations of the other runners of the installation: each holds a file <runner>.mb (“MB pid start-time” of its process) in disk-reservations/ of the installation state directory while its job runs, and at start removes its leftover file. The runner first writes its own reservation, then adds up the others and, if there is not enough, removes its own: two runners deciding at the same time may both refuse, but will not both take the same space. A reservation whose process is dead by pid and start time is not counted and is deleted; an unreadable reservation is counted as having taken all the space (a refusal naming it, capacity 0). Reservations are counted without distinguishing volumes. If there is not enough space, the job does not wait but ends as failed with the reason code disk_insufficient and the text “not enough disk: the job needs N MB, M MB are free on <path> after the cache cleanup (K MB reserved by other runners)”, the steps are skipped; a volume that could not be measured is not checked (a warning in the log). The runner capacity disk_mb is the free space of the state directory volume at the moment of the report minus the reservations of others (if it cannot be measured, the value at start).
  • Limits and cleanup. Before the start the runner builds the limits of the job from the broker [resources] (sent with the assignment) and its own [limits], reserves the disk with the margin factor and passes the limits to the executor (lr-exec). After the job ends it runs the matching [[cleanup]] hooks, each as a short job in the state directory, with the job environment, LOCALRUNNER_JOB_LABEL and the [job_env] variables. The hook output goes to the job log under the header cleanup <name>. Details in 3.14.
  • Sleep inhibition (section 10) is held while a job runs and released when it ends: on Windows a separate thread holds SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED), on macOS /usr/bin/caffeinate -i -w <runner pid> runs, on Linux nothing is done. The end of the runner process releases the inhibition by itself.
  • Command names. The runner declares in its capabilities the [commands] names (the field commands). An assignment with named_commands is translated by the runner into its own command lines before the active-job marker; a name without a description is the result failed with the code rejected_command_not_allowed, no step is started, all steps receive skipped. The lines are substituted before the source step, so its substitutions also apply in the runner’s line.

14. Data

One SQLite database per side. The broker has broker.db: the history of runs on its runners (with the client), the computer registry, runners, the order queue. The hub has hub.db: the outbox (orders without Accepted and cancels), active orders and the list of brokers. The runner has runner.db: the outbox, the service registry (for finding orphans) and the cache index. Inside broker.db the links are ordinary foreign keys; between hub.db and broker.db they are logical, by JobId. Pools and limits live in policy.toml, not in the database. Full logs are files in the broker logs/<job-id>.log.

  • The final state of a job is written once: a repeated delivery of the result or a second final state does not change the row. For a running job it is determined only by the runner report; cancelling a waiting order removes it at once.
  • The run record stays on the broker within the retention period. The hub keeps only the outbox and a copy of the log: an outbox entry is deleted on the broker Accepted, and the broker does not know what is in the hub outbox.
  • History retention on the broker: 30 days and 2 GB of logs, 365 days of rows by default (policy); cleanup goes from the oldest and does not touch active jobs.
  • The broker.db schema is at version 2: job gained peak_mem_mb and peak_disk_mb, runner gained enforcement. An older file is migrated at the first start, with a copy broker.db.bak-1. In the history output the two columns appeared before BROKER, so scripts that read it by column number must be updated. Protocol additions (limits in the assignment, peaks in the result, machine load in the heartbeat, enforcement in the capabilities) are optional fields, so older peers keep working and the protocol version is unchanged.
  • order holds only the queue up to assignment; the run state is kept by job.state, and after assignment the order row is deleted.
  • The accepted seq is stored next to what it numbers: on the broker in job.recv_seq_hub and job.recv_seq_runner (outgoing to the runner — job.send_seq_runner; when an order is re-queued, the runner counters are reset), on the hub in active_order.last_seq, on the runner in runner_recv (one row per job; cleaned together with finished jobs by the retention period). A confirmed outbox entry is not deleted but closed (acked_at), and the closed entry with the highest seq of the job remains: the next seq is always one greater, even if the queue is empty.
  • machine holds only public keys and client labels; the registration token of the ci runner is not written anywhere.

Termination reasons. Every final state and every refusal carries a reason code, visible in history, explain and on the dashboard: runner_stopped (the runner was stopped by the command down --cancel), runner_removed (the runner was removed), broker_unavailable (the broker did not return within the grace period, the job was aborted), runner_lost (the runner was lost, the period expired), client_removed (the client key was revoked), sender_gone (the reaper cancelled the order of a dead sender), hub_absent (the hub was absent longer than absent_after_min), service_failed, secret_missing, runner_restarted (the runner was restarted while a job was alive, result failed), cancelled_by_user, disk_insufficient (the runner lacked free space for the disk_mb of the job even after clearing the cache, result failed), resource_exceeded (the runner killed the job for exceeding the declared mem_mb or disk_mb in the kill mode, result failed, text declared mem_mb exceeded: declared X MB, peak Y MB), rejected_* (refusal on intake with the name of the reason, for example rejected_pool_memory — the profile asks for more memory than the pool has, or rejected_override_above_pool — the --mem or --cpu value of this run asks for more than the pool). An order assigned to a runner but not started, when the runner is lost, returns to the queue: at once if the runner has not yet confirmed the assignment (ack on assign); a confirmed assignment is held for this runner for the grace period [grace] lost_min from the loss of connection (the runner itself waits for the broker the same time before it kills its job) and returns to the queue only if the runner did not come back within this period with started, a result or resume that names this job (hello without information about the job does not lift the period; resume without it means the runner did not receive it, and the assignment returns to the queue at once), so one assignment is not executed by two runners at the same time. After a broker restart an assigned but not started job is held for its runner for the same period from the broker start (the assignment confirmation is not stored, so it is considered confirmed). A window remains: if the connection breaks while the runner ack is still in transit, the assignment returns to the queue at once and may be executed twice; a late message about a job that already has a final state does not change it and is written to the log. A job in cancelling on a runner that is lost ends through lost.

The remaining entities are simple and described by the table above: a step repeats the job states, an order after assignment becomes a job, the link of the hub with the broker is available or unavailable.

16. Scenarios

Usage scenarios by role as sequence diagrams. A solid arrow is a message, a dashed one is a reply, a framed block is a refusal branch or a condition. The participant “User” is a person or an agent session.

Installation and access

16.1 First start on one computer

Roles: the computer owner. The up command starts the three roles as separate processes; all are connected by local IPC.

16.2 A runner joining from another computer

Roles: the owner. The runner connects to the broker itself: no incoming ports are needed on its computer. The owner enters the broker address by hand; the code lifetime is set by [join] code_ttl_min (1 hour by default).

16.3 A client computer hub joining

Roles: the owner, the user. The hub joins as a client with its own key; the owner sets the label (for example, ci) when issuing the code. A hub on the broker computer does not need a code.

16.4 Key revocation and runner removal

Roles: the owner. Every member has its own key, so revocation is targeted.

16.5 Broker service on a dedicated computer

Roles: the owner. The broker executes nothing, so it runs as an OS service under a separate account and does not depend on who is logged in.

16.6 Several runners on one computer

Roles: the owner. Parallelism means several runners: one code for N joins, each runner has its own key, name and state directory.

16.7 Several OS users on one broker

Roles: the owner, the users. There is one pool and one broker. The hub and runners of the users connect to the service over local IPC; “same computer” works only within one OS user.

16.8 A laptop changes network

Roles: the hub. The broker determines the hub zone by the connection address, checking it against [networks]; the user enters nothing. A mobile network is remote.

16.9 Docker Compose: broker and runner in containers

Roles: the owner. State lives in volumes: recreating the containers does not require joining again.

16.10 Update, removal and move of a node

Roles: the owner. An update replaces the binary, the database schemas migrate themselves. Removal keeps the keys and history by default.

Execution

16.11 Run on the same computer (working tree)

Roles: the user, the agent. The profile is read from the working tree, the runner works in the sender directory. The order never goes to the network.

16.12 Remote run of a commit on another platform

Roles: the user, the agent. A runner of another installation works with the pushed commit. A command has one platform; a second platform is a second job by a separate command.

16.13 Broker choice and the “no suitable runner” refusal

Roles: the hub. The order zone boundary is hard: a “same computer” order does not go to the network, an order with zone lan does not go to remote.

16.14 Waiting in the queue: priorities and gap filling

Roles: the broker. Policy decides the order; a small order bypasses a heavy one only if it does not delay its reserved start, which is computed from the timeouts of the running jobs.

16.15 A job with a service, cache and secret

Roles: the runner, the broker. A service starts only as part of an order after resources are reserved; the job environment is built from scratch.

16.16 Run from GitHub Actions

Roles: ci. The GitHub ci runner takes no resources: its job places an ordinary order through the hub of its computer with the client label ci.

Cancellation and failures

16.17 Cancelling a job

Roles: user, agent. The hub checks the label and the OS user; the broker allows cancelling only orders of the same key.

16.18 Dead sender

Roles: hub (reaper). The sender is the process that called the CLI. A job with --detach outlives it.

16.19 Hub connection loss and return

Roles: hub. An order belongs to the hub key, not to the connection: a short loss (laptop sleep, network change) cancels nothing.

16.20 Broker crash and return

Roles: broker. Orders without Accepted wait in the hub outbox, accepted ones are kept on the broker, runner results wait in its outbox.

16.21 Runner loss and job timeout

Roles: broker, runner. The broker itself frees the resources of a lost job; the runner receives the loss deadline at registration.

Management and viewing

16.22 Policy change

Roles: owner. Only a person sitting at the broker computer edits it; an error leaves the previous policy in place.

16.23 Viewing state and the dashboard

Roles: user, agent. The dashboard is only an addition: everything on it is available in the CLI with --json.

16.24 Stopping a runner

Roles: owner. Two ways: finish the current job or cancel it.

16.25 Autostart by role

Roles: owner. Optional and independent of a manual up. The broker is installed as an OS service; the hub and runners run under the user.

18. Out of scope

  • Phones and physical devices over USB/ADB. Android and iOS jobs run on an emulator or simulator provided by the runner computer.
  • NAT traversal and tunnels: a broker outside the local network must have a reachable address.
  • Submitting jobs, editing profiles and configuration, starting and stopping runners from a web page (it offers only cancel).
  • Remote policy editing and commit packaging through the broker.
  • Any knowledge of a specific command or consumer tools inside the core.
  • Limits on disk I/O, pinning a job to cores, pausing running jobs, a proxy for the Docker socket and OS disk quotas (a separate volume, VHD, tmpfs); the core knows no containers or build daemons, cleanup is a command written by the owner (3.14).
